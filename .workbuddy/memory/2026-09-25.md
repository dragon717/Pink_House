1. `docs/TIME_HALL_CLOUDKIT_CONSOLE_SETUP.md` §3 与 `publication/README.md` 的「凭证」一节
   写「在 Console 建 key → 下载私钥 PEM」——**与 Apple 口径相反**。Apple 的正确流程是：
   本地 `openssl ecparam -name prime256v1 -genkey -noout -out eckey.pem` 生成密钥对，
   **只把公钥**（`openssl ec -in eckey.pem -pubout`）粘进 Console 的 API Access →
   Server-to-Server Keys，保存后 Console 回填 Key ID；私钥永不离开本机。
2. `publish_adapters.sign_request` 只签 `date_bytes + b":" + body`，
   而 Apple 规范是 `[date]:[base64(sha256(body))]:[URL subpath]` 三段。
   README 自己也承认「未经真实环境验证」——真机联调前必须先修这里。
   （另：设计文档 §6.3/§6.4 的 THDataPack/THMedia 字段名与实现不一致，
   实现 + Console 配置清单为准：`partitionID/releaseSeq/sha256/byteCount/asset`。）

**推荐方案**：运营发布通道（Mac，s2s 凭证写）+ 设备只读消费通道；普通用户对
THRelease/THDataPack/THMedia 零写权限（World 只读）。v1 建议把覆盖层整包当
单个分片（partitionID 形如 `pink-house/shop-catalog/all`）发布，客户端下载后
直接当作 `overlayCatalog` 走现有合并规则。
**关键坑**：`CatalogAsset.originalURL` 里的 `local:<文件名>` 引用跨设备无效，
运营上传图必须改走 THMedia，客户端要建立 `mediaKey → contentHash → 本地缓存路径` 解析。

## 资产上传卡点突破（下午续）
- **bad upload receipt 的根因找到一半**：上传端点响应的 `singleFile` 里服务器返回自己的 `fileChecksum`（短值，如 `AWQXZrzRAccBMoY8OAMNWzOB5md2`，非我们提交的 SHA-256），receipt 尾部编码了该值。此前 modify 提交的 fileChecksum 是**自己的 SHA-256**，与 receipt 内嵌值不一致 → 校验失败。cloudkit.js 的 `consumeUploadReceipt` 把**整个 singleFile 对象原样**写回记录字段（`.then(e=>e.singleFile)`），不是自拼三件套。
- **新卡点（覆盖了上面）**：modify 全部报 `CREATE operation not permitted (ACCESS_DENIED)`——**s2s key 不绕过安全角色**，Apple 官方口径「inherited privileges of the creator of the key」。此前 Console 配置文档让把所有角色 Write/Create 收光 → s2s（继承开发者=已认证用户身份）也被拒。时间线证据：角色收紧前探针能跑到 receipt 校验层。
- 已修正 `docs/TIME_HALL_CLOUDKIT_CONSOLE_SETUP.md` §2：两段式（Development 放宽 Authenticated 行 Create+Write；Production 用 Custom Role + 开发者 User Record）。

**真正的根因在客户端流程（三处，都能单独造成「列表空的」）**：
1. **远端层只进内存，冷启动不恢复**：`ShopCatalogCloudSyncService` 第 3 步

2. **节流越过空态**：`lastCheckedAt` 存在就跳过 30 分钟，会把「本地还没有内容」的
   首次检查一起吞掉（TestFlight 空态写过 `lastCheckedAt` → 换 Xcode 后 30 分钟内打开必空）。
3. **零诊断**：链路没有一行日志、UI 不展示状态，失败与「没发布」在界面上都是空列表。

**修复**（均在消费端）：
- `ShopCatalogCloudSyncProtocol.catalog(fromVerifiedPack:)` + `ShopCatalogPackCache.restoredCatalog()`
  = 冷启动从已验证缓存包恢复的唯一入口。
- Service 新增 `hasRemoteLayer`：进入先尝试恢复；节流只在有远端层时生效；
  「序号未变」「payloadHash 未变」两条捷径都加上「且内存里有」；缓存包丢失 → 重新下载。
- 全链路 `[ShopCatalogSync]` 日志（发布版保留）；首屏 `syncBanner`（syncing / nothingPublished /
  failed 带原因与「立即重试」）+ 导航栏手动刷新按钮。
- 回归 4 例（`ShopCatalogCloudSyncTests`）：冷启动恢复、有内容时零网络请求、
  无内容时节流放行、缓存丢失触发重下。

## 需求：图片没上传，拉不下来（「数据到了、图全空」）—— THMedia 链路打通

   引用改写 `thmedia:<contentHash>`；`bundle:`/http 不动；**缺图退出码 5 硬失败**。
   新参数 `--shop-catalog-media` / `--shop-catalog-archive`（后者自动解 tar）。
   先 strip 归档再 collect，归档专属图不白传。
3. 消费端 `ShopCatalogMediaStore`（新）+ `ShopCatalogPackCache` 媒体缓存：`thmedia:` 按需下载 →
   落盘 Caches/ShopCatalogSync/media/ → 命中缓存不再打网络；会话内失败不重试。
