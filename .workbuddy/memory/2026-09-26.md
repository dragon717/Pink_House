### 验尸要点（下次别踩）

- ⭐ **`NSData.compressed(using: .zlib)` 给的是裸 deflate（RFC 1951），不是 zlib 封装。**
  名字骗人。2026-09-26 实测（macOS 26）：输入 0B→2B `03 00`；1B→3B `73 04 00`；
  512B→20B 首字节 `0x7B`。首字节从不是 `0x78`。20 字节恰等于 Python
  `zlib.compress(src,9)` 去掉 2+4 封装后的 deflate 段长。
  **所以绝不能剥「2 字节 zlib 头 + 4 字节 Adler32 尾」** —— 那会把 deflate 数据本身截断，
  产物必然 `deflate 解压失败 / Cocoa 5377`。同文件 `decompress` 的注释早就写明了这条，
  写 `compress` 时要先跟它对齐口径（我当时没看，白跑两轮 6 分钟的全量测试）。
  自检手法：`xcrun swift` 跑个 10 行探针，把产物喂 Python `gzip.decompress`，比等 xcodebuild 快两个数量级。
- 「判别是否 zlib 封装」若要写，阈值**必须 ≥ 8**（2 头 + 2 字节空 deflate 块 + 4 Adler32）。
  我第一版拍脑袋写 `>= 6`，结果空数据（2B）与 1 字节输入（3B）被判成「长度异常」直接抛错。
- `@MainActor` 的 store（持有 SwiftData 容器）进单测，**测试类本身要标 `@MainActor`**，
  只标在 publisher 那个类上不够；`job.nextRetryAt?.timeIntervalSince(now)` 是 `Double?`，
  直接喂 `XCTAssertEqual(_,_,accuracy:)` 报类型错，要 `try XCTUnwrap`。
- `ShopCatalogImageStore.url(for:)` **只拼路径、不查盘**，对不存在的文件也返回非 nil。
  直接用它会让人「文件不存在」掉进 `unreadable` 分支，而 `fileMissing` 的语义
  （沙盒重置 / 漏带图 → 重新选图）与 `unreadable`（文件在但读失败 → 重试）对运营是两回事。
  默认 `resolveFile` 已补 `fileExists` 检查。
- `ShopCatalog` 等模型有**显式 init**：参数顺序必须按声明序（sizeCharts 在 assets **之前**），
  且 `CatalogProduct` 的 `category` 无默认值。
- 会话中途**另一个 agent 会话**把领域层 `git mv` 到 `Packages/SharedCatalog` 又整体回滚，
  我的领域层改动被覆盖两次 → 本仓库并行会话活跃时，改完必须立刻 `git diff` 复核。
- 构建用独立 `OBJROOT=build/objUpload`（避免与并行会话撞 build.db 锁）。
- **别在脚本运行中途改脚本**：bash 按字节偏移增量读取，我在 `run_ops_upload_tests.sh`
  运行到一半时改了文件头，结果脚本从错位的偏移继续读 → `line 51: syntax error`，
  收尾的结论行全部没打印（xcodebuild 结果本身没受影响，但白白多一轮排查）。

### 第二轮：补完方案二 §5 的「重试入口」

核对两份方案逐条落地情况时发现唯一一处**代码内**未完成项：
方案二 §5 要求「下载失败显示明确占位**和重试入口**，不把图片当作没有图片」，
而 `ShopCatalogAssetImage` 失败后只是 `remoteMediaFailed = true`，占位图与
「本来就没图」长得一样，且**没有任何恢复路径**。

- `ShopCatalogMediaStore.clearSessionFailure(mediaKey:)`：新增生产可用的重试 API。
  只清「本次会话失败记忆」，不动已装好的缓存。
- `ShopCatalogAssetImage`：
  - 新增 `failedPlaceholder`（暖底 + 「加载失败，点按重试」+ 可点按 + a11y button 语义），
    与原有 `placeholder`（照片图标 = 本来没图）在视觉与可操作性上都区分开；
  - `content` 里插入 `else if remoteMediaFailed { failedPlaceholder }` 分支
    **排在本地兜底图之后** —— 本地 `UIImage` 能解出来时优先显示真图，不能被失败提示盖住；
  - `AsyncImage` 的 `.failure` phase 也改用 `failedPlaceholder`（原来落进 `default:` 显示普通占位）；
  - `retryLoading()` 必须**同时**做两件事：清 store 的会话失败记忆 **且** 换
    `asyncImageReloadToken`。只把 `remoteMediaFailed` 置回 false 是无效的 ——
    store 会直接返回 nil，表现成「点了没反应」。
- 新增 `ShopCatalogMediaRetryTests`（3 例，`@MainActor`）：用一个**永远失败**的
  `private actor FailingMediaReader` 数「到底有没有真的打网络」。
  走失败路径时 `download` 在 catch 里直接返回 nil、**不碰缓存目录**，所以这组用例零落盘、
  不需要 `useTemporaryForTesting()`。断言：首拉计 1 次 / 重复拉不再计数 /
  `clearSessionFailure` 后计 2 次（证明重试真的重新发请求）/ 清一个键不影响另一个键 /
  `mediaKey == nil` 零网络。

### 一轮审计结论（两份方案逐条）

- **代码内可完成的全部完成**：7 个测试类 35 例全绿（`** TEST SUCCEEDED **`），
  Python 发布端自检全绿。
- 方案一 §5.3 `minimumReaderVersion` **不提升**，理由已写进
  `ShopCatalogOpsPublisher` 的注释：`ShopCatalogSyncProtocol.readerVersion` 恒为 1，
  历史构建也都是 1（加入 `thmedia:` 支持时没跟着抬），所以这个版本号目前区分不出
  「认不认 mediaKey 的读端」；此时提升会**同等拦下所有已发布客户端**。
  要启用这条闸门必须配套：① 消费端 `readerVersion` 抬到 2 并发出新包 →
  ② 把 publisher 的默认值显式写死成 2（别再依赖 `?? readerVersion`，
  否则运营端一升级就把自己变成「只允许 2」的发布者）→ ③ 再发布 `minimumReaderVersion=2`。
- 注意：`ShopCatalogOpsMediaStaging.rewrite` 把 `local:` 改写成 `thmedia:<hash>` 时
  **连 `originalURL` 一起改写**，所以不认 `thmedia:` 的旧客户端**没有 URL 兜底**，
  商品图会全部落到占位（正文/价格仍显示）。这是 §5.3 的既定前提，不是 bug。
