# 追加 · 同日第三轮：App 拉不回线上目录 —— **根因修复**

用户报「还是没有从 develop 云端公共数据库拉下来」，截图里 App 的报错是

    refused · 桥接器内部错误：URLError: <urlopen error [Errno 54] Connection reset by peer>

## 根因（两层，都已修）

**① 一个坏边缘 IP 掐死整次请求（主因）**

`api.apple-cloudkit.com` 解析出 5–6 个边缘 IPv4，其中 `17.248.216.28` 是
「**TCP 连得上、TLS 握手被立刻 RST**」（连续 3 轮 3/3 复现，0.01s）。

而 `socket.create_connection()`（urllib 内部走的那条）**只在 TCP connect 失败时**
才换下一个地址 —— **TLS 阶段炸掉不回退**，整次请求判死，其余健康地址一个都没试。
DNS 答案顺序轮换 → **坏 IP 排第一就失败，排后面就正常**，这就是「一会儿行一会儿不行」。
4 次外层重试每次重新解析、拿到同一份顺序 → 全撞同一个坏 IP，
耗时正好 = 重试等待之和 `0+5+15+30 = 50` 秒，最后吐「内部错误」。

**② 失败被说成「桥接器内部错误」，且 `retryable` 恒 false**

一次网络抖动伪装成程序 bug。运营只会去查权限、查数据，而正确动作是「原样重试一次」。

## 修法

| 位置 | 改动 |
|---|---|
| `publish_adapters.py` | 新增 `resolved_tcp_addresses` + `connect_first_ready`：**把「就绪」定义成 TLS 握手完成之后**，在那一层做地址回退；证书错误**不**参与回退（换地址也没用） |
| 同上 | `_FailoverHTTPSConnection`（只覆盖 `connect()`，重定向 / 超时 / HTTPError 全走标准库）+ `_FailoverHTTPSHandler` + **唯一出网入口 `open_https()`**；三处调用点（`_send` / 资产上传 / 资产下载）全部收口 |
| 同上 | `NetworkError`（**刻意不继承 `ProtocolError`**，否则会被降级成「被拒绝」并丢掉可重试）+ `NETWORK_FAILURES` 按**错误形状**判（同一件事可能是 `NetworkError` / `URLError(ConnectionResetError)` / `RemoteDisconnected`） |
| `ops_publish_bridge.py` | `EXIT_NETWORK = 7`；`main()` 单独分支：只读模式 → `refused` + **`retryable=True`** + 「不是程序错误，原样重试即可」；**发布模式 → `pendingConfirmation` + 不可重试**（写没写进去未知，R09 先查询） |
| `OpsCloudSyncView.swift` | ① `outcomeRetryable` 接进模型并显示「可原样重试」徽章（原先解析了却没人用）；② **新增 `pullFailure` / `pullFailureRetryable`**：下载卡片原先只有 `if let pulled`，**拉回失败一个字都不显示**，看起来像按钮不管用 —— 这是「还是没有拉下来」这个困惑的直接来源 |
| 新增 | `selftest_network_failover.py`（**16 项**，纯替身、不联网），含结构约束：适配层里**不得再出现裸 `urlopen(`** |

## 对抗性验证（同一份 DNS 顺序：坏 IP 排第一）

    旧路径 ✗ [0.13s] ConnectionResetError: [Errno 54] Connection reset by peer
    新路径 ✓ [0.17s] TLSv1.2 —— 自动换到健康地址

旧路径那行与用户截图里的报错**逐字一致**，根因闭环。

## ⚠️ 排查时踩到的坑：本机 shell 里装着代理，差点把根因认错

`env | grep -i proxy` → `http_proxy=https_proxy=http://127.0.0.1:61088`（agent 环境注入的透明代理）。
**有代理时 urllib 连的是 `127.0.0.1`，根本不会解析 `api.apple-cloudkit.com`** ——
那时看到的 RST 是代理的，跟边缘 IP 无关。真实链路实验必须
`env -u http_proxy -u https_proxy -u HTTP_PROXY -u HTTPS_PROXY …`。
判定证据：`ps eww <App pid>` 里**没有任何 proxy 变量** → App 是直连，才会撞上坏边缘 IP。

# 追加 · 同日第七轮：拉回改成「以线上为准逐条对账」，两端都与远程一样（用户口径）

用户需求原话：「拉取的数据应该是增量，而不是替换。若拉取的本地没有，则增量；
若拉取的没有，本地却有，则替换」→ 追问后确认目标是 **ios/mac 两端都要与远程一模一样**。
⇒ 落地成 **远程为准的逐条对账**（不是整份覆盖，也不是「保本地并集」）：

| 情形 | 结果 |
|---|---|
| 线上有、本地没有 | 加进来（增量） |
| 两边同一个 id | 用线上那份覆盖 |
| 本地有、线上没有 | **从本地移除**（「被替换掉」的就是这一支） |

## 7) 顺手发现并修掉：`previousReleaseSeq` 两端不同口径

- **两端分歧**（红线）：iOS `ShopCatalogOpsPublisher:359` 写
  `snapshot?.header.releaseSeq`（读到的那份头）；Python 侧写死 0

- **修法**：在 R07 基线闸门之后（`head` 已读到并比对过）、`stage("build","started")` 之前取

## 8) 顺手查明：`rootIndexHash` 每次都变（不是 bug，但会骗人）

`rootIndexHash` = `root-index.json` 字节的 SHA-256，而那份 JSON 里带 `publishedAt`
（构建时刻）。所以**同样输入重建两次，摘要是不同的**：

| 次 | 产物 rootIndexHash | payloadHash |
|---|---|---|
| 18:27 | `272e1798…6ef8` | `dc866091…` |
| 18:30 | `f97927f8…cb4f6` | `dc866091…` |

⇒ 别写「同样输入 ⇒ 同摘要」的断言，别拿它当缓存/幂等键。R07 比的是**线上发布头里那个值**
（App 记 `receipt.rootIndexHash`，`_head_matches_release` 再回读比一次，
两边读同一份 `release.json`）→ 自洽，不受影响。
