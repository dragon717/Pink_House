## D. 尺码表原图折叠展示（Request D）

需求：默认**收起**（隐藏），仅显示一个可点击触发入口；点击展开完整原图；再次点击或

### 做法：折叠形态也走纯逻辑，视图不自己 `if`

nonisolated 可单测）：由 `Plan.image` + 用户展开意图推导

3. **丢失警示不折叠**：`.unavailable` 是「图登记过但文件没了」的待办提示，不是图片内容；
   折起来用户就永远不知道要重新上传 → 直出，且不给展开入口（没有图可展开）。

视图侧（`ShopCatalogProductDetailView.swift`）：
- `@State isSizeChartImageExpanded` 只存用户意图；新增 `sizeChartImageSection(_:)` 消费 disclosure。
- 展开态 = 完整原图（复用共用 `chartImageBlock`，点图进全屏）+ 显式「收起」按钮；
  入口本身也可点收起（需求「再次点击**或通过关闭操作**」两条路径都给了）。
- 展开/收起同一个 `withAnimation(.easeInOut(duration: 0.25))`，图片块带
  `.transition(.opacity.combined(with: .move(edge: .top)))`。
- 表格**不参与折叠**（尺码表的主要信息），只有原图折叠——这也是它不能复用价格表卡那套

### 关键设计判断：**不设硬拦截**

草稿箱全状态可删（含已发布 / 已归档这份发布回执）。理由：批次删除的拦截文案原文就是
「…请先提交 / 发布，**或在草稿箱中删除这些草稿**后再删除批次」——若草稿删除也再拦一道，
那条指引就成了死路。安全性由「不碰覆盖层」保证：删掉的只是草稿箱记录，线上商品资料与
销售记录不变，因此不需要拦截，只需要把影响范围讲清楚。

## 尺码表按款式共享（Request G，2026-09-23）

需求：同款任一颜色填了尺码表 → 该款**所有**颜色自动共享同一套尺码数据，
后台数据与**前台商品页外侧的尺码信息**同步。

### 核心口径：尺码表属于**款式**，不属于颜色

新增 `ItemManager/Services/ShopCatalog/ShopCatalogSizeChartSharing.swift`（`nonisolated enum`，
纯逻辑、可单测），作为这件事的**唯一事实来源**：

- 同款判定：`seriesID` 相同 + `designKey` 相同（复用 `ShopCatalogSameDesignGrouper`，
  与详情页轮播的兄弟判定同源）。
- **读**：`canonicalChart(for:among:charts:)` —— 取款式范围内**最后一条有意义**的尺码表
  （有列/有行/有原图任一即有意义）。这样「只有红色填过」的历史数据**无需迁移**，
  粉色直接读到同一份；效果等同覆盖层 merge 的「后写者胜」。
  **读范围含已归档颜色**（归档一个颜色不该让整款失去尺码表）。
- **写**：`writePlan(chart:for:among:charts:)` → `WritePlan{removals, upserts}`：
  先整款移除旧行，再为**每个在售颜色**各 upsert 一行（行 id 复用既有行，否则
  `sizechart-<productID>` 确定性生成）。`chart == nil` = 清空**整个款式**。
  **写范围不含已归档颜色**。因此任一颜色的编辑（含新建发布、补录、深度编辑保存）
  都会把内容扇出到全色，天然幂等。
- 尺码轴方向判别 `sizeLabels(of:)`：真实数据里两种方向**都存在**——
  种子 `columns = [S,M,L]` / `rows = 胸围/腰围/裙长`，而手填/OCR 表角标「尺码」
  时 `rows = [S,M,L]` / `columns = 形体部位`。所以先看列轴是否 `looksLikeSizeRun`
  （**全部**词元都是尺码 token 才算，S/M/L/XS/XXL/均码/F/90/100…，`胸围`/`80-84` 不算），
  否则退回行标签。原 `sizeOptions` 直接 `rows.map(\.label)` 在种子数据上会把
  「胸围/腰围/裙长」当尺码显示，属既存错误，一并修掉。

### 改动点

- `ShopCatalogSizeChartSharing.swift`（新增）：如上。
- `ShopCatalogStore.swift`：`sizeChart(forProduct:)` / `sizeRun(forProduct:)` 改为走
  `canonicalChart` / `sizeRun(among:)`（原为 `sizeCharts.first { productID == }`）；
  `sizeRun` 顺位 = 款式尺码表 → 本商品 variants → 同款兄弟 variants。
- `ShopCatalogOps.swift`：三处写入（新建发布、补录已收录商品、`updatePublishedProduct`）

  （否则算不到种子里的同款兄弟）。
- `ShopCatalogProductDetailView.swift`：`sizes` 与预约弹窗的尺码区都改读
  `store.sizeRun(forProduct:)` —— 这就是「前台商品页外侧」的尺码来源。
- `ShopCatalogSeriesMenuView.swift`：点菜页卡片尺码 chips 同上。
- `ShopCatalogProductDeepEditView.swift`：新增 `chartInheritedFromAnotherColor`，
  当读到的尺码表 `productID != 本商品` 时给出「继承自同款其它颜色」提示，

# 需求 K：补录表单「款式 + 多颜色 SKU」一体化（完成）

**用户反馈**（截图 = 补录草稿页）：
> 「现在的表单结构不够合理，请实现在当前页面内添加多颜色 SKU 的功能。不需要让用户通过
> 『新建单品』来建颜色。把 designName（款式名）和多个 product（颜色的录入整合在同一个
> 表单里，让公共资料实现跨颜色复用，图片单独上传。」
> 「请在颜色 SKU 添加区，将图片上传组件与颜色字段直接绑定……不要单独弄一个图片上传区
> 让用户去对应。前端详情页切换颜色时，直接读这个对应绑定好的图。」

**判断**：需求 J 解决的是「已经录成多条之后怎么补同步」，这次是**更上游**——
根本不该让用户录成多条。所以没有再加同步入口，而是把 `ShopCatalogDraftDetailEditor`
从「一条草稿一个颜色」改成「**一个表单 = 一个款式 + N 个颜色行**」。

## 表单结构
商品（款式名/分类）→ 款式公共资料（面料/描述/尺码表）→ 价格组 → **颜色（N 色）** → 店家/系列。
颜色行内：颜色名 · 配色图（行内缩略图/传图/删图，第一张标「主图」）· 尺码勾选 · 「将发布为：X」预览。
**删除**了旧的「多行图片文本区 + 配色尺码文本区」与「复制到同款其他颜色」区块
（表单已能直接管全部颜色，同步区是第二个入口）。

## 新增/改动
- `Services/ShopCatalog/ShopCatalogDraftStyleForm.swift`（NEW，纯逻辑）：
  `ColorRow`（颜色行）、`StyleInput`（款式层整快照）、`colorName/of`、`styleName`、
  `productName(colorName:styleName:)`、`rows(of:sourceID:)`（源草稿排首位）、
  `identity/isSameStyle/sameStyleFamily`、`applyStyle/applyColor/makeNewDraft`、
  `resolveStyleName`、`validate`。
- `ShopCatalogOps.swift`：`ShopCatalogStyleFormResult`（updated/created/removed/skippedSettled）
  + `ShopCatalogDraftStore.applyStyleForm(sourceDraftID:style:colors:)`；
  **同款判定上移到纯逻辑层**，删掉原先私有的 `syncStyleIdentity`/`isSameStyleForSync`
  （`syncStyleInfo` 一并改走同一份判定）。
- `ShopCatalogOpsView.swift`：表单按 SPU/SKU 重排 + 行内图片组件 `ShopCatalogColorImageRow`。
- `ShopCatalogBatchDetailView.swift`：入口文案「＋ 添加单品」→「＋ 添加款式（一个表单录入整款，含多颜色）」。

## 五条关键口径（易踩）
1. **款式名一处决议**（`resolveStyleName`：显式优先，否则按源草稿派生，再给所有颜色共用）。
   让每条草稿各自派生 → 新加的颜色没有历史商品名可派生 → 空款名 → 商品名退化成只有颜色词
   → **「加一个颜色」变成两个款式**。这是本次最容易出的坑。
2. **同款家族口径唯一**（`sameStyleFamily`）：表单展示范围与仓库落盘范围必须同源，
   否则「界面看不到、落盘却认为该移除」的草稿会被当成用户删色而**误删**。
3. **移除颜色 = 删除其未发布草稿**（与「删批次不连带删草稿」不矛盾：批次是归组记录，
   颜色行就是草稿本身）。已发布的保留并计入 `skippedSettledCount`。
4. **图片与颜色强绑定的落点**：`ColorRow.imageRefs → draft.images(CatalogAsset，
   id=asset-<草稿id前8位>-<序号>，确定性幂等) → 每个 variant.imageAssetID = 本色主图`。
   前端详情页轮播取本商品 images（= 当前颜色）+ 同款其他色主图，切色读的就是这条链。
5. **商品名 = 颜色名 + 款式名**，对存量草稿幂等（派生款名再组合回原名），
   打开一次表单不改名；多色必须有款式名，单色允许留空。

## 踩坑
- 端到端用例首次失败 `missingColorName(index: 0)`：我造的源草稿是**空白新草稿**（name = ""），
  其颜色名当然是空 —— 真实场景由用户在颜色行填写。测试里显式赋值即可，不是产品缺陷。
- `currentReservationPrice` 在 `CatalogPriceArchive` 上，不在 `CatalogProduct` 上
  （要 `store.priceArchive(forProduct:)`），第一版测试写错编译不过。

# 需求 L：详情页「配色」行缺失 —— 系统性根因修复（完成）

**用户反馈**：后台发布了「生成色/粉紫色/蓝色」三个同款单品（段段方领 JSK），
前端详情页**只有标题「段段方领 JSK · 3色」和顶部「生成色」标签，没有「配色」这一行**；
同款另一条「段段长Jsk · 2色」却有「配色：红色 粉色」。要求全局修复该系统性 Bug。

**根因（不是漏写 if，是「同一件事两个数据源」）**：
| 位置 | 数据源 | SPU/SKU 下的结果 |
| --- | --- | --- |
| 标题「· N 色」 | 同款商品集合 `siblings.count + 1` | 3 ✅ |
| 「配色」行 | `store.colors(forProduct:)` = **本商品自己的规格色** | 0 或 1 ❌ |
同款不同色是**独立商品** → 本商品只有自己那一色；纯名称命名（没建规格行）时 `variants` 为空
→ `colors == []` → **整行消失**。「段段长Jsk」正常纯属「碰巧」：它的两色恰好在自己的规格里。

## 修法（收敛为唯一来源）
- `Services/ShopCatalog/ShopCatalogDesignPalette.swift`（NEW，纯逻辑）：
  `sameDesignProducts(of:among:)`（同系列+同品类+同款式名+未归档，排除自己）、
  `colors(of:among:explicitColors:)`（去重保序、本商品在前）。
  单个商品贡献颜色**两种形态都要覆盖**：多规格色（旧形态）全部列出；
  规格色为空则退回**商品名里的颜色词**（新形态）；**不**用整名兜底。
- `ShopCatalogStore.designColors(forProduct:)` —— 详情页「配色」行唯一数据源。
- `ShopCatalogProductDetailView`：`sameDesignSiblings` 改走纯逻辑模块（**删掉视图里那份重复过滤**）；
  `colors` 改读 `designColors`。
  → 标题「· N 色」/ 配色行 / 轮播兄弟色 三者共用同一份同款商品集合。

## 刻意没动
- 加购弹窗的「配色」区块（`chipGrid`）**仍读 `colors(forProduct:)`** —— 那是「挑本商品买哪个色号」
  的规格选择器，与「这款有哪几色」语义不同，合并会把别的商品色号塞进购买记录。
- 点菜页本来就对：颜色 chips 取自合并卡内的同款商品组（`group.products`）。

## 测试
`ItemManagerTests/ShopCatalogDesignPaletteTests.swift`（NEW）：纯逻辑 9 + 仓库层 3
（后者用**真实发布链路**产出三个同款颜色商品，断言每个商品的配色行都是整款 3 色）。
连同 5 个相邻套件一起重跑：**98 项 0 失败**。
核心不变量：**标题写「· N 色」，配色行就必须有 N 个颜色**。

## 发现的真缺口：尾款是**现算**的，没读后台录入值

需求 §II 原文「尾款金额自动读取后台录入的**『尾款』**数据」，首版却是
`balanceAmount = event.price - depositAmount`。而 `CatalogSaleEvent` 本来就带独立的
`balance` 字段（价格表四列：定金 / 尾款 / 预约价 / 现货价），`CatalogPriceArchive.currentBalance`
也早已暴露 —— 等于把录入的尾款丢了。

- 种子数据自洽（428 = 128 + 300）→ 数值相同，**看不出问题**，所以首轮 21 个用例全绿也发现不了。
- 模型注释明确「不做强约束」，价格表由人工/OCR 录入 → 预约价 ≠ 定金 + 尾款 完全可能。
  此时待补尾款与后台录入值差一截，直接违反「心愿尾款里出现**金额完全正确**的待办任务」。

### 修法

1. 新增 `ShopCatalogWardrobeAmount`（`ShopCatalogWardrobeEntryPolicy.swift`，nonisolated）：
   `pendingBalance(backendBalance:reservationPrice:depositPaid:)` = 后台尾款 → 缺失回退推导 → 负数归零；
   `isBackendPriceInconsistent(deposit:balance:reservationPrice:)`（缺字段不判定）。
2. **两处消费点共用它**：`makeDraft`（落库）与 `ShopCatalogReservationSheet.pendingBalance`（弹窗预览）。
