## 根因链（全部实测钉死，非推断）

1. **Mac 与 CloudKit 之间此前没有任何通路**。受控发布器（`OpsPublisherBridge` +
   `ops_publish_bridge.py`）早已写好，但**没有任何界面调它**；导出待发布包的入口随
   2026-09-27 的分区清理一起消失（服务层还在）。App 容器内无导出包 / 请求文件 / 回执 /
   凭证文件，shell 历史无 `publish_cloudkit` → 从未被调用过。
2. **Mac 也没有「读取线上基线 / 拉回目录」界面**，两条只读模式只存在于 CLI。
3. **线上发布头停在 seq 1 从未变动**：`publishedAt=2026-09-25T06:34:27Z`（=北京 14:34），
   `rootIndexHash=e0551223…`，`changeTag=mugn90pg`。iOS 与 Mac 写的是**同一协议同一容器**
   （`ShopCatalogOpsPublicCloudWriter` → `iCloud.bugod2.ItemManager` 公共库，
   无 `icloud-container-environment` 覆盖 = Development）→ **iOS 那次「已发布并验证成功」
   并没有切换发布头**。iOS 的回读验证是真的（`verifyEndToEnd` 会比对 `releaseSeq`），
   所以要么那次实际失败了、要么 iOS 端跑的不是 Development。
4. **线上 seq1 的 276 个 asset 全是 `local:`、`thmedia:` 为 0** → 09-25 那次发布没带图，
   任何客户端拉到都是占位图。
5. **Mac 草稿 `5EF72441-…` 引用 450 个不同的 `local:img-XXXXXXXX.jpg`，磁盘上一张都没有**
   （仓库 / 模拟器容器 / 下载 / 桌面 / 文档全搜过，0 命中；staging 里 38 个目录只有 7 个文件，
   该草稿目录只剩 1 个）→ `makePublicationArchive` 必然缺图硬报错，**今天发不出去**。
   ⚠️ 注意：这些名字与线上包里的引用**同名**，说明是同一批种子图，本机器从没有过文件。
6. **Production 401**：prod keyID `cb94be54…` 与 dev 是同一对公私钥，但 401 = 该 keyID
   未在 Console Production 注册成功。只能用户人工处理。
7. **Mac 端没有任何「导入整包」入口**：服务层 `OpsWorkspace.importCatalog(from:)` 还在，
   但 09-27 清理后无视图调用。而设计里 iOS→Mac 的通道就是
   「iOS 导出整包（含图片）tar（`shop-catalog.json` + `images/<原文件名>`）→ Mac 解开 → 发布」，
   注释原本就写在 iOS 侧导出函数上。**接收端被删 = 这条链路断死**。

| series.cover | 9 | 9 |
| series.priceChart.sourceImage(s) | 16 | 16 |

### ⭐ 新根因 B（推断，需用户在 Console 处理）：Development 的 Security Role 没开写权限

iOS 发布暂存走的是**完整清单**（`ShopCatalogOpsMediaStaging.plan` →
`ShopCatalogMediaReferences.publisherRewritten`），所以发布失败**不是**漏图。
`ShopCatalogOpsUploadError.mapped` 把 `permissionFailure` / `serverRejectedRequest`
映射成 `.blocked("CloudKit 权限拒绝（Security Role 未授权当前账号）")`。
CloudKit 的 **Security Role 是按环境配置的** → Production 开了、Development 没开，
正好解释「TestFlight 正常、Xcode 直编不行」。
`unavailableReason` 只是本地存储故障，不是白名单闸门，已排除。

### ⭐ 新根因 C（已修）：iOS 媒体阶段「每张图都全量回读」→ 撞限流 → 发布头永远切不动

用户贴的启动日志给出铁证：

```
📢 当前运行环境: Development (调试版)
[ShopCatalogSync] 发布头 seq=1 schema=1 （本地已装 seq=1，内存有远端层=true）
[ShopCatalogSync] 序号未变且本地已有内容，零下载
```

→ iOS 读的确实就是 Development，且它自己也看到头还是 seq 1（发布没落地）。

旧 `ShopCatalogOpsPublisher.uploadOne` 对**每一张图**都做：
① `fetchMediaMetadata`（单点查询）→ ② 不存在才 `saveMedia` → ③ **无条件**
`fetchMediaBytes` 把整张图下载回来算 hash。450 张图 = 450 次查询 + 450 次全量下载，
再加上末尾 `verifyEndToEnd` 又把 assets 的图**再下载一遍**（276 次）。
撞 CloudKit `requestRateLimited` → 一部分任务落 `retryable/failed`
→ `unresolved` 非空 → 直接 `return .notPublished("N 张图片未通过校验（发布头未切换）")`。
**这就是「iOS 点了发布、头却一直是 1」的机制。**

修法（iOS 侧「重复上传拦截」，三点）：
1. **批量问存在性**：新增 `ShopCatalogOpsCloudWriting.fetchMediaMetadata(mediaKeys:)`，
   默认实现逐张（只为不打断既有测试替身），真实实现走 `database.records(for:)` 分块 200。
   450 次查询 → 3 次。批量失败不阻断，退回逐张。
2. **线上已有 = 不传字节 + 不回读字节**：`THMedia` 是内容寻址的**不可变**记录，
   摘要与字节数对得上即同一份内容。只有**本次真上传**的才拉字节校验（§3.2 第 6 步保留）。
3. **末尾端到端验证不再二次下载**：`verifiedThisRun: Set<String>` 记本轮已验过的
   mediaKey，`verifyEndToEnd` 命中就跳过。

另加**拦截可见**：`ShopCatalogOpsMediaStats`（新传 / 跳过 / 未通过）打到
`publisher.lastMediaStats`，上传 Section 显示一行，只说「图片 N 张」看不出重没重传。

### ⭐ 追加（用户需求）：上传任务三页签 + 启动时脏数据修复

截图证据：上传任务 429 条混在一个列表里，其中连**媒体任务**都挂着「发布头冲突」
（`changeTag` 冲突只对发布头任务有意义）—— 典型脏数据。

- **三页签**（`ShopCatalogOpsUploadSection`）：**当前** = 今天的非失败任务；
  **失败** = `isTerminalFailure || retryable`（**不分日期**，失败被时间藏起来只会被遗忘）；
  **历史** = 其余（非今天 + 更早的成功任务）。计数显示在分段 Picker 上。
- **启动修复**（`ShopCatalogOpsUploadStore.repairStaleTasks()`，`init` 里 `reload()` 之后调）：
  `.uploading`（上次会话中断，进度无意义）与 `.conflict`（启动时没有运行在跑，
  conflict 全是脏数据）→ 复位 `.staged`、清 lastError/nextRetryAt、**不清 attemptCount**。
  ⚠️ 只许在启动路径调用；运行中途调用会把正在跑的任务打回待办。
  复位后下次发布由批量存在性查询判成「线上已有」→ 直接跳过（正好接上重复上传拦截）。

### ⭐ 追加 2：那 31 条「发布头冲突」的真身 —— `save` 不是 upsert

用户截图（新页签已生效）：当前 398 / 失败 31 / 历史 0，失败页全是**媒体任务**挂着
「发布头冲突：发布头已被其它发布覆盖（changeTag 冲突），上传图片 xxx 未生效」。

线上复查：**发布头仍是 seq 1**（rootIndexHash 不变）→ 之前那次**发布没成功**，
「媒体已校验」只代表图片字节上去了。

根因：**CloudKit `save` 不是 upsert**。目标记录名已存在、而手里的 CKRecord 是新建的
（没有 change tag）→ `serverRecordChanged`。上一场会话被杀时字节已到服务端、
本地没来得及记 `mediaVerified`；下次发布的存在性查询再漏判，`saveMedia` 就撞上它，
被 `mapped` 翻译成「发布头已被其它发布覆盖」—— 那是发布头才有的语义，误导。

修法：`saveMedia` / `savePack` 捕获 `serverRecordChanged` **按「已存在」放行**
（内容寻址 + 不可变 ⇒ 幂等），交给调用方的回读校验确认内容一致；真不是同一份内容
回读会如实失败。`mapped` 的冲突文案改成中性的「记录已被其它端覆盖」。
配合启动修复：下次启动 `.conflict` 先复位 `.staged`，再发布时批量查询判「已有」→ 跳过。

给 `THMedia` / `THDataPack` / `THRelease` 的 **Authenticated** 勾 **Create**（默认已有）+ **Write**（默认没有）。

（`THMedia`/`THDataPack` 是内容寻址的**新建**记录，Create 就够，所以图反而传得上。）

**但这只是「让 iOS 自己也能发」**：既定发布通道是 Mac 走 s2s key，s2s 是 admin 权限，
**不受 Security Role 限制** → 不改权限也能把 seq 2 发出去。改权限是可选加固，不是阻塞项。

Production 另需：① Console 里把 Development Schema **Deploy to Production**；
② Production 的 s2s key 要单独注册（当前 `keyID.production` 未注册 → 401）。

## 追加 5：Mac 端「dev + TestFlight(production) 都能拉/更新云端」（已落地）

### ⭐ 凭证改为**按环境分文件**（核心）

改前：容器内只有一份 `cloudkit.json`，一个环境变量只能给子进程传一个凭证 →

- `requiresCredentialFile()`：`localFixture` 不联网 → 不需要凭证

- 新增 `OpsCredentialSummary`（只含 containerID / keyID / 声明环境，**私钥永不进这里**）

`onlineHead` / `pulled` / `outcome` / `lastReceiptSeq` / `baselineAcknowledged`
都只在读到它们的那个环境里成立。切环境不清 = 拿 Development 的 `seq+1` 去写 Production，
**而且没有任何一层会报错**（号合法、基线核对也是同环境 hash 在比）。
→ `targetEnvironment.didSet` → `resetEnvironmentScopedState(from:)`；
`publish()` 再加一道 `head.environment == targetEnvironment.rawValue` 校验。

`publish_adapters._from_payload` 原用 `payload.get("environment", environment)` →

**环境段换成 development**，打到 Development 库却以为在发 Production。**比 401 危险：不报错。**

### ⭐ Production 401 的实测根因（已钉死，不是「没注册」）

但 `privateKey` 与 `privateKey.production` 的公钥**完全相同**（同一对密钥注册两次，合法）。
`containerID.production` 正确。**实测两条通道（Keychain / 文件凭证）都 401
`AUTHENTICATION_FAILED`** → 判定：**cb94be54… 这把 Production key 本身没有访问权**
（Console 的 Production 环境里要么没这把、要么注册时用了别的公钥）。
处置：Console → 环境 Production → API Access → Server-to-Server Keys →
