## 品牌上新资讯功能：双轨分发方案确定

承接 2026-09-13 的方案调研（`docs/品牌上新资讯功能方案.md`）。

### 用户思路与澄清

用户提出两条路：(A) Mac 上写脚本爬 → 转静态数据放进 App；(B) 用户/运营上传 → CloudKit 公共库 → 分发给普通用户。

澄清点：采集本来就不在 iOS 端做，Mac/服务端脚本采集是方案既有设计，iOS 端从不爬取。两条路不是二选一，必须合流为双轨。

### 实测数据（关键约束）

`ItemManager/Resources/TimeHall/`：
- 目录大小 **318 MB**，图片 **5328 张**，`catalog.json` 4.4 MB
- 内容实体：events 721 · commerceItems 308 · coordinates 150 · items 74 · stories 36 · archiveCatalogues 47

**结论：Bundle 已到极限，新增内容一律走 CloudKit，不再塞 Bundle。** 后续应反向迁移历史内容到 CloudKit，Bundle 只留精选与首屏。

### 双轨架构

```
Mac 定时跑 import_*.py → 增量 diff
   ├─→ CloudKit 公共库（sourceKind=editorial，全用户实时）
   └─→ Bundle catalog.json（只留最近 N 条精选，离线兜底）
                ↓
   客户端合并：云端优先，本地兜底
```

四个硬约束：
1. CloudKit Public DB 需登录 iCloud 才能读 → Bundle 兜底是必需项，不是可选
2. CloudKit 是同步服务不是推送系统：小时/日级够用，分钟级需真后端 + APNs
3. 开放用户上传触发 Apple 1.2 UGC 条款（举报/审核/封禁/联系入口四件套）→ 第一期只做 editorial
4. 图走 CKAsset 占存储配额 → 沿用官方 HTTPS 外链，只物化封面

运营在 App 内上传属 editorial 不触发 UGC，沿用 `NoticeCloudKitService` 的 `adminIDs` 白名单。

### 用户决策（已定稿，2026-09-14）

1. **时效性：日级** — 不追求分钟级，CloudKit 同步能力足够，不需要真后端 + APNs
2. **第一期只做 editorial（运营上传），不开放用户上传** — 规避 Apple 1.2 UGC 四件套风险
3. **品牌范围：先做日牌**（复用现有 `import_*.py` 管道）；**国牌由运营人工从淘宝采集**，在 App 内 admin 入口上传

这三条砍掉了本期最大的工作量：RSSHub 自建、淘宝客 API 接入、LLM 抽取管道、UGC 审核与举报体系全部不需要。

### 由此确定的实施路径

- 第一步：给 `import_news_batch.py`(250行) / `import_commerce_batch.py`(393行) 加增量 diff，输出 `pending_updates.json` + `published_ids.json`
- 第二步：App 内 admin 上传入口，复用 `NoticeCloudKitService` 的 `adminIDs` 白名单，支持导入 JSON + 手动录国牌商品
- 第三步：客户端读 CloudKit published + Bundle 兜底，未登录 iCloud 降级纯 Bundle 不白屏
- 第四步（可选）：`deadlineAt` → 日历提醒；上新 ↔ 衣橱匹配

保留「运营一键导入」而非脚本直推 CloudKit 的三个理由：① 脚本推需 cktool / server-to-server key，复杂度高 ② 保留人工审核合规闸口 ③ 日级下每天点一次够用。

## ⚠️ 更正：项目已有自研图片体系（我上一轮判断错了）

我只查 SPM 依赖（只有 `generative-ai-swift`）就断言"没有图片库"——**错的**。实际有完整自研实现：

| 组件 | 能力 |
|:--|:--|
| `ItemManager/ImageManager.swift` | 内存缓存按机型自适应 40-300MB（:111-142）+ 磁盘缓存目录 + 单图上限保护（:163） |
| `Components/AsyncDownsampledImage.swift` | fileName + targetSize 降采样，先查内存缓存再异步加载（已读源码确认） |
| `Services/OptimizedImageLoader.swift` | actor + NSCache |
| `Services/TimeHall/TimeHallCatalogStore.swift:59` | 时光馆独立缓存 96 张 / 80MB |

**结论：不引入 Kingfisher，扩展 ImageManager。**

### 真正的能力边界

体系基于**本地文件名**（`cachedImage(fileName:targetSize:)`）。
唯一远程路径 `downloadFileIfNeeded()`（:290）用的是
`FileManager.startDownloadingUbiquitousItem` = **iCloud Documents** = **每用户私有空间**。

iCloud Documents ≠ CloudKit Public DB。前者适合同步用户自己的衣橱照片，
**不能让所有用户看同一张品牌上新图**。品牌图必须走 CloudKit Public DB + CKAsset。

方案：新增 `RemoteAssetStore` 做「云端资源 → 落地本地缓存目录 → 交 ImageManager」，
缓存/降采样/淘汰全部复用现有代码。

**现有代码唯一实质缺口：磁盘缓存没有总大小上限 + LRU**（P1 必须补）。

### CloudKit 上云的关键坑（已写入方案第 3 节）

**CKAsset 没有可预测的公开 URL**：不能在 catalog 里存 https 地址直接丢给图片库；
必须查 CKRecord → 取 CKAsset → 本地文件。Web Services 的 downloadURL 是带签名临时地址会过期。
→ 缓存 key 必须用图片稳定 id（assetID + variant），绝不能用 URL。

上传：存量 5328 张只能走 `cktool`（Xcode 自带 CLI，需 Management Token）批量导入；
增量走 App 内 admin 的 `CKAsset(fileURL:)`。
配额：计入容器配额，随活跃用户增长，Console 可查；只传 thumb + medium 不传 full。

### 关键设计决策与踩坑

1. **Apple Compression 的 `COMPRESSION_ZLIB` 是裸 DEFLATE（RFC 1951）**，不是 zlib 包裹流。
   gzip 包体去掉 10 字节头 + 8 字节尾即可解。已实现 gzip 解码 + CRC-32 双向自校验防压缩炸弹。
2. **分片拆包后跨包引用会被误判为悬空**：包内校验只在「目标类型也出现在本包」时要求引用闭合；
   跨包依赖由根清单 `dependencyPackRecordNames` 声明 + `validate_release_references` 全局校验。
3. **撤回优先 + partial 不被反填**：`composeLocalFragment` 用 `supersededEntityTypes` 防止
   partial 包被 Bundle 旧条目拼回已删除内容。
4. **`TimeHallRuntimeConfiguration.cloudSyncEnabled` 默认关闭**：生产库还没有 THRelease 时
   避免每次启动浪费 CloudKit 配额；等运营发布首个版本后再在设置页打开。
5. **Swift 默认 MainActor 隔离**（`SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`）下，
   给新类型整体标 `nonisolated` 消除跨 actor 警告；Swift 5 模式下 `nonisolated enum/struct` 合法。

## 仲夏夜系列：商品归集 + 价格根因修复 + 运营白名单三态闸门

### 1. 商品归集（同一淘宝链接 = 一个商品）

**症状**：樱花小羊在种子 JSON 里是 5 个独立单品、5 条各自为政的条目，
但淘宝上它们是同一个链接（`item.htm?id=1032370386538`）下的不同款式。
拆开展示会让「已收藏 / 已入库」判断失真，也让价格区间无处安放。

**做法**：不新增架构，只给规格组加一个 `role`。
- `MidsummerSpecRole` 新增 `.variant`（款式/版型/款型 → `.variant`），
  与既有的 `color` / `size` 并列，`resolvedRole` 加中文关键词推断。
- 5 条单品合并为 1 条 `kind: set` 的商品，三组规格 `款式 × 颜色分类 × 尺码`，
  54 条 SKU 各带**逐款参考价**。
- 入库名从「樱花小羊」变成「樱花小羊 段段JSK」——
  `MidsummerSpecResolver.displayName(_:selection:)` 把款式拼进去，
  `MidsummerWardrobeInsertion.makeDraft` 的备注同时写「款式：…」。
- 卡片与详情页显示「含 N 个款式」（`variantCount`）。

**代码增量极小**（这是判断「归集该不该改架构」的分水岭）：
`MidsummerSpecRole.variant` + `displayName` / `selectedVariantName` + 视图层、
款式数展示 + `wardrobeMapping` 认 `.variant` / `.other`。**架构一行没动。**

结果：13 系列 / **30 商品**（原 34）；樱花小羊 5 → 1。

### 2. 价格根因修复（不是补数据，是改模型）

**之前为什么会错**：价格是三个互不相干的裸字段——系列级 `priceMin` / `priceMax`、
单品级 `price`、有的地方写定金有的写全款。
于是「同一个数字有时是定金有时是全款」，区间靠手填、填完还会和单品打架。

**改法四条，逐条对应一种历史错误**：
1. **区间派生，不再存储**：删掉系列级 `priceMin` / `priceMax`，
   `MidsummerSeriesDTO.priceRange` 从单品（含 SKU 逐款价）算出来。
   改一处单品价，整条链跟着变——不再有「系列区间和单品对不上」。
2. **口径必填**：新增 `MidsummerPriceKind`（`.shop` 商品页价 / `.reference` 参考价）
   + `priceCapturedOn`（yyyy-MM-dd）+ `priceNote`。
   有价无口径的条目，构建期就被 `MidsummerPriceIntegrityTests` 拦下。
3. **定金与全款分列**：定金是独立维度（无法归到某个单品），
   单独放 `depositMin` / `depositMax` / `priceSource`。
   界面定金优先 → 派生区间 → 尾款 → 「待补充」，四级 fallback。
4. **缺价必说明**：没价的单品必须写 `priceNote` 说清为什么没价
   （如「该款图鉴未标参考价」），不允许静默空缺。

**真实价格**：Lo 研社图鉴（lolitalibrary.com）31022–31030，上传者狐芙，
逐款参考价 **¥199–699**：印花SK 329 / 印花JSK 399 / 段段JSK 699 / 无腰OP 499 /
内搭 199 / 开衫 209 / 围裙 219 / 罩裙 269 / 小物无价。
定金带 ¥7–139 出自三坑新语 2026-06 淘宝榜。

⚠️ **诚实记录**：淘宝短链 `e.tb.cn/h.8JmuwHMKIB4LK8H` 解出的
`item.htm?id=1032370386538&price=119` 里的 **119 是分享者所选规格的定金口径挂出价**，
和逐款全款不同源，**没有**拿它当全款填。mtop 接口未登录返回 `RGV587_ERROR`，
拿不到登录态 SKU 价。这个 119 写进了 `priceNote` 说明不同源，而不是悄悄用。

**测试当守卫**（`MidsummerPriceIntegrityTests`，5 条）：
有价必带口径+采集日 / 采集日 ISO 格式 / 缺价必说明 / 定金全款分列 /
同数不写两遍 / 归集商品 SKU 价与派生区间（¥199–699）/ 改一处价格整链跟着变 /
`hasPrice` 对 SKU 价生效。

### 3. 运营白名单：从布尔改成三态

**使用者的原话要求**：「如果说他不在白名单里面，这个运营上传界面应该是不对它显示的。
不对普通用户显示。」——即**本机开关也不该撬开**。

原来的 `isAdmin()` 返回 `Bool`，把「不是运营」和「取不到身份」压成同一个 `false`，
于是模拟器上永远没有上传入口（内容维护者没法干活），
而给「创作者模式」开关又会连带把真·非白名单账号也放进来。

改为 `NoticeCloudKitService.CreatorGate` 三态：
- `allowed` → 显示
- `denied` → **硬不显示**，本机「创作者模式」开关撬不开
- `unresolved`（模拟器 / 未登录 / 断网）→ 只有这一态允许开关解界面闸门

`MidsummerStore.canContribute` 就是这三态的 switch；`isAdminUser = (creatorGate == .allowed)`。
页脚 `MidsummerDataNote` 的 `denied` 分支如实写「本机 iCloud 账户不在运营白名单里，
因此不显示上传入口」——**不给「开启创作者模式」按钮**，因为给了只会让人以为开关坏了。
`accessibilityIdentifier("midsummer-creator-denied-note")` 供测试断言。

⚠️ 这只是**界面闸门，不是安全边界**。真正的写入权限在 CloudKit Console 的
Security Roles（见 `docs/MIDSUMMER_TALE_CLOUDKIT_SETUP.md §2`）。

**Xcode 里搜什么**：**`CreatorGate`**（`NoticeCloudKitService.creatorGateLogTag`）。
启动 `ItemManagerApp.onAppear` 就 `Task { _ = await ...creatorGate() }`，
打印五行：本机 iCloud 用户标识 / 白名单 / 命中白名单 / 判定结果。
取不到身份打 `⚠️ [CreatorGate] 取不到 iCloud 用户标识：…`。
`getCurrentUserID()` 的日志也带同一 tag，并直接提示「想把它加进白名单，复制上面的值」。

用 `name=iPhone 16 Pro` 跑 `xcodebuild test` 会**不报编译错、直接 destination 解析失败**：

```
xcodebuild: error: Unable to find a device matching the provided destination specifier:
  { platform:macOS, arch:arm64e, ..., name:My Mac, error:My Mac's macOS platform doesn't match ... }
EXIT=70
```

注意它会**静默退化成 `My Mac`**，看起来像环境问题，其实是设备名不存在。
**跑测试前先 `xcrun simctl list devices available` 确认名字**；本次用的是
`-destination 'platform=iOS Simulator,name=iPhone 18 Pro,OS=27.0'`。

AGENTS.md 里的 `iPhone 16 Pro` 那段构建/安装命令需要同步更新（未擅自改，等确认）。
