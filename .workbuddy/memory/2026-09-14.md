## 品牌上新资讯功能：双轨分发方案确定

承接 2026-09-13 的方案调研（`docs/品牌上新资讯功能方案.md`）。

### 用户思路与澄清

用户提出两条路：(A) Mac 上写脚本爬 → 转静态数据放进 App；(B) 用户/运营上传 → CloudKit 公共库 → 分发给普通用户。

澄清点：采集本来就不在 iOS 端做，Mac/服务端脚本采集是方案既有设计，iOS 端从不爬取。两条路不是二选一，必须合流为双轨。

### 实测数据（关键约束）

`ItemManager/Resources/TimeHall/`：
- 目录大小 **318 MB**，图片 **5328 张**，`catalog.json` 4.4 MB
- 内容实体：events 721 · commerceItems 308 · coordinates 150 · items 74 · stories 36 · archiveCatalogues 47

**结论：Bundle 已到极限，新增内容一律走 CloudKit，不再塞 Bundle。** 后续应反向迁移历史内容到 CloudKit，Bundle 只留精选与首屏。

### 双轨架构

```
Mac 定时跑 import_*.py → 增量 diff
   ├─→ CloudKit 公共库（sourceKind=editorial，全用户实时）
   └─→ Bundle catalog.json（只留最近 N 条精选，离线兜底）
                ↓
   客户端合并：云端优先，本地兜底
```

四个硬约束：
1. CloudKit Public DB 需登录 iCloud 才能读 → Bundle 兜底是必需项，不是可选
2. CloudKit 是同步服务不是推送系统：小时/日级够用，分钟级需真后端 + APNs
3. 开放用户上传触发 Apple 1.2 UGC 条款（举报/审核/封禁/联系入口四件套）→ 第一期只做 editorial
4. 图走 CKAsset 占存储配额 → 沿用官方 HTTPS 外链，只物化封面

运营在 App 内上传属 editorial 不触发 UGC，沿用 `NoticeCloudKitService` 的 `adminIDs` 白名单。

### 用户决策（已定稿，2026-09-14）

1. **时效性：日级** — 不追求分钟级，CloudKit 同步能力足够，不需要真后端 + APNs
2. **第一期只做 editorial（运营上传），不开放用户上传** — 规避 Apple 1.2 UGC 四件套风险
3. **品牌范围：先做日牌**（复用现有 `import_*.py` 管道）；**国牌由运营人工从淘宝采集**，在 App 内 admin 入口上传

这三条砍掉了本期最大的工作量：RSSHub 自建、淘宝客 API 接入、LLM 抽取管道、UGC 审核与举报体系全部不需要。

### 由此确定的实施路径

- 第一步：给 `import_news_batch.py`(250行) / `import_commerce_batch.py`(393行) 加增量 diff，输出 `pending_updates.json` + `published_ids.json`
- 第二步：App 内 admin 上传入口，复用 `NoticeCloudKitService` 的 `adminIDs` 白名单，支持导入 JSON + 手动录国牌商品
- 第三步：客户端读 CloudKit published + Bundle 兜底，未登录 iCloud 降级纯 Bundle 不白屏
- 第四步（可选）：`deadlineAt` → 日历提醒；上新 ↔ 衣橱匹配

保留「运营一键导入」而非脚本直推 CloudKit 的三个理由：① 脚本推需 cktool / server-to-server key，复杂度高 ② 保留人工审核合规闸口 ③ 日级下每天点一次够用。

### 新增 `docs/图片与性能扩展方案.md`（Part A 非技术 + Part B 技术规格）

## ⚠️ 更正：项目已有自研图片体系（我上一轮判断错了）

我只查 SPM 依赖（只有 `generative-ai-swift`）就断言"没有图片库"——**错的**。实际有完整自研实现：

| 组件 | 能力 |
|:--|:--|
| `ItemManager/ImageManager.swift` | 内存缓存按机型自适应 40-300MB（:111-142）+ 磁盘缓存目录 + 单图上限保护（:163） |
| `Components/AsyncDownsampledImage.swift` | fileName + targetSize 降采样，先查内存缓存再异步加载（已读源码确认） |
| `Services/OptimizedImageLoader.swift` | actor + NSCache |
| `Services/TimeHall/TimeHallCatalogStore.swift:59` | 时光馆独立缓存 96 张 / 80MB |

**结论：不引入 Kingfisher，扩展 ImageManager。**

### 真正的能力边界

体系基于**本地文件名**（`cachedImage(fileName:targetSize:)`）。
唯一远程路径 `downloadFileIfNeeded()`（:290）用的是
`FileManager.startDownloadingUbiquitousItem` = **iCloud Documents** = **每用户私有空间**。

iCloud Documents ≠ CloudKit Public DB。前者适合同步用户自己的衣橱照片，
**不能让所有用户看同一张品牌上新图**。品牌图必须走 CloudKit Public DB + CKAsset。

方案：新增 `RemoteAssetStore` 做「云端资源 → 落地本地缓存目录 → 交 ImageManager」，
缓存/降采样/淘汰全部复用现有代码。

**现有代码唯一实质缺口：磁盘缓存没有总大小上限 + LRU**（P1 必须补）。

### CloudKit 上云的关键坑（已写入方案第 3 节）

**CKAsset 没有可预测的公开 URL**：不能在 catalog 里存 https 地址直接丢给图片库；
必须查 CKRecord → 取 CKAsset → 本地文件。Web Services 的 downloadURL 是带签名临时地址会过期。
→ 缓存 key 必须用图片稳定 id（assetID + variant），绝不能用 URL。

上传：存量 5328 张只能走 `cktool`（Xcode 自带 CLI，需 Management Token）批量导入；
增量走 App 内 admin 的 `CKAsset(fileURL:)`。
配额：计入容器配额，随活跃用户增长，Console 可查；只传 thumb + medium 不传 full。

### 关键设计决策与踩坑

1. **Apple Compression 的 `COMPRESSION_ZLIB` 是裸 DEFLATE（RFC 1951）**，不是 zlib 包裹流。
   gzip 包体去掉 10 字节头 + 8 字节尾即可解。已实现 gzip 解码 + CRC-32 双向自校验防压缩炸弹。
2. **分片拆包后跨包引用会被误判为悬空**：包内校验只在「目标类型也出现在本包」时要求引用闭合；
   跨包依赖由根清单 `dependencyPackRecordNames` 声明 + `validate_release_references` 全局校验。
3. **撤回优先 + partial 不被反填**：`composeLocalFragment` 用 `supersededEntityTypes` 防止
   partial 包被 Bundle 旧条目拼回已删除内容。
4. **`TimeHallRuntimeConfiguration.cloudSyncEnabled` 默认关闭**：生产库还没有 THRelease 时
   避免每次启动浪费 CloudKit 配额；等运营发布首个版本后再在设置页打开。
5. **Swift 默认 MainActor 隔离**（`SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`）下，
   给新类型整体标 `nonisolated` 消除跨 actor 警告；Swift 5 模式下 `nonisolated enum/struct` 合法。

### 构建环境注意事项（重要，踩了三次）

- 本机 Xcode 27.0（27A266a），模拟器为 iPhone 18 Pro（**没有** iPhone 16 Pro，AGENTS.md 里的示例已过期）。
- 在受限沙箱里跑 `xcodebuild` 会连撞**三个**沙箱坑，都不是代码问题：
  1. SwiftPM manifest：`sandbox-exec: sandbox_apply: Operation not permitted` →
     加 `-IDEPackageSupportDisableManifestSandbox=YES`
  2. 宏插件服务：`swift-plugin-server produced malformed response`，报错集中在所有
     SwiftData `@Model` 文件（`Brand.swift`/`Clothing.swift`/`Tag.swift`），极易误判成代码错误 →
     加 `OTHER_SWIFT_FLAGS='$(inherited) -Xfrontend -disable-sandbox'`
  3. 用户脚本阶段：`PhaseScriptExecution Remove Duplicate Resources failed`，日志里**没有** `error:` →
     加 `ENABLE_USER_SCRIPT_SANDBOXING=NO`

  把真正的错误挤出 `head` 预算。用 `grep -nE "^/Users/.*: error:"`。
