### 本轮实测踩到的四个坑（都已修 + 已写进 SKILL.md）

1. ⭐ **`Text(字面量)` 解析 Markdown，`Text(变量)` 不解析**（`LocalizedStringKey` vs `String` 初始化器）。
   结果 `**重点**` 从变量来时会**逐字显示**。→ 新增 `opsMarkdown(_:)`，所有变量文案必须过它。
   （快照实测抓到：`**不直连公共库**` 原样带星号。）
2. ⭐ **基线快照是「编码后」产物**（`.iso8601`，秒精度），而内存 `catalog` 里的 `Date` 带小数秒
   → 直接 `Equatable` 比会让**每个带日期的实体**都判成「已修改」；而**严格策略的作用域是从差分推出来的**
   → 作用域被**静默放大**（实测显示 6，实际只改了 2）。
   → `recordConfirmedPublish` 里先 `normalizeWorkingCopyToStoragePrecision()`（过一遍编解码）。
3. ⭐ **沙箱 GUI App 拿不到 stdout** → harness 的日志必须落到产物目录。
   - `open -n --stdout <path>` 实测**不生成**文件（静默失效）；
   - 直接 exec 二进制 → **退出码 133 = SIGTRAP**，日志 0 行。
   后果极隐蔽：造数据失败只打 stdout → 快照退化成**空态** → 空态看起来「布局就是这样」，验收直接放过。
   （实测：系列价格表因**列数/值数不齐**被录入端 `rows.allSatisfy { … }` 挡下，
   快照上只表现为「价格表：无」，截图里完全看不出是一次失败。）
   → 新增 `seedStep(_:_:)`（每步出声）+ `log()` / `writeLog()`，收尾 `defer` 落 `harness.log`。
4. ⭐ **`markCancelled()` 定义了却无人调用** → `OpsBridgeError.cancelled` 是**走不到的分支**，
   运营点「取消当前运行」在台账上不会被标成「已取消」。
   同时 `OpsBridgeRunResult.timedOut/cancelled` **恒为 false**（`run` 在构造结果前就 throw 了）
   —— 「返回了结果就说明没超时」是假命题。→ 删掉这两个字段；`cancel()` 改为
   **先标记 collector 再发 SIGTERM**（顺序反了会有「进程已退、标记未写」的窗口）；
   超时路径改用不标记的私有 `terminateRunningProcess()`；`.cancelled` 文案补上 R09 提示
   （取消 ≠ 没发生，切头后必须查结果）。

### 结构决定（写进代码注释了）

- **`private(set)` 按文件生效**：类型自己的扩展写在别的文件里也读不到 setter（实测 **184 处**编译错）
  → `catalog` / `statusMessage` / `lastError` 落地成**裸 `var`**（`internal(set)` 是冗余写法，编译器会警告）。
  契约改为「内容变更一律走编辑方法 + `canMutate()` 门禁，视图层只读」，靠评审维持。
- **`OpsFormFrame` 自己执行「成功才 `dismiss()`」**，不让 9 个表单各写一遍 `if ok { dismiss() }`。

## 续 4 · 「让 Mac 那套 Python CLI 能传到 CloudKit」（用户拍板 + 根因修复 + 实测）

**用户拍板**：上节 §仍未闭环 的第 1 条 —— **采纳 Mac 路径**（Mac 导出待发布包 → Python CLI 打
CloudKit），不需要 Mac 直连 CloudKit。原话：「只需要让那个 Mac 的那一套 Python CLI 能够传到
CloudKit 的话就可以，如果办不到的话，再我们再想别的办法。」

于是任务变成「把这条通道打通」，而**打通过程中挖出一个会让 App 谎报的真 bug**。

### ⭐ 核心发现（P0）：`apply=False` 被当成了「不许联网」，于是读被一起挡掉

`CloudKitWebServicesAdapter` 把 dry-run 判定写在**传输层**
（`_post` 开头 `if not self.apply: return {}`）。但 CloudKit 连 `records/lookup`（读）
也用 POST 动词，于是**读被一起挡掉**。而桥接器的 `--mode baseline`（R07 只读基线核对）
**恒传 `apply=False`**，后果：

    线上明明有 releaseSeq=1
    桥接却稳定返回 None → App 被告知「线上尚无商店发布头（本次将是首次发布）」

这就是我上一轮记的「M3 发布桥接做不了：读不到线上基线」的**真因** —— 不是「Mac 不直连
CloudKit」，是**读请求压根没发出去，而失败被伪装成了「线上没有」**。

**为什么离线演练抓不到**：`FilesystemAdapter` 的读不走 `apply` 判定（只有 `_write` 判），
所以 `drill_offline.sh`(34) 与 `drill_bridge_offline.py`(32) **全绿**。
又一次「演练绿灯 ≠ 真路径正确」，因为演练用的是另一个适配器。

**修法**：把闸门从传输层下移到**写操作**。
- `_send(path, payload)` —— 真实发出，与 `apply` 无关；**读用它**；
- `_post(...)` —— 写路径入口，`apply=False` 时静默返回 `{}`；
- `fetch_current_release()` / `_asset_exists()` 改走 `_send`；
- `_send` 里接上原本闲置的 `http_post` 注入点，让不变量**能离线锁住**。

**回归锁**：新增 `selftest_cloudkit_read.py`（**18 项，离线、不需要凭证也不需要
`cryptography`** —— 靠注入传输层 + 覆盖 `_headers` 绕开签名）。含**反向断言**：
把 `_post` 换成必然抛异常的桩，读仍须成功（防止两条路又被合并）。
其余项：dry-run 下三个写操作请求数必须为 0；`NOT_FOUND` 时返回 None **但请求数 ≥ 1**
（「问过了才知道没有」）；桥接入口 `read_head()` 同样必须真发请求。

## 续 5 · 让「App 驱动 Python CLI 打 CloudKit」这一环可验（App 内沙盒探针）

用户拍板：「只需要让那套 Python CLI 能传到 CloudKit 就可以，办不到再想别的。」
→ **CLI 侧办得到**（上一轮已实测：真实 Development 容器只读 `releaseSeq=1`）。
本轮把**「App 驱动 CLI」**这一环做成**可测量**的，并顺带抓出两个真缺陷。

### 新增：`PinkHouseOps/BridgeProbeHarness.swift`（文件触发，与快照 harness 同机制）

```bash
CONTAINER=~/Library/Containers/bugod2.ItemManager.Ops/Data/Library/Application\ Support/PinkHouseOps
printf 'probe-run1' > "$CONTAINER/bridge-probe.request"
open -n build/sym/Debug/PinkHouseOps.app     # 跑完自杀
# 产物 <容器>/…/probe-run1/{probe.log,probe.json}
```

九关：S1 设置 / **S2 未授权对照** / S3 开授权 / S4 真读脚本 / S5 列发布目录 /
**S6 子进程读仓库（⑥b）** / S7 哪个解释器带 cryptography / S8 容器内凭证 /
S9 端到端 `--mode baseline`。**只读**，从不构造 `--mode publish`；凭证只报结构（名称/字节数/顶层键名）。

三条设计不变量：① 每关**成对**（未授权 vs 授权）—— 只跑一侧，在一个根本没沙盒的构建里也会全绿；
② 判据是**真读**不是 `fileExists`；③ 只读 + 不打印私钥。

**探针自己出过一次缺陷**：S5 读不到目录列表就 `return` → S6/S7 在未授权场景根本不跑，
只剩一句「S5 失败」。已改成不提前返回。**对照组数据缺一半 = 探针白跑。**

### 探针抓到的缺陷 1：`fileExists` 在沙盒里**会骗人**（P0）

实测（未授权时，同一路径）：

| 手段 | 结果 |
|---|---|
| `FileManager.fileExists` | **true** |
| `Data(contentsOf:)` | `Operation not permitted` |
| 子进程 `ls` | `Operation not permitted` |

沙盒下 `stat` 与 `open` 走**两套判定**。于是 `OpsPublisherBridge.run` 原来的
`guard fileManager.fileExists(atPath: script.path)` 会**放行**，一路跑到 `process.run()`，
最后以「退出码 1、没有任何输出」（`OpsBridgeError.noDiagnostics`）收场 ——
把「没权限」说成「脚本坏了」。

修复：新增 `OpsBridgeSettings.isReadableFile(_:)`（**能打开 + 读这一步不抛错**）当闸门；
`diagnosis()` 也改成**自己开一次授权** + 分开报「不存在」与「在但读不到」。
⚠️ 实现细节：**不能**用 `(try? handle.read(upToCount: 1)) != nil` ——
`read(upToCount:)` 在 **EOF 返回 `nil`**，空文件会被误判成读不了（这条是被
`testEmptyFileIsReadable` 抓出来的）。

效果对比（探针 S9 的结论文案）：
- 修前：`受控发布器以退出码 1 结束，但没有输出任何可读信息。`
- 修后：`找不到受控发布脚本：…/ops_publish_bridge.py。请在发布中心里重新选择仓库目录。`

### 探针抓到的缺陷 2：解释器候选顺序在沙盒下**必然选错**（P0）

实测子进程输出：

| 候选 | 子进程结果 |
|---|---|
| `/usr/bin/python3` | `xcrun: error: cannot be used within an App Sandbox.` |
| `/opt/homebrew/bin/python3` | 本机**不存在** |
| `/usr/local/bin/python3` | 本机**不存在** |
| 仓库内 `.venv/bin/python3` | 唯一装了 `cryptography` 的那个 |

旧顺序（显式 → homebrew → usr/local → `/usr/bin`）在沙盒下 100% 选中
`/usr/bin/python3`（CLT 替身，不是真解释器）。修复：
`pythonCandidates(explicit:publicationDirectory:)` —— 显式 → **仓库内 venv** → homebrew → usr/local → `/usr/bin`。
`resolvedPythonPath` / `diagnosis` / 错误文案同步。

### 另一条环境不变量（新）

**本 target 开了 `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`** → 文件里**所有类型默认主线程隔离**。
跨线程盒子必须显式 `nonisolated`，否则「在管道读取线程调用 MainActor 方法」只报一条
很轻的告警（`call to main actor-isolated instance method in a synchronous nonisolated context`），
轻到会被当噪音放过。

   接收方**不读**。典型的「字段传了但没人用」——看起来做了，实际没做。

## 续 7 · 拍板 C = A+B：R07 过期基线与「拉回线上基线」全部落地

### B：发布前的过期基线闸门（`run_publish` 里，构造产物之前）

- `baseline_mismatches(request, head) -> [str]`：纯函数，判定表见 `RULES.md §R07`。
  要点是**「拿不到证据就不能当一致」**：线上摘要读不到 → 也算不一致
  （只比发布号会漏判「别人发了同一个号」）。空基线一律不一致。
- 不一致且 `baselineAcknowledged` 不为真 → `EXIT_CONFLICT(5)`，结论里点名「基线已过期」
  并给出两条出口；`baselineAcknowledged` 只当**已留痕的例外**，放行时打 `warning`，绝不静默。
- **dry-run 也走同一判定**（演练不该绕过过期检测）。读发布头失败 → `EXIT_REFUSED`（宁可挡住）。
- 它在链路上真正挡住的是「读完基线 → 切到别处 → 期间别人又发了一版 → 回来点发布」
  这个窗口 —— App 本地的 `submissionBlockers` 用的是几分钟前读到的快照，挡不住。

### A：`--mode pull-catalog`（只读回读线上商店目录）

- 适配器加两个**必须实现**的只读方法：`fetch_root_index_bytes()` / `fetch_pack_bytes(hash)`。
  CloudKit 侧 `_lookup_asset_value` + `_download_asset`（纯 GET，**不走 `_post`**）。
  ⚠️ 实测坑：`THRelease` 的资产字段叫 **`rootIndexAsset`**，`THDataPack`/`THMedia` 叫 **`asset`**。
  **传错不报错**，只拿到空字典 → 表现成「线上没有这个资源」。
- 四道摘要自证：根清单 SHA-256 == 发布头 `rootIndexHash`；分片**按 `entityType` 找**
  （不猜 `partitionID`）；分片 SHA-256 == `payloadHash`；**只认唯一一个**商店分片
  （多于一个 = 口径变了 → 中止，免得拉回半份）。
- 线上没有发布头 / 没有商店分片 → **`EXIT_OK`** 且如实说「线上是空的」，
  **不产出** `shop-catalog.json`。产出空目录会被读成「拉回了一份空目录」，正好是反的。
- ⚠️ 拉回的是**已下发口径**（归档条目与孤儿销售事件已被构建剔除、`local:` 已改写为
  `thmedia:<内容摘要>`）→ 必须**显式告知**，否则会被当「完整备份」用。

## 续 8 · `opsMarkdown` 漏网点清零 + 落成可执行门禁（同日，收尾）

### 起因：上一轮只修了 `opsMarkdown` 自己，没查「谁绕过了它」

续 7 把 `opsMarkdown` 的实现修对了（`AttributedString(markdown:)`），但那只保证
**走了这一层的调用点是好的**。这一轮做的是另一半：**全仓盘点有哪些变量文案根本没走这一层**。

### 盘点方法（可复用）

```bash
# ① 所有含 ** 的非注释行（先把 /// 与 // 滤掉，否则注释会淹没结果）
grep -rnE '\*\*' PinkHouseOps/{Views,Services} PinkHouseOps/SnapshotHarness.swift \
  | grep -vE ':\s*///' | grep -vE ':\s*//'
# ② 所有 Text(标识符) 形态（Text(字面量) 会解析，所以只可疑变量形态）
grep -rnE 'Text\((label|help|text|message|subtitle|note|guidance|detail|title)\)' PinkHouseOps/
```

然后**逐条看语法形态**。关键判据是「参数是**变量**还是**单个字面量**」：

| 写法 | 解析 Markdown？ |
|---|---|
| `Text("…**…**…")` | ✅ 单个字面量 → LocalizedStringKey |
| `Label("…**…**…", systemImage: "x")` | ✅ 同上（`systemImage:` 只是参数标签） |
| `Text("…**…" + "…")` | ❌ 拼接结果是 `String` 变量 |
| `Text(变量)` / `Text(cond ? "a" : "b")` | ❌ |

> ⭐ 最容易漏的就是 `Text("a" + "b")` —— 看着像字面量，实际是**运行时拼接**。
> 只有**单个**字面量才自动走 `LocalizedStringKey`。
