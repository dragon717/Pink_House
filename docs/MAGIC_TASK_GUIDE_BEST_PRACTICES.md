# 魔法任务引导定位与高亮最佳实践

本文档基于两条已落地链路沉淀：
- 萌宠智能对话（`aiAnalysis`）解锁前/解锁后双态引导
- 来财（`wealth`）五步跨页面引导  
- 小组件定制（`widgetCustomize`）四步跨页面引导  
- House 热区 / 悬浮层 / 顶层引导窗口命中治理

目标：让后续魔法任务引导改造可复用、可验证、低风险。

---

## 1. 问题复盘（本轮已修）

### 1.1 问题现象（AI 引导）

1. 点击“新手引导”后，第一步（返回「我」）被直接跳过。  
2. 第二步 VIP 卡片高亮与真实卡片容器尺寸不一致。  
3. 第三步“兑换会员时长”高亮偏上，视觉焦点不准。  

### 1.2 根因（AI 引导）

1. **错误的自动跳步时机**：`onAppear` 里直接推进 step1 -> step2，未等待真实用户路径。  
2. **硬编码 frame**：高亮区域用固定 `CGRect`，无法适配不同卡片尺寸/布局变化。  
3. **未做局部微调能力**：高亮与视觉焦点没有“轻量偏移参数”。  

---

### 1.3 问题现象（Wealth 引导）

1. 启动引导后错误跳到萌宠对话，不符合“先点 House”的用户路径。  
2. “马上来财”高亮范围偏大，与真实热区不一致。  
3. 热区理论可穿透，但首次点击命中率低（用户体感“点不进去”）。  
4. House 第一步高亮圈与猫爪视觉焦点不贴合，需要联动微调。  

### 1.4 根因（Wealth 引导）

1. **导航抢跑**：触发引导时做了自动 Tab 跳转。  
2. **采集层级错误**：对带 `position` 的容器做 frame 采集，得到的是大容器而非目标热区。  
3. **命中区过小**：视觉区域小、热区也小，虽能穿透但点击容错不足。  
4. **焦点只调一层**：只调猫爪或只调圈会造成“看着不准”。  
5. **顶层引导窗口命中模型被误解**：`GuidePassThroughWindow` 的“交互白名单区域”并不会把点击转发给底层业务控件，而是让引导层自己的 view 接住点击；如果高亮步骤只画圈、不在引导层注册透明按钮，用户会看到高亮但点不进。  
6. **全局悬浮手势覆盖过大**：像悬浮宠物这类全局组件，若把 `DragGesture(minimumDistance: 0)` 挂在整屏根容器上，会和 House 热区、引导热区发生竞争。  

---

### 1.5 问题现象（Widget 引导）

1. 第一版把 step1「返回到我」自动跳过，用户感知链路断裂。  
2. 修正后又出现另一端问题：如果用户启动引导时已经在「我」页，step1 可能卡住不推进。  
3. 点击 step1 的小猫爪时，只切了引导步骤，没有真的退出「魔法任务」页面。  
4. step2「下滑找到小组件」提示不够明显，用户难以理解需要继续往下滑。  
5. step3「点击小组件豆腐块」提示框落在底部，遮挡了目标区域。  

### 1.6 根因（Widget 引导）

1. **把“当前页面状态”当成“已经完成用户动作”**：已在 `me` tab 不等于 step1 可以直接跳过。  
2. **只改引导状态，未驱动真实页面返回**：小猫爪没有触发 `dismiss`，导致页面仍停留在 `MagicTasksView`。  
3. **缺少页面退出事件收敛**：没有把「魔法任务已关闭」作为推进 step1 -> step2 的正式事件。  
4. **滑动提示只有弱视觉，无明确文案**：用户不知道目标在更下方。  
5. **气泡位置未跟步骤目标协同**：目标在底部时，说明气泡仍固定在底部。

## 2. 已落地方案（当前实现）

### 2.1 步骤推进从“时间驱动”改为“事件驱动”

- 不在 `onAppear` 自动推进 step。  
- **解锁前链路** step1 -> step2 必须满足：
  - 用户回到 `me` tab；
  - 且已采集到 VIP 卡片真实 frame。  
- 解锁前 step2 -> step3 由 VIP 中心打开事件推进（`.vipCenterOpened`）。  
- **解锁后已领养链路** step1（点击萌宠对话 Tab）-> step2（点击对话窗口内嵌引导选项）由真实 `homeTabChanged(tab=petChat)` 推进。
- 解锁后已领养链路 step2 -> step3（能力讲解）由内嵌引导选项点击事件推进（`.petChatGuideOptionTapped`）。
- 若用户已做过一次“看天气穿搭”，再次启动 `aiAnalysis` 引导时，不能复用历史消息里旧的引导按钮作为当前目标；需要为本次引导会话补一条新的可见引导消息，并移除旧的同类专用提示，确保 step2 总能命中当前屏幕里的真实按钮。
- **解锁后未领养链路** 必须先插入领养前置流程：`进入萌宠对话 -> 领养面板出现 -> 左右滑动浏览 -> 回到奶茶 -> 点击领养 -> 输入名字并点确定 -> 回到对话内引导选项 -> 能力讲解`。
- 领养面板分支应使用真实事件推进：面板出现、当前宠物切换、名字弹窗出现/取消、领养完成，不能只因为进入 `PetChatView` 就直接跳到对话按钮步骤。
- 领养按钮和选宠区域都应采集真实 frame；“领养奶茶”和“输入名字”这两步的说明气泡放上方，避免遮住领养按钮或系统命名弹窗。

### 2.2 高亮从“硬编码”改为“真实控件坐标”

- 在 `MeView` 捕获 VIP 卡片全局 frame。  
- 在 `VIPCenterView` 捕获“兑换会员时长”按钮全局 frame。  
- 在首页底部导航捕获「萌宠对话」Tab 区域，在萌宠对话页捕获对话内嵌引导选项按钮区域。  
- Legacy 自定义底栏（iOS 18-25）中的「萌宠对话」Tab，建议单独采集固定锚点（如 `68x56`）并将 fallback 按底栏真实布局公式计算，避免右偏。  
- Overlay 内把全局 frame 转成本地 frame 后绘制挖空与高亮。  

### 2.3 兼容策略

- 提供 fallback frame（兜底），避免采集失败时引导完全不可用。
- VIP 卡片 fallback 同时适配两种高度：`100`（未开通）与 `180`（已开通）。
- “兑换会员时长”高亮支持微调偏移（当前 `dy = +10`）。

#### iOS 26 特殊注意

- **Tab 项定位**：iOS 26 的 `UITabBarButton` 已移除，`captureGuideTarget` 在 Tab label 上也失效。Tab 项定位改用 `TabBarItemAnchorResolver` 的 PlatterView 等分策略。
- **Fallback 不能假设 tab bar 居中**：iOS 26 的 Liquid Glass tab bar 不居中（search tab 独立分离在右侧），使用 `SmallWorldMenuOverlay.buildFallbackFrame` 统一计算。
- 详见 `docs/TabView_Best_Practices.md` 第 9 节。

### 2.4 生命周期清理

- 每次开始/完成/关闭引导都清理引导目标 frame，避免旧页面坐标污染。  

### 2.5 Wealth 顺序与事件收敛

- 强制路径：`House tab -> 马上来财 -> 请签 -> 数钱 -> 安财`。  
- 不自动跳萌宠，不抢用户操作。  
- 通过通知驱动推进：`.homeTabChanged`、`.wealthDestinationOpened`、`.wealthViewOpened`、`.wealthMainTabChanged`。  
- House 第一步（点击 `House tab`）优先使用实时采集目标（`homeHouseTab`）；高亮框按目标中心归一化，猫爪与高亮使用同一中心点，避免错位。  

### 2.6 热区采集与命中区策略（关键）

- **采集**：用独立透明锚点采集目标 frame（`allowsHitTesting(false)`），不要直接对“可能被定位/缩放的容器”采集。  
- **命中**：对难点中的小热区，允许“仅扩命中区，不扩视觉文案区域”。  
- **一致**：命中区扩展后，高亮锚点也要同步扩展，避免“看得到点不到”。  
- **House 小入口兜底**：像「穿搭手帐镜子入口」「梦裙日历台历入口」这类在竖屏 Pro 机型上会缩到 `30pt` 左右的小热区，必须单独设置最小点击尺寸；推荐按中心点扩展到至少 `40x64`（细长入口）或 `52x52`（块状入口）。  
- **全局手势**：悬浮宠物、浮层拖拽把手、全局截图辅助层等，默认只在“视觉本体附近的小区域”起手，不要把手势挂在全屏 `GeometryReader/ZStack` 根上。  
- **顶层引导窗口**：凡是运行在 `GuidePassThroughWindow` 上的点击步骤，都要明确区分两种模式：
  - 只讲解，不接管点击：遮罩/高亮/猫爪统一 `allowsHitTesting(false)`；
  - 需要用户点高亮区域：必须在引导层自己放一个透明按钮或透明点击层，并注册 `captureGuideInteractionRegion`，不要假设“挖空后底层控件自然能点到”。  

### 2.7 Widget 顺序、返回与提示收敛

- 强制路径：`返回到我 -> 下滑找到小组件 -> 点击小组件豆腐块 -> 进入小组件说明页`。  
- step1 必须先显示，不允许因“已在我页”而直接跳过。  
- 用户点击系统返回，或点击小猫爪，都会先真实关闭 `MagicTasksView`，再进入 step2。  
- `MagicTasksView` 退出通过通知回传：  
  - 请求关闭：`.dismissMagicTasksView`
  - 已关闭：`.magicTasksViewDismissed`
- 对 `aiAnalysis` 这类 step1 是“返回到我”的链路，`magicTasksViewDismissed` 必须区分“明确由引导返回动作触发的关闭”与“普通视图消失”；只有前者才能推进到下一步，避免返回步骤还没显示就直接跳到 VIP 卡片。  
- step2 使用“文案卡片 + 手势/箭头循环动画”强化提示，明确说明目标在下方豆腐块区域。  
- step3 气泡放到上方，避免遮住底部目标热区。  

### 2.8 iOS18 自定义底栏遮挡治理（设置页）

- 先区分问题层：**滚动手势是否可达** vs **内容容器是否被底栏覆盖**。  
- 对“我页豆腐块进入的设置页”优先在**共享设置容器**统一留底（如 `AdaptiveSettingsView`），不要每个子页零散补丁。  
- 统一用 `.safeAreaInset(edge: .bottom)` 预留 Legacy 自定义 TabBar 高度（`56 + 底部偏移 + 缓冲`），避免“能滑但最后一项露不全”。  
- 避免双重留白：容器层已做底部避让后，Tab 层不要再对同一页面重复加 inset。  
- 对滚动步骤推进（如“继续下滑找到属性字段管理”）使用“部分可见阈值”而不是严格全可见，降低底部临界区卡步概率。

## 3. 最佳实践清单（可直接复用）

### 3.1 引导步骤推进

- [ ] 不在 `onAppear` 直接跳步骤。  
- [ ] 每个步骤定义明确“推进条件”（通知、状态、frame 可用性）。  
- [ ] 条件不满足时停留当前步骤，不抢跑。  
- [ ] “用户已处于目标页面”与“用户已经完成该步骤”要分开判断。  
- [ ] 若设计要求保留某一步，即使当前已满足页面条件，也只能在真实用户动作或显式次级入口后推进。  
- [ ] 对“返回到我页/上一页”这类步骤，不能因为底下宿主 tab 本来就是目标页就自动跳过；必须等待上层 `MagicTasksView` / 设置页 / 二级页真实关闭后再推进。  

### 3.2 高亮定位

- [ ] 优先使用真实控件 frame。  
- [ ] 必须做 global -> local 坐标转换。  
- [ ] fallback 只作为兜底，不作为主路径。  
- [ ] 引导启动若清空了目标 frame 缓存，必须立即触发可见目标重采集（即使 frame 未变化），避免静态入口长期停留在 fallback 错位。  
- [ ] iPad 上若拿不到真实 frame，优先只显示说明气泡，不显示 fallback 高亮。
- [ ] iPad 上拿到真实 frame 后，高亮挖空/描边不再按屏宽二次放大（保持 1x），避免框体过大误导点击。  
- [ ] 底部 Tab 圆形高亮若经过自适应缩放渲染，需对输入 frame/radius 做反向补偿，避免“圈体放大一圈”与贴底裁切。  
- [ ] 高亮圆角应与真实控件视觉风格一致。  
- [ ] 目标位于底部区域时，优先把说明气泡放上方；目标位于顶部区域时反向处理。  
- [ ] 对双页签/分段控件步骤，若文案要求点击其中一个页签，不要只高亮整条分段控件；应收敛到对应页签本身，并让猫爪落在该页签中心。  
- [ ] 对系统 `alert` / 输入框类步骤，若键盘弹出会推动弹窗上移，引导高亮不能写死屏幕中心；要监听键盘 frame 变化并按可见区重新计算弹窗高亮位置。  

### 3.3 交互穿透

- [ ] 遮罩和高亮动画默认 `.allowsHitTesting(false)`。  
- [ ] 引导提示框统一挂在全局最上层窗口渲染，避免被 `sheet/fullScreenCover` 遮挡。  
- [ ] 只让真实业务控件处理点击，减少误触。  
- [ ] 若用户反馈”第一下难点中”，先检查命中区尺寸，不要先怀疑穿透失效。
- [ ] 若引导提供”替代操作入口”（如小猫爪），该入口必须驱动真实业务动作，而不是只改本地 step 状态。
- [ ] 若页面上存在全局悬浮组件（如 `PetOverlayView`），优先检查是否把手势挂在整屏根容器；这类组件的交互区域必须收敛到视觉本体附近。  
- [ ] `GuidePassThroughWindow` 的“交互白名单”语义是“允许引导层自己的控件接住点击”，不是“把点击透传回主窗口业务控件”；设计点击步骤时不要混淆这两种模型。  
- [ ] 对需要点击高亮框推进的步骤，优先在引导层放透明按钮，并让它触发和底层一致的真实业务动作或导航事件。  
- [ ] 对只要求“点击底层真实控件”的步骤，要么完全不启用引导层交互白名单，要么同时在引导层补透明热点；不能只画高亮圈再期待底层自然收到事件。  
- [ ] 对”点击后触发页面跳转/动画”的高亮步骤（如点击手帐卡片触发3D翻页、点击菜单项触发图片选择器），需要在 `highlightedRectGuideContent` 中传入 `onHighlightTap` 回调，在用户点击高亮区域时立即推进步骤，使高亮消失。不能依赖目标页面的 `onAppear` 通知，因为页面跳转/动画期间 `onAppear` 尚未触发，高亮会残留。
- [ ] `onHighlightTap` 的实现方式：在高亮区域上方覆盖一个 `Color.clear` + `contentShape(Rectangle())` + `onTapGesture`，既能接收点击又不阻挡底层控件。注意：`simultaneousGesture` 在 `allowsHitTesting(false)` 的 view 上无效。
- [ ] （待验证）`onHighlightTap` 方案实测未生效，需进一步调研 `Color.clear` 在 `allowsHitTesting(false)` 的 ZStack 中是否真正可点击，或需要改用其他方案（如监听业务通知、在业务层直接推进步骤）。

### 3.4 状态管理

- [ ] 引导临时状态和业务状态分离。  
- [ ] 退出引导时重置临时锚点。  
- [ ] 日志打印只保留步骤关键路径。  
- [ ] 跨页面引导要维护最近一次 `homeTab` 等全局状态，但只能作为判断辅助，不能替代用户动作事件。  
- [ ] 对“页面关闭”“页面打开”“目标 frame 捕获成功”分别建立独立通知，不混用。  

### 3.5 微调参数治理

- [ ] 把焦点偏移写成常量（如 `houseGuideXOffset/YOffset`），不要散落魔法数。  
- [ ] “圈 + 猫爪”联动调整，保持同一视觉目标。  
- [ ] iPad 上对首次引导和魔法任务引导，禁用圆形猫爪高亮，避免大屏下出现误导性落点。
- [ ] 首次引导 `welcome` 阶段底部圆形高亮（小猫起点）优先使用屏幕高度比例下移，并加底部安全区上限约束，避免在 Pro / Max 机型偏高或贴底。
- [ ] 首次引导若“跑步视频”先于位移动画开始预播，计算跑步秒数时必须扣除这段预播时间，并额外留出尾帧预算；不要把首段播到只剩不到一帧再切第二段。  
- [ ] 首屏与所有右上角入口（`+` / 更多）统一先采集图标周围透明锚点，再按容器尺寸和顶部安全区换算成可点击区域；不要直接用屏幕百分比或固定 `dy`。  
- [ ] 对右上角导航入口（如批量编辑 step1「更多」）统一使用同源 `y` 轴偏移，避免只挪高亮或只挪猫爪导致错位。  
- [ ] 对“先点更多再点编辑”这类双动作入口，菜单弹出后应切换到「编辑」行高亮；拿不到实时 frame 时提供稳定 fallback，避免用户看不到目标。  
- [ ] 「编辑」行 fallback 计算应基于原始「更多」按钮锚点，不要复用 step1 下移后的高亮坐标，避免高亮框落到菜单下方。  
- [ ] 对“认识批量编辑工具条”这类说明步骤，应同时高亮底部工具条容器，并让猫爪落在工具条中心，避免只显示说明卡片导致用户找不到焦点。  
- [ ] 猫爪透明度/位置作为独立参数，便于按页面做细调。  
- [ ] 滑动提示类步骤需要同时治理：文案、动画、停留位置、是否遮挡目标。  

### 3.6 跨页面返回步骤专项

- [ ] step1 若文案是“返回到某页面”，必须让页面真实返回，而不是仅在引导层模拟完成。  
- [ ] 若页面有系统返回按钮和自定义辅助入口（如猫爪），两者都要汇聚到同一推进函数。  
- [ ] 页面关闭后的推进应优先监听 `onDisappear` / 关闭通知，而不是依赖固定延迟。  
- [ ] 固定延迟只作为兜底，不作为主路径。  

### 3.7 滑动查找步骤专项

- [ ] 对“继续下滑/上滑查找”的步骤，必须给出显式方向文案。  
- [ ] 至少提供一种强视觉提示：箭头、手势动画、路径渐亮、呼吸光效。  
- [ ] 目标一旦进入可见区并捕获到 frame，应再推进到点击步骤，而不是要求用户重复理解。  
- [ ] 若页面存在 iOS18 Legacy 自定义底栏，优先在公共滚动容器统一做底部 `safeAreaInset`，不要让最后一项落在底栏后方。  
- [ ] 可见性判定建议使用非对称可见区（顶部与底部分别扣减）+ 部分可见阈值，避免“用户已看到目标却仍卡在继续下滑”。  

### 3.8 解锁前任务复用专项

- [ ] 先判断功能是否“未解锁但允许预引导”，不要把它们直接挡死。  
- [ ] 解锁前优先复用同一条“衣橱右上角 +”引导链，但文案要按功能目标微调。  
- [ ] `ootd / 魔法贴纸 / 梦裙日历 / 空间手帐 / 批量导入` 共用同一套衣橱预引导渲染与定位函数，不要再按功能各写一套 step1/step2。  
- [ ] 复用链建议拆成两步：**step1 点 + 号展开菜单**、**step2 点目标菜单项**（如手动创建/批量导入），避免把两件事塞在一步文案里。  
- [ ] 如果某个功能只是“借用另一个功能的预引导作为前置任务”（例如 `spaceBook` 在 `ootd` 未解锁时借用 `ootd` 预引导），完成该引导后要按被借用功能的完成语义处理，不能把完成/解锁/奖励错误记到外层功能上。  
- [ ] 若前置功能的任务条件其实已经完成、只是还没在魔法任务里点击“立即解锁”（例如 `spaceBook` 依赖的 `ootd`），优先引导回到魔法任务列表，找到该前置任务并点“立即解锁”；不要错误地重新带用户去做一遍衣橱前置任务。
- [ ] 预引导完成后，不要误记为“已完成体验引导”；只有真正解锁后的正式体验，或 manual 任务，才落完成态。  
- [ ] 对“手动创建 / 批量导入”这种复用链路，完成条件应监听真实页面打开事件，而不是点了菜单按钮就算完成。  
- [ ] 对非衣橱解锁前引导（如 `aiAnalysis`），也要保持“解锁前链路”和“解锁后正式体验链路”分离，避免未解锁时误记正式体验已完成。  
- [ ] step1 -> step2 优先用“菜单已展开”事件推进，并用菜单项真实 frame 做高亮；拿不到时再用菜单区域 fallback。  
- [ ] 菜单项目标采集优先挂在 `Button` 行本体，不要只挂在 `Label` 文本/图标上；不同系统样式下行容器更稳定。  
- [ ] 菜单每次展开前先清空上一次菜单项 frame（手动创建/批量导入），避免复用旧坐标导致高亮漂移。  
- [ ] `+` 按钮菜单链路建议多路上报“菜单已展开”：`+` 按钮点击、菜单项 `onAppear`、菜单项 action 触发三处至少覆盖两处，避免系统样式差异导致 step1 卡住。  
- [ ] 顶栏 `Menu` 在新系统样式下可能被系统合并成胶囊分组；`+` 号目标采集应优先挂在 `label` 图标本体，不要只挂在整个 `Menu` 容器。  
- [ ] 对右上角 `+` 号高亮要做归一化：当捕获框异常变宽（疑似整组胶囊）时，自动收敛到最右侧按钮区域，再用于 step1 高亮与猫爪落点。  
- [ ] 若视觉上仍偏上，优先基于按钮框高度 / 顶部安全区做相对微调；只有同一类入口共用一套相对公式时，才允许保留 step1 的轻量同源 `y` 轴偏移。  
- [ ] step2 使用菜单项 frame 时，需校验“尺寸 + 顶部区域 + 与 add 按钮相对位置”三要素，防止旧 frame 漂移到中部卡片区。  
- [ ] 若菜单包含「从上次未保存继续」导致总行数变化，step2 fallback 必须按真实行数（3 行）计算；`batchImport` 解锁态要优先高亮最下方「批量导入」。  
- [ ] fallback 的“是否有草稿行”判断，必须与菜单渲染逻辑使用同一口径（有效草稿），不能只看 `UserDefaults` 原始 key 是否存在。  
- [ ] 当目标菜单项 frame 暂时缺失时，可用相邻菜单项推断下一行/上一行，避免错高亮到「手动创建」。  
- [ ] 若系统 `Menu` 在当前系统样式/容器下无法稳定拿到菜单项坐标，优先切到“引导快捷入口”方案（底部气泡 action 按钮），并确保该按钮触发与真实业务一致的打开动作（手动创建/批量导入）。  

### 3.9 「返回我页 + 点击豆腐块」专项

- [ ] return step 必须独立保留，不因当前 tab 恰好正确而自动跳过。  
- [ ] return step 结束事件优先收敛到页面真实 dismiss / disappear 通知。  
- [ ] 若目标豆腐块常位于首屏下方（如主题配色），应在 return 后补“下滑查找”步骤，再进入点击步骤。  
- [ ] 进入 `Me` 页后的目标豆腐块，统一走 `GuideTargetKey + captureGuideTarget`，不要再写死坐标。  
- [ ] 主题配色、个性化偏好这类“返回后再点设置入口”的链路，可共用同一套 return-step 设计。  
- [ ] 客制化配色和个性化这类“主题页签内二段引导”，建议拆成：返回我页 → 下滑找主题配色 → 点击主题配色 → 切到客制化配色页签 → 讲解个性化入口。  
- [ ] 本地文件备份与恢复链路建议拆成：返回我页 -> 下滑 -> 点系统与更多 -> 单独讲解「备份数据」重要性 -> 单独讲解「恢复数据」与跨设备/跨平台恢复价值 -> 引导完成首次备份；最终完成条件建议收敛到真实备份触发事件（如 `localBackupTriggered`），并在文案里明确“备份可能较慢，可先跳过下次再做”。  
- [ ] 若首次备份步骤会弹出二次确认框，step6 的高亮必须切换到确认框本身，小猫爪落在「确认备份」按钮；取消后要清掉该弹窗的临时 target frame，回退到「备份数据」入口，避免高亮残留在旧位置。
- [ ] 导出表格（CSV）这类“点击即触发异步动作”的入口，完成条件应监听真实触发事件（如 `exportCSVTriggered`），不要用点击高亮就算完成。  
- [ ] 云端文件备份与恢复这类“先登录再讲解”的链路，必须区分登录态：未登录先高亮 Apple 登录，已登录可直接进入功能讲解步骤。  
- [ ] 个性化偏好这类“设置页多模块讲解”应拆成连续步骤，并对每个模块分别高亮（如界面样式→筛选模式→应用外观）。  
- [ ] 隐私显示这类“设置页双开关讲解”应依次高亮每个开关，并明确两者控制的展示字段差异（入库价 / 原价）。  
- [ ] 标签/品牌/属性字段这类“设置页底部管理项”链路应增加显式下滑步骤，再逐项高亮讲解；目标靠近底部时提示框放上方。  
- [ ] 最后一步（应用外观）建议提供更细粒度说明：背景类型、透明度、模糊、字体配色与卡片样式分别影响什么。  

### 3.10 House 热区 / 长按菜单专项

- [ ] House 场景入口分两类：静态热区（如穿搭手帐、梦裙日历）和长按快捷菜单（如魔法贴纸），两者要分别建事件。  
- [ ] 热区优先采真实热区 frame；快捷菜单优先采菜单项 frame，若拿不到就用“菜单已打开 + 目标页已进入”双事件兜底。  
- [ ] 魔法贴纸长按链路要先检查常用菜单是否含「魔法贴纸」：若缺失，先走「返回我页 → 点击常用菜单设置 → 添加魔法贴纸 → 返回我页」，再继续「长按 House tab → 点击魔法贴纸」。  
- [ ] 穿搭手帐镜子热区的 fallback 建议落在镜子中上段（避免贴到上沿或偏到镜子外）。  
- [ ] 从 House 热区进入后的第二步，不要直接结束；至少补一层“这个页面的核心信息是什么”。  
- [ ] 若入口在底部 tab 或悬浮菜单附近，说明气泡要避开热点本身。  
- [ ] House 首次进入点不动时，先分三层排查：`底层热区按钮是否收到点击`、`是否有全局悬浮手势层抢事件`、`是否有顶层引导窗口白名单把点击锁在引导层`。  
- [ ] 若“无引导正常，有引导失效”，优先检查当前步骤是否只画了高亮框、但没有在引导层注册同位置透明点击热区。  
- [ ] 若“无引导也失效”，优先检查全局悬浮组件是否把 `DragGesture(minimumDistance: 0)` 或 `TapGesture` 挂在整屏根容器。  
- [ ] 对系统 `Menu` / 原生菜单类步骤，若高亮准确但点击仍不稳定，优先改成“引导态使用 guide-owned 自定义菜单浮层、非引导态继续保留原生 `Menu`”，不要继续依赖系统菜单面板的命中或几何捕获。  
- [ ] 自定义引导菜单必须锚定真实按钮 frame，菜单项显示条件与正式菜单共用同一套业务判断；点击引导菜单项时，必须走与正式菜单完全同一条 action。  
- [ ] 空间手帐这类“入口页签 + 列表/详情双层结构”链路，启动时先判断用户当前停在哪一层；如果连续任务把用户留在平面书页详情页，先引导点左上角返回到手帐列表，再捕获「空间」页签，避免直接高亮一个当前不可见的目标。

### 3.11 多阶段内容创建专项（空间手帐）

- [ ] “手帐 -> 书页 -> 编辑器 -> 扫描”这类链路，必须拆成多个真实业务事件，而不是一张说明卡带过。  
- [ ] 若产品定义入口在“衣橱统计卡片（穿搭手帐）”，不要误用 House 热区作为 step1。  
- [ ] 对创建型步骤，尽量让业务动作本身自然落到下一页，例如“创建空间手帐后直接进入新手帐”。  
- [ ] 若用户已有历史数据（已有空间手帐 / 书页），应优先复用存量内容并跳过新建步骤，引导“直接点第一本 / 第一页”继续后续链路。  
- [ ] 书页创建后，再引导点击书页进入编辑器；不要在”书页已创建”和”编辑器已进入”之间凭延迟跳步。
- [ ] 对”点击手帐卡片→3D翻页动画→进入详情页”、”点击菜单项→选择自定义图片→创建书页”这类多段异步流程，高亮消失应尽早触发（点击时），不应等待最终页面 `onAppear`。当前 `onHighlightTap` callback 方案未验证通过，需调研替代方案。
- [ ] 编辑器说明应先讲清主工具栏、素材库和导入菜单，再引导到具体能力（如相机扫描）。  

### 3.12 SwiftUI 编译复杂度专项

- [ ] 大型 Overlay 不要把十几条 `.onReceive` / `.onChange` 串在一个表达式里。  
- [ ] 按领域拆成 `bindLifecycleEvents / bindSettingsGuideEvents / bindHouseGuideEvents / bindWealthGuideEvents` 这类小函数，降低类型推断压力。  
- [ ] 复杂 `switch + GeometryReader + AnyView` 的组合一旦变多，要优先控制每个分支体量，而不是继续往一个函数里堆。  
- [ ] 编译器报 “unable to type-check this expression in reasonable time” 时，先拆 modifier 链，再看业务逻辑。  

### 3.13 引导视频衔接专项

- [ ] 引导里的“跑步/指向/讲解”这类多段视频，不要只按视觉动画时长拍脑袋配秒数；先确认素材真实时长、播放倍率、预播时长和尾帧停留预算。  
- [ ] 若视频会先于位移动画开始预播，计算首段可播放预算时必须扣掉这段预播时间，否则很容易把首段播到只剩不到一帧。  
- [ ] 若产品要求“循环播一段，结束时停在最后一帧再切下一段”，优先使用单 `AVPlayerItem` + `didPlayToEndTime` 后手动 `seek(.zero)` 的循环方案；不要依赖 `AVPlayerLooper.disableLooping()` 来承接最后一遍的结束回调。  
- [ ] 首段切到非循环后，应让播放器在当前 item 上自然播到末尾，并以明确的尾帧停留时长推进下一段；不要把“尾帧停留”建立在兜底定时器上。  
- [ ] 这类问题排查时，先区分“管理器切段过早”与“播放器没收到结束回调”两层，再决定是调秒数还是换播放器策略。  
- [ ] 临时诊断日志应同时覆盖管理器时间线（开始、关循环、收到 onFinished、真正切段）与播放器时间线（加载、循环转单次、收到 `didPlayToEndTime`）；确认根因后必须删除。  

### 3.14 提醒框主题配色一致性专项

- [ ] 引导提醒框颜色统一来自 `MagicThemeDesignSystem.palette(...)`，不要混用硬编码品牌色。  
- [ ] 文本优先使用语义色：`primaryText / secondaryText / tertiaryText`，不要直接写 `.primary/.secondary`。  
- [ ] 跳过胶囊优先使用 `quickOptionFill / quickOptionStroke / quickOptionText`，避免 `.ultraThinMaterial` 在不同主题下失真。  
- [ ] 进度圆点的非激活色使用 `tertiaryText.opacity(...)`，确保在魔法配色 / 客制化配色 / 个性化配色下都可读。  
- [ ] 主按钮文字优先使用 `bubbleUserTextColor`，与主题系统的气泡色策略保持一致。  

### 3.15 体验任务鱼币分档专项

- [ ] 仅 `manual`（体验任务）在首次完成引导时发放鱼币，避免解锁型任务混入该奖励。  
- [ ] 鱼币按引导步数分档：`1~2 步 = 66`、`3~4 步 = 88`、`5 步 = 100`、`6 步 = 200`、`7 步 = 300`、`8 步及以上 = 500`。  
- [ ] 奖励触发应绑定“真实完成事件”（`completeFeatureExperienceGuide`）并在首次解锁成功后发放。  
- [ ] 任务详情应展示“引导步数 + 奖励档位”，让用户清楚不同任务为什么奖励不同。

## 6. 关键冲突与决策建议

### 冲突 A：严格顺序 vs 自动导航便捷

- 决策：引导优先“用户操作感知”，不抢跳页面。  
- 原因：自动导航虽快，但会造成“我没点就过去了”的失控感。

### 冲突 B：高亮精准 vs 点击容错

- 决策：视觉高亮贴近真实热区，同时可对点击目标做小幅命中扩展。  
- 原因：移动端真实使用中，命中容错比像素级精度更影响体验。

### 冲突 C：穿透正确 vs 首次命中失败

- 决策：先验证命中框大小，再验证遮罩 hit-testing。  
- 原因：大量“点不进去”并非穿透失败，而是热区过小。

### 冲突 D：保留步骤完整性 vs 当前页面已满足

- 决策：保留步骤文案与演示完整性，但推进依然由真实动作触发。  
- 原因：用户需要理解路径，不代表系统可以擅自替用户完成该步骤。

### 冲突 E：辅助入口便捷 vs 业务页面真实变化

- 决策：辅助入口（如猫爪）可以存在，但必须驱动真实返回/跳转。  
- 原因：若只改引导状态，会导致“文案说已返回，页面却还在原处”的割裂感。
