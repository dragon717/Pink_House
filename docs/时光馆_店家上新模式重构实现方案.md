# 时光馆重构实现方案 —— 对齐「少女心愿·店家上新」模式

> 版本：V1.0（2026-09-20）
> 依据文档：《少女心愿‑店家上新/历年系列 V1.1‑Dev 开发文档》
> 参照模式：工程内已落地的「少女心愿」模块（代码命名空间 `ShopCatalog`）
> 关联文档：`docs/少女心愿_店家上新_第一版落地计划.md`、`docs/Pink_House_TimeHall_Static_CloudKit_Design.md`

## 0. 一句话结论

把底部 Tab「时光馆」从当前「梦裙编年史 + 多模式图鉴 + 双品牌双管道」的杂糅状态，重构为与「少女心愿」完全同构的 **Lolita 店家商品档案库**：时光馆首屏即「店家上新」，公共 Catalog（Shop / Series / Product / Variant / SizeChart / SaleEvent / Asset）+ 用户私有状态（心愿 / 尾款 / 衣橱）ID 引用 + 白名单运营（草稿→审核→发布→归档）。旧编年史与 Midsummer 数据一次性迁入 Catalog，旧视图归档下线，不重写心愿 / 尾款 / 衣橱底层。

## 1. 现状问题诊断（为什么必须重构）

| # | 问题 | 现状证据 |
|---|------|---------|
| 1 | **巨石视图** | `Views/TimeHall/TimeHallView.swift` 单文件 3469 行，含 4 种模式（编年史/图鉴手册/珍选/搭配）、主题枚举、衣橱草稿 Builder（2218 行起） |
| 2 | **双轨业务并存** | 时光馆内同时存在 TimeHall V3 DTO（Bundle 编年史种子）与 ShopCatalog（店家上新）两套商品模型；Midsummer（仲夏物语）又是第三条独立管道 |
| 3 | **三套品牌身份** | `TimeHallMerchant` 枚举、`TimeHallBundleSource.brandSeeds`、`TimeHallBrandMeta` 各自维护品牌清单；`TimeHallBrandListTheme` 用 camelCase（"pinkHouse"）而 seeds 用 kebab-case（"pink-house"），占位色永远 miss |
| 4 | **Rebuild 半成品** | `Views/TimeHall/Rebuild/` 只迁完品牌列表页，轮播选品牌页 `merchantSelection` 已弃用但仍残留在源文件中 |
| 5 | **云分发建好待用** | TimeHall CloudKit 只读静态分发（THRelease/THDataPack/THMedia）链路完整但 `isCloudSyncEnabled` 默认关闭，首个 THRelease 未发布，形成空转维护成本 |
| 6 | **与业务文档定位脱节** | V1.1 文档明确「时光馆 → 店家上新 → 店家列表 → 店家主页 → 当前上新/历年系列 → 系列详情 → 商品详情」，而现状时光馆首屏不是店家上新 |

## 2. 目标定位

> **时光馆 = 少女心愿自己的 Lolita 店家商品档案库的正式入口（品牌年鉴馆）。**

- 首屏即「店家上新」：看店家当前上新、翻历年系列年鉴、查商品档案（图/配色/尺码/尺码表/历史价格）。
- **不是商城**：无购买、无支付、无订单、无物流、无淘宝跳转；普通用户仅查看 + 加入心愿 / 尾款 / 少女衣橱。
- 运营由白名单 `CreatorAccess` 管控，入口在 `设置 → 运营工具 → 店家商品库`，普通用户不可见。
- 底部导航不变：`衣橱 / 心愿尾款 / 时光馆 / 我`（`AppFeatureRegistry` 的 `.timeHall → route .tab(4)` 保持）。

### 与「少女心愿」模式的六要素一致性对照

| 模式要素 | 少女心愿现状 | 时光馆重构后 |
|---|---|---|
| 公共 Catalog | `ShopCatalogModels.swift` 七实体 | **完全复用，零新增模型** |
| 私有状态分离 | `Clothing` + 3 个可选引用字段 | 完全复用（见 §5.2） |
| 状态机 | `draft→submitted→reviewed→published`，任意态可 `archived` | 完全复用 `ShopCatalogDraftStore` |
| 运营端 | 白名单 + 补录上新 + 淘宝导入 + 看板 | 完全复用 `ShopCatalogOpsView` |
| 防重复 | name/alias 匹配店家、同店同名系列、同系列同名商品 → 追加 SaleEvent | 完全复用 `ShopCatalogDraftValidator` |
| 持久化 | Bundle 种子 + 本地 override + drafts JSON | 完全复用同一套 JSON 文件 |

**结论：时光馆重构不是再造一套 Catalog，而是让时光馆 Tab 直接成为 ShopCatalog 模式的用户端首屏，并把旧资产迁进来。**

## 3. 核心功能模块

### 3.1 用户端（全部复用 `Views/ShopCatalog/`，不新写页面）

| 页面 | 承载文件 | 核心功能 |
|---|---|---|
| 店家上新首页 | `ShopCatalogListView` | 搜索店家名称/别名；当前上新、最近上新、历年系列、全部店家；卡片以「系列」为单位 |
| 店家主页 | `ShopCatalogShopView` | 店家封面；当前上新；按年份 chip 浏览历年系列（品牌年鉴） |
| 系列详情 | `ShopCatalogSeriesView` | 系列主视觉/年份/季节；全部商品；品类筛选（JSK/OP/SK/Blouse/KC/小物/鞋/包/其他）；多选多品类批量加入衣橱 |
| 商品详情 | `ShopCatalogProductView` | 图集轮播+大图；店家/系列/配色/尺码；价格档案（预约价/现货价/差价）；结构化尺码表+原图；按钮组按预约状态切换 |

| 运营端 | `ShopCatalogOpsView` | 今日更新/草稿/待审核/待补充看板 + 补录上新（淘宝导入/手动）+ 整包导出 |

## 4. 用户交互流程

### 4.1 主链路（与 V1.1 文档完全一致）

```text
底部Tab【时光馆】
  └─ 店家上新首页（搜索/系列卡片流）
       └─ 店家主页（封面 + 当前上新 + 年份chip历年系列）
            ├─ 当前上新 ──┐
            └─ 历年系列 ──┤
                          ▼
                    系列详情（品类筛选 / 多选模式）
                         ├─ 多选加入少女衣橱 → WardrobeMergeView → 衣橱落库
                         └─ 点击单品 ▼
                       商品详情（轮播图/尺码表/价格档案）
                            ├─ 加入心愿
                            ├─ 我已经预约（预约期间）→ 心愿尾款
                            └─ 加入少女衣橱
```

### 4.2 商品详情按钮状态逻辑（复用现有判定）

| 场景 | 按钮组 |
|---|---|
| 预约期间（存在未结束的 `reservation` SaleEvent） | 加入心愿｜我已经预约｜加入少女衣橱 |
| 非预约期间 | 加入心愿｜加入少女衣橱 |
| 「我已经预约」 | 建立尾款记录：自动带入商品/店家/系列，用户选配色尺码，带入预约总价，定金可改自动算尾款，尾款时间可填「待公布」，支持自定义提醒；状态机 `我已经预约→已付定金→待付尾款→尾款完成→加入少女衣橱`，**无已发货/已收货** |
| 「尾款完成」 | 一键写入少女衣橱，支持多件合并 |

### 4.3 运营流程（复用现有）

```text
设置 → 运营工具 → 店家商品库（白名单可见）
  └─ +补录上新：选定店家+系列（可新建）
       ├─ 淘宝链接/分享文本批量导入 → 每条解析为独立 Product 草稿（失败不阻塞）
       └─ 手动录入：+添加单品，多品类混合，独立表单
  └─ 草稿逐个补全 / 删除 → 批量提交 → 单品粒度审核（部分通过/部分驳回）
  └─ 状态机：draft → submitted → reviewed → published（任意态可 archived）
  └─ 防重复：匹配已有店家/系列/商品；同商品新现货 → 追加 stock SaleEvent
```

## 5. 关键数据结构

### 5.1 公共 Catalog（复用 `Models/ShopCatalog/ShopCatalogModels.swift`，零改动）

| 实体 | 字段 |
|---|---|
| `CatalogShop` | id, name, aliases[], logo, cover, description |
| `CatalogSeries` | id, shopID, name, year, season, cover, description |
| `CatalogProduct` | id, shopID, seriesID, name, category, images[], description |
| `CatalogProductVariant` | id, productID, color?, size? |
| `CatalogSizeChart` | id, productID, unit, columns, rows, sourceImage |
| `CatalogSaleEvent` | id, productID, type(reservation/stock/rerelease), price, deposit?, balance?, startAt?, endAt? —— **追加式，永不覆盖** |
| `CatalogAsset` | id, type, thumbnailURL?, previewURL?, originalURL, width, height |

派生只读视图：`CatalogPriceArchive`（预约/现货各取最近一条 → 差价）。

### 5.2 用户私有状态（复用，不重写）

`Clothing.swift:150-152` 已有的 3 个可选引用字段即是全部关联：

```swift
var catalogProductID: String?
var catalogVariantID: String?
var catalogSaleEventID: String?
```

心愿（`isDepositPlan` + deposit/balance）、衣橱（`Clothing` + `AccessoryItem`）均不建新模型。

### 5.3 旧 TimeHall 资产 → Catalog 迁移映射（一次性迁移工具的输入输出约定）

| 旧实体（`TimeHallModels.swift` V3 DTO） | 迁移去向 | 说明 |
|---|---|---|
| pinkHouse 编年史 `CatalogueDTO` / `ArchiveCatalogueDTO` | `CatalogSeries`（year/season/cover） | pink-house 作为一个 `CatalogShop` |
| `TimeHallItemDTO`（kind dress/clothing/accessory, productCode） | `CatalogProduct`（category 按 kind+styles 映射） | **保留原 productCode 作为新 CatalogProduct.id 种子**（稳定标识） |
| `TimeHallCommerceItemDTO.priceTiers`（含 depositJPY/balanceJPY） | `CatalogSaleEvent`（stock/reservation + price/deposit/balance） | 每条 tier 一条事件，全部保留 |
| `TimeHallCommerceItemDTO.sizeChart` | `CatalogSizeChart` + `sourceImage` | 原图进 `CatalogAsset` |
| `TimeHallMerchant`（midsummerTale） | `CatalogShop`「仲夏物语」 | MidsummerSeries/MidsummerItem → CatalogSeries/CatalogProduct |
| `StoryDTO` / `CoordinateDTO` / `EventDTO` / `HistoryEntryDTO` | **不迁移** | 属编年史叙事内容；随旧馆归档，运营后续需要时按 Catalog 结构手动补录 |
| 收藏 `timeHall.treasured.v1`（UserDefaults） | 迁移为对应用品的 `Clothing` 心愿记录（isDepositPlan=false + catalogProductID） | 无法匹配的收藏保留在旧馆归档数据中不丢 |

### 5.4 持久化（与 ShopCatalog 完全一致）

- 种子：Bundle `ItemManager/Resources/ShopCatalog/shop-catalog.json`（迁移产物追加进种子或以 override 注入）
- 运营发布覆盖层：`Application Support/ShopCatalog/shop-catalog-override.json`（`rebuildMergedCatalog()`：同 id 跳过、新 id 追加、SaleEvent 一律追加）
- 草稿：`shop-catalog-drafts.json`
- 旧 TimeHall 缓存（`Caches/TimeHall/`）与控制状态（`Application Support/TimeHall/control.json`）在过渡期保留，Phase 4 清理；`TimeHallCacheSettingsView` 文案改为「馆藏档案缓存」或随旧馆下线。

## 8. MVP 验收标准（对齐 V1.1 文档 §5）

**用户端**
1. 时光馆 Tab 首屏即店家上新；可浏览店家上新、历年系列；查看图片、配色、尺码、尺码表；同屏查看预约价、现货价与差价。
2. 可加入心愿、加入少女衣橱；系列页支持多选多品类商品加入衣橱。
3. 心愿尾款状态仅：我已经预约、已付定金、待付尾款、尾款完成；无已发货/已收货。
4. 页面无任何购买链接/淘宝跳转。

**运营端**
5. 白名单可见运营入口，普通用户不可见；淘宝源链接不透出。
6. 一次补录任务录多单品、多品类混合；多条淘宝链接批量导入生成草稿，部分失败不阻断。
7. 店家/系列/商品编辑、删除、归档严格按引用保护执行（被引用 → 仅归档）。
8. 草稿‑提交‑审核‑发布‑归档完整；批量提交、单品粒度审核（部分通过/部分驳回）。
9. 手动录入可完整完成全部业务，不依赖淘宝解析。

## 9. 开发硬性约束（复述 + 新增）

1. 不重写心愿、尾款、衣橱底层逻辑，只靠 3 个 catalog* 引用字段关联。
2. Series 与 Product 不可合并；一个系列多条单品。
3. SaleEvent 追加式，历史价格永不覆盖。
4. 一切关联用数据库 id；商品名称、productCode 都不是稳定 ID（productCode 仅可作 id 种子）。
5. 被引用的 Catalog 实体只归档，禁止物理删除。
6. 淘宝解析只出草稿，绝不自动发布。
7. 用户侧不透出购买/跳转。
8. 【新增】旧 TimeHall/Midsummer 数据只迁不删：迁移工具必须输出报告，CloudKit 公共库数据保留不动。
9. 【新增】`ThemeSkinSlot`、主题皮肤、底部导航等既有结构一律不动。

## 10. 自测关键故事（对应 V1.1 文档 §7 + 迁移特有）
