# 「心愿 → 衣橱」加购分支按预约阶段区分 · 需求实现说明

> 2026-09-24 · 店家上新 / 加购记账
> 用户原文：
> 1. 预约期间：用户选择加入衣橱时，提供两个选项 —— ① 定金+尾款加入 ② 全款加入。
> 2. 预约结束后、用户仍想加入衣橱时：同样提供两个选项 —— ① 定金+尾款加入 ② 全款加入。
> 3. 定金尾款阶段结束后进入现货阶段：此时**仅提供全款**加入，选项为 —— ① 按预约价全款加入 ② 按现货价全款加入。
> 4. 当用户以定金+尾款方式加入心愿时，将其归入**心愿尾款列表**；在该列表内，当用户付完尾款后，系统需**自动将其加入衣橱**。

---

## 0. 结论先行

| 需求 | 本轮之前 | 本轮改动 |
|---|---|---|
| ① 预约期间两个选项 | 已实现（选择弹窗：加入心愿尾款 / 预约价全款预约） | 不动，只把「候选 + 默认选中 + 文案」的取数收敛到策略层 |
| ② 预约结束后两个选项 | 已实现（同上，默认改为全款） | 不动（尾款中同族，继续默认定金+尾款） |
| ③ **现货阶段仅全款、但两个价格口径** | ❌ **缺失**：只有「加入少女衣橱」一个入口，且直接走现货价，没有「按预约价全款」这条路 | ✅ 新增分支 `fullStockPaid` + 落库 `PriceMode.fullStock`；现货阶段改为弹选择弹窗，两个全款口径同屏 |
| ④ 定金+尾款入心愿尾款列表 → 付完尾款自动进衣橱 | 机制已存在（同一条 `Clothing`：`isFinalPaymentPlan` 决定进不进列表，`markFinalPaymentCompleted` 切成已拥有即进衣橱），但**无回归锁** | ✅ 补端到端单测钉死这条链路 |

一句话：**本轮真正新增的是「现货阶段的两个全款价格口径」；其余三条是把已有行为收敛到唯一口径并加回归锁。**

## 1. 阶段 → 分支矩阵（唯一口径：`ShopCatalogWardrobeEntryPolicy`）

| 购买阶段 | 候选（顺序 = 界面顺序） | 默认选中 | 生成心愿尾款任务 |
|---|---|---|---|
| 预约中 `reservationActive` | `depositPaid` / `fullPaid` | 定金+尾款 | 定金+尾款：**是**；全款：**否** |
| 预约已结束 `reservationEnded` | `depositPaid` / `fullPaid` | 预约价全款 | 同上 |
| 尾款中 `balancePending` | `depositPaid` / `fullPaid` | 定金+尾款（这一阶段的动作就是补尾款） | 同上 |
| **现货 `inStock`** | **`fullPaid` / `fullStockPaid`** | **按现货价全款**（无现货价才退回按预约价全款） | **两个都不生成** |
| 预约未开始 `reservationUpcoming` | `wishlist` | —— 不弹选择弹窗（加入心愿 = 开售提醒） | 是（全记待付） |

三条口径约束：

* **候选只给「取得到数」的口径**：`fullPaid` 要有预约价档案、`fullStockPaid` 要有现货价档案；缺档的那一项**不出现在列表里**（宁可不给，也不给一个点下去必然取不到价的按钮）。
* **`defaultChoiceOption` 的返回值同时是「要不要弹选择弹窗」的判据**：返回 nil = 该阶段没有可选项，视图走各自原路径（多选确认页 / 加入心愿）。**四个阶段（预约中 / 预约已结束 / 尾款中 / 现货）都不得静默默认一种付款方式直接落库。**
* **文案按阶段取**：现货阶段已经不存在「预约」这个动作，两个选项是**价格口径**而非付款方式，所以标题从「预约价全款预约」改为「**按预约价全款加入**」「**按现货价全款加入**」，段落标题也从「加入方式」改为「全款计价方式」。

## 3. 金额口径：用户依旧零输入

* 全部金额仍只从 `CatalogPriceArchive` 读：预约价 / 已付定金 / 待付尾款 / **现货价**。
* 待付尾款唯一算法仍是 `ShopCatalogWardrobeAmount.pendingBalance`（**读后台录入的尾款**，没录才回退「预约价 − 已付定金」），弹窗预览与落库共用。
* **两个全款口径的唯一差别 = 入橱金额取自哪份档案**（预约价 vs 现货价），其余完全一致：都记为 `isDepositPlan = true / deposit = 总额 / balance = 0` → 衣橱标签都是「全款」、`pendingFinalPaymentAmount == 0` → **都不生成任何心愿尾款任务**。
* 为了让事后能分辨「这一笔全款是按哪个价记的」，备注固定写「价格口径：全款 ¥X（按预约价/按现货价，已付清，不生成尾款任务）」。
* 现货价档案缺失时 `.fullStock` **返回 nil**（不静默记 0 元），由视图回退到多选确认页。

## 4. 定金+尾款 → 心愿尾款 → 付清自动进衣橱（需求 ④）

这条链路上**没有第二份数据**，全程是同一条 `Clothing` 记录的状态变化：

```
定金+尾款加入（PriceMode.reservation）
  → Clothing(isDepositPlan = true, deposit = 后台定金, balance = 后台尾款)
  → reservationKind == .depositPlan 且 !isFullPaymentReservation
  → isFinalPaymentPlan == true            ⇒ 出现在「心愿尾款」列表（DepositPlanView 的筛选口径）
  → 列表/详情页可发起「付尾款」（WealthSavingLedger.shouldShowFinalPaymentPayoffAction）
  → WealthSavingLedger.recordFinalPayment → markFinalPaymentCompleted
       （isDepositPlan = false、清 depositDate/finalPaymentDate、写一条 finalPayment 财富流水）
  → isFinalPaymentPlan == false           ⇒ 自动离开心愿尾款列表
  → reservationKind == .owned             ⇒ 自动成为衣橱里的「已拥有」
```

新增回归锁 `testDepositPlanEntersWishlistAndPayoffMovesToWardrobe` 把上面每一步都断言了一遍
（含「付清后不再显示付尾款入口」「成为衣橱资产后按完整裙装价计价」）。

## 6. 边界与未做

* 现货阶段改为弹选择弹窗后，商品详情页的**单品入库不再经过多选确认页**（`ShopCatalogWardrobeMergeView`）；多选确认页仍服务于系列点菜页 / 无价格档案的兜底路径，未改动。
* 「按预约价全款加入」只是**记账口径**（按当年的预约价记清），不校验用户是否真的在预约期买过——记账工具不为用户编事实，也不替用户设卡。
* 两个全款口径都记为「全款」标签，卡面不再区分价格来源；区分信息落在记录备注里（避免为一个次要维度再加一个标签）。
