## 一、定位：上新订阅 + 节点提醒，不是商品聚合

三坑（Lolita / JK / 汉服）的「上新」不是商品上架事件，而是 3-6 个月的时间线：

| 阶段 | 用户怕什么 | 主要阵地 |
|:--|:--|:--|
| 图透 | 错过种草 | 微博官博 |
| 开定金 | 抢不到 | 微博 + 淘宝 |
| 补尾款 | **忘记补款（最高频痛点）** | 店铺通知 |
| 出货 | 延期分批无感知 | 微博 + QQ 群 |
| 再贩 / 掉落 | 无预告突袭 | 超话 / 树洞 |

定位决定过审概率：Apple 4.2 会拒「单纯内容聚合器」，所以「上新 ↔ 衣橱匹配」「尾款节点 → 日历提醒」这些联动是**必要条件**，不是加分项。

## 三、双轨分发架构

### 3.1 采集在 Mac / 服务端，iOS 端零爬取

重申：iOS 端不做任何爬取，App 只读合规数据。这也绕开了反爬与合规问题。

### 3.2 双轨

```
Mac 定时跑 import_*.py（日牌，日级）
        ↓ 增量 diff → pending_updates.json
        ↓ 运营在 App 内 admin 入口一键导入
   ┌────┴────┐
CloudKit 公共库      Bundle catalog.json
全用户实时可见       离线兜底 + 未登录 iCloud 用户
   └────┬────┘
    客户端合并：云端优先，本地兜底
```

**为什么保留「运营一键导入」而不是脚本直接推 CloudKit**：

1. 脚本推 CloudKit 需要服务端认证（cktool / server-to-server key），复杂度高
2. 运营导入前可预览、可剔除——保留人工审核这个合规闸口
3. 日级节奏下，每天点一次完全够用

### 3.3 现状数据（2026-09-14 实测）

```
ItemManager/Resources/TimeHall/   318 MB
图片数量                            5328 张
catalog.json                       4.4 MB
内容实体    events 721 · commerceItems 308 · coordinates 150 · items 74 · stories 36
```

**Bundle 已到极限，新增内容一律走 CloudKit。** 后续反向优化：历史内容逐步迁到 CloudKit，Bundle 只留精选与首屏。

### 3.4 四个硬约束

| 约束 | 说明 | 应对 |
|:--|:--|:--|
| iCloud 登录 | Public DB 需登录 iCloud 才能读，未登录读不到 | Bundle 兜底（必需） |
| 时效性 | CloudKit 是同步服务不是推送系统；日级完全够用 | 已定日级，无需真后端 |
| UGC 触发 1.2 | 开放用户上传需举报/审核/封禁/联系入口四件套 | 本期只做 editorial，不触发 |
| 图片配额 | `CKAsset` 占 CloudKit 存储配额 | 日牌用官网外链；国牌运营传本地图 |

| 路径 | 范围 | 方式 |

## 五、数据模型

**复用 `TimeHallEntry`**，不新建 record type。新增字段：

| 字段 | 类型 | 说明 |

| `stage` | String | 图透 / 定金 / 尾款 / 出货 / 再贩 / 现货 |

## 六、实施步骤

### 第一步：加增量 diff（1-2 天）

给 `import_news_batch.py`（250 行）与 `import_commerce_batch.py`（393 行）加 diff：

- 跑完与 `catalog.json` 比对，输出 `pending_updates.json`（只含新增条目）
- 维护 `published_ids.json` 记录已发布 id，避免重复
- 沿用现有 `--dry-run` 习惯，diff 也先 dry-run

### 第二步：App 内 admin 上传入口（3-5 天）

- 复用 `NoticeCloudKitService` 的 `adminIDs` 白名单
- 两个能力：① 导入 `pending_updates.json` ② 手动录入国牌商品（标题/品牌/价格/定金/尾款/截止日/图片）
- 上传即 `sourceKind=editorial`，`status=published`
- **现成可复用**：`Views/Notice/NoticeAdminView.swift` 已是一套完整 App 内管理界面，`NoticeService` 已有 4 处 `isAdmin()` 门控；本期是扩品类，不是从零写 CMS

### 第二步附：运营白名单必须是「双层闸门」（关键）

复用 `adminIDs` 的思路成立，但**只做客户端一层是不够的**——它不是安全边界，只是 UI 开关。

**第 1 层（客户端，已有）**：`NoticeCloudKitService.adminIDs` 硬编码 `recordID.recordName`
（`_819804d902cb79c2d6e4bf736ed6c50b`），`isAdmin()` 为真才显示管理入口。

**第 2 层（服务端，当前缺失，必须补）**：CloudKit Console → Security Roles → 新建自定义角色，
把 `Notice` / `BrandFeedItem` 的 Create/Write **只给这个角色**，`_icloud` 与 `_world` 一律改为 Read-only。

⚠️ 现状问题：`docs/CloudKitDashboardSetup.md` 第 110-116 行给 `_icloud` 角色配的是
**Write ✅**，即「任何登录 iCloud 的人都可写记录」。对现有公告而言风险尚可接受；
但上新流要带商品跳转链接，一旦被注入钓鱼/劫持转链，影响面是全体用户，风险等级完全不同。

配套动作：

1. 运营用**专用 Apple ID**（不要共用个人号），登录后在 App 内跑一次 `getCurrentUserID()`，
   把输出的 recordName 记档；该 ID 与「Apple ID + 容器」绑定，换号即失效
2. 在 CloudKit Console 自定义角色里粘贴这些 recordName 作为成员
3. **Development 与 Production 两个环境的 Security Roles 要各配一次**，只配一个等于没配
4. 图片走 `CKAsset` 会吃容器存储配额，只传压缩后的封面图

**审核侧额外收益**：Apple 审核员的账号不在白名单里 → 完全看不到上传入口 → 不会触发 1.2 UGC 审查。
这是复用这套机制比自建网站更强的一点。

**可选优化（2-3 人团队可不做）**：`adminIDs` 硬编码意味着加减运营要发版。
若团队会扩，可改为 Public DB 存一条 `BrandFeedAdmin` 记录（World 可读、仅自定义角色可写），
App 启动时拉一次；但仍需保留一个硬编码 root 作冷启动引导。

### 第三步：客户端读取与合并（3-5 天）

- 时光馆新增「上新」分区，读 CloudKit published
- Bundle `catalog.json` 作离线兜底与首屏
- 未登录 iCloud 时降级为纯 Bundle，不白屏

### 第四步（可选）：联动

- `deadlineAt` → 日历提醒，解决「忘记补尾款」
- 上新 ↔ 衣橱匹配
