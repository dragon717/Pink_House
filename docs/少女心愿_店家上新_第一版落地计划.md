## 第一部分 定位与边界

### 1. 功能定位

「店家上新 / 历年系列」是少女心愿自己的 Lolita 店家商品档案库。

它负责：

- 查看店家当前上新；
- 查看店家往年系列；
- 查看系列下的商品；
- 查看商品图、配色、尺码、尺码表；
- 查看历史预约价与后续现货价；
- 将商品加入现有心愿；
- 将预约商品直接带入现有心愿尾款；
- 将已经拥有的商品直接写入现有少女衣橱；
- 将主裙 + KC + 袖套等多件商品合并成一个现有衣橱条目。

它**不提供购买链接、不做商城、不做支付、不做订单、不做物流。**

一句话定位（与《第一版落地方案》一致）：

> 不是商城，而是少女心愿自己的 Lolita 店家商品档案库。普通用户只看资料、加入心愿 / 少女衣橱；白名单运营负责补录与维护。

### 2. 必须遵守的产品边界

#### 2.1 不改变现有少女心愿 UI

必须沿用当前：

- 页面背景；
- 粉色 / 金色视觉体系；
- 卡片样式；
- 字体层级；
- 圆角；
- 顶部导航；
- 底部导航；
- 衣橱详情；
- 心愿尾款；
- 按钮与交互习惯。

禁止为店家上新重新设计整个 App。

#### 2.2 「时光馆」就是正式入口

现有底部导航：

```text
衣橱
心愿尾款
时光馆
我
```

其中「时光馆」就是本次功能正式入口。不新增新的 Bottom Tab。

#### 2.3 不提供用户购买入口

用户侧禁止出现：

```text
立即购买
去淘宝
前往店铺
购买链接
商品链接
支付
订单
物流
```

淘宝只作为运营录入资料的输入来源。

#### 2.4 明确不做清单

- 商城、支付、订单；
- 物流、已发货、已收货；
- 普通用户修改公共商品资料；
- 第一版开放 UGC 商品投稿；
- 淘宝解析结果自动发布。

## 第二部分 业务架构与数据模型

### 3. 总体结构

```text
                    时光馆
                      │
             店家上新 / 历年系列
                      │
                     Shop
                      │
                    Series
                      │
                    Product
                      │
       ┌──────────────┼──────────────┐
       │              │              │
    Variant        SizeChart      SaleEvent
                                    │
                          ┌─────────┴─────────┐
                          │                   │
                       预约记录             现货记录

────────────────────────────────────────

                  用户现有功能

                    Product
                       │
       ┌───────────────┼────────────────┐
       │               │                │
       ▼               ▼                ▼
      心愿          心愿尾款        少女衣橱
                       │
                    尾款完成
                       │
                       ▼
                   少女衣橱
```

核心分层（与《第一版落地方案》一致）：

- **公共 Catalog**：这件商品「是什么、什么时候卖过、多少钱」；
- **用户状态**：我「想要 / 已预约 / 已拥有」。

公共商品事实与用户私有状态分离，Catalog 与用户衣橱数据必须分层。

### 4. Catalog 数据模型

第一版至少：

```text
Shop
Series
Product
ProductVariant
SizeChart
SaleEvent
CatalogAsset
```

核心字段：

| 模型 | 核心字段 |
|---|---|
| Shop | id, name, aliases, logo, cover, description |
| Series | id, shopID, name, year, season, cover, description |
| Product | id, shopID, seriesID, name, category, images, description |
| ProductVariant | id, productID, color, size |
| SizeChart | productID, columns, rows, sourceImage |
| SaleEvent | id, productID, type, price, deposit, balance, startAt, endAt |
| CatalogAsset | id, type, thumbnailURL, previewURL, originalURL, width, height |

Series 与 Product 必须分开；商品名称不能作为稳定 ID。

现有用户模型不重写，只增加可选引用字段：

```text
Wishlist / TailPayment / Wardrobe
+ catalogProductID?
+ catalogVariantID?
+ saleEventID?
```

公共 Catalog 实体优先归档，不物理删除已被用户引用的数据。

### 5. CatalogAsset

图片资源不能只存缩略图。

```text
CatalogAsset

id
type

thumbnailURL
previewURL
originalURL

width
height
```

type：

```text
productImage
sizeChartImage
seriesCover
shopCover
```

必须保留 `originalURL`，用于保存原图。

### 6. 价格档案与 SaleEvent

价格属于商品历史，不是商城售价。预约价和现货价不是同一个字段的「新旧值」，而是同一商品的不同 SaleEvent。

**禁止 Product 只保存一个 price。**必须：

```text
Product
└── SaleEvent[]
```

类型至少：

```text
reservation（预约价）
stock（现货价）
rerelease（再贩）
```

预约结束后新增现货 SaleEvent，禁止覆盖旧预约价；全部历史保留。

示例：

```text
2026.09 首发预约
预约价 ¥428
定金 ¥100
尾款 ¥328

2026.11 现货
现货价 ¥568
```

SaleEvent 明细：

| 记录 | 类型 | 价格 | 时间 | 展示 |
|---|---|---|---|---|
| SaleEvent #1 | reservation | ¥428 | 2026.09 | 历史预约价 |
| SaleEvent #2 | stock | ¥568 | 2026.11 | 当前现货价 |
| SaleEvent #3 | rerelease | 可选 | 未来 | 后续自然扩展 |

用户页同时展示：

```text
历史预约价
¥428

当前现货价
¥568

现货比预约高
¥140（+32.7%）
```

## 第四部分 心愿与尾款联动

### 16. 加入心愿

商品详情：

```text
[加入心愿]
```

直接进入现有心愿系统。心愿代表「我想拥有」：从 Catalog 引用商品资料，用户只补自己的选择 / 备注。

自动带入：

```text
catalogProductID
catalogVariantID
商品名
品牌
系列
商品图
颜色
尺码
```

### 17. 我已经预约 → 心愿尾款

预约期间商品显示：

```text
[我已经预约]
```

进入现有心愿尾款。心愿尾款代表「我已经预约」：记录总价、定金、待付尾款、尾款时间与提醒。

自动带入：

- 商品；
- 颜色；
- 尺码；
- 预约总价；
- 定金；
- 待付尾款；
- 尾款时间。

记录预约页面要求：

- 商品、店家、系列自动带入；
- 颜色 / 尺码选择；
- 预约总价自动带入；
- 已付定金可修改；
- 待付尾款自动计算；
- 尾款时间可为「待公布」；
- 提醒时间可设置。

### 19. 少女衣橱正式模型

核心原则：

> 上新不是另一个衣橱，它只是现有少女衣橱的标准化数据入口。

```text

│
├── primaryItem
│
└── accessories[]
```


## 第五部分 运营端

### 26. 运营白名单与运营中心

普通用户完全看不到运营工具。

运营 / 创作者入口：

```text
设置
↓
运营工具
↓
店家商品库
```

运营身份：

```text
Catalog Editor
```

运营中心第一版展示：

```text
今日更新 / 草稿 / 待审核 / 待补充

[＋ 补录上新]
```

### 27. 运营录入方式

```text
＋ 补录上新
  ├─ 从淘宝内容导入（推荐）
  │     粘贴链接 / 分享文本 → 自动拆分 → 生成草稿
  └─ 手动录入
        从空白开始
```

### 28. 淘宝快捷导入

淘宝仅用于运营侧信息输入。支持：

```text
淘宝 URL
淘宝完整分享文本（优先推荐）
```

流程：

```text
复制
↓
少女心愿运营工具
↓
粘贴
↓
开始解析
↓
生成草稿
```

第一版尽量自动解析：

- 淘宝 URL / 商品标识；
- 店家名称候选；
- 商品标题；
- 系列名称候选；
- 商品类型；
- 商品图片（可访问时）；
- 颜色；
- 尺码；
- 预约价；
- 现货价；
- 定金；
- 尾款；
- 预约开始 / 结束时间。

尺码表第一版不强求自动 OCR：能拿到原图就先保存原图，结构化尺码由运营补录。

解析核心原则：

> 能拆多少拆多少，剩下人工补。

不能设计成「要么全成功，要么全失败」。

自动解析只生成 Draft：

```text
淘宝内容
↓
自动解析
↓
CatalogDraft
↓
运营确认
↓
发布
```

禁止自动解析后直接发布。自动解析是加速器，不是发布前置条件；手动录入始终可以完整完成全流程。

解析结果字段三态展示：

| UI 状态 | 含义 | 后续动作 |
|---|---|---|
| ✓ 已识别 | 高置信度字段 | 运营快速确认 |
| ? 请确认 | 自动识别但不确定 | 运营选择或修正 |
| 待补充 | 未识别 | 手工填写 |

### 29. 已有实体匹配与防重复

解析后依次匹配：

```text
Shop
↓
Series
↓
Product
```

避免重复创建：

- **已有店家匹配**：根据店家名 / aliases 匹配，避免同一个品牌重复创建；
- **已有系列匹配**：解析到「雪国来信 JSK」时，优先提示当前店家已有「雪国来信」系列；
- **已有商品匹配**：发现同名同系列商品时，优先打开已有 Product，而不是创建第二条。

现货快速补录：如果已有「雪国来信 JSK 预约 ¥428」，后续解析到「现货 ¥568」，应该提示：

```text
检测到已有商品

[新增现货价格记录]
```

生成新的：

```text
SaleEvent(type = stock)
```

而不是新建 Product。原预约 ¥428 继续保留。

```text
复制新现货淘宝内容
→ 识别「雪国来信 JSK」
→ 发现已有 Product
→ 本次识别现货 ¥568
→ [添加为现货记录]
→ 原预约 ¥428 继续保留
```

### 30. 手动录入兜底

即使淘宝完全解析失败，仍必须可以手动完成：

```text
店家
↓
系列
↓
商品
↓
图片
↓
颜色
↓
尺码
↓
尺码表
↓
预约价
↓
现货价
↓
保存
```

禁止把「无法完整抓取淘宝页面」设计成流程失败。部分解析成功（例如成功解析 7 项 + 缺失 3 项）时：

```text
显示「已整理出部分资料」
→ 继续手动补录
→ 保存草稿
```

### 31. 运营发布状态

```text
淘宝解析 / 手动录入
↓
draft（草稿）
↓
submitted（提交）
↓
reviewed（审核）
↓
published（发布）
```

以及：

```text
archived（归档）
```

原则：自动解析不能直接污染正式 Catalog。

### 34. 强制开发约束

以下约束由本计划与《第一版落地方案》的约束清单合并去重而成，两份文档共用同一编号：

1. 不改变少女心愿现有 UI。
2. 不新增店家上新 Bottom Tab；时光馆就是正式入口。
3. 不做商城、支付、订单、物流；不做发货 / 收货状态。
4. 不向用户暴露淘宝购买链接。
5. 不重新实现一套心愿、尾款、衣橱；不为新功能重写现有衣橱 / 心愿 / 尾款。
6. Series 与 Product 必须分开，不合并。
7. 预约价不能被现货价覆盖，全部保留历史。
8. Product 必须支持多个 SaleEvent。
9. 商品名称不能作为稳定 ID。
10. 公共 Catalog 实体优先归档，不物理删除已被用户引用的数据。
11. Catalog 与用户衣橱数据必须分层；上新只能作为现有衣橱的数据入口。
12. WardrobeEntry 必须有主衣物；小物不能与主衣物平级决定主类型；主衣物决定主类型。
13. 小物写入现有衣橱小物区域；价格信息支持小物明细。
14. 旧衣橱必须兼容。
15. 商品图和尺码图必须保留可保存原图。
16. 淘宝解析只能生成草稿，不自动发布。
17. 淘宝解析失败不能阻塞手动补录；手动录入始终可以完整完成全流程。
18. 淘宝快捷导入是效率工具，不是发布前置条件。
