# 图片与性能扩展方案

> 面向「图书馆式全量检索 + 图片量增长到十万级」的优化方案。
> 调研时间：2026-09-14 · 状态：**待用户拍板选型后实施**
> 关联：《品牌上新资讯_运营说明.md》《品牌上新资讯_开发规格.md》

---

# Part A · 给非技术的一页纸

## 三句话结论

1. **图片一张都不要装进 App，只装文字信息。** 图片全部放云端，用户看哪张下载哪张。
2. **用户手机上最多占用 500MB，超了自动清理最老的。** 所以图片涨到几十万张，用户手机占用也不会跟着涨。
3. **安装包要反过来变小**——从现在的 318MB 降到 50MB 以内。

## 为什么现在这样会出事

实测（2026-09-14）：

```
图片总数     5328 张
总大小       288.6 MB（整个 Bundle 318 MB）
平均单张     55 KB
最大单张     2325 KB   ← 2.3 MB，列表里出现几张就卡
```

### 更正：你们已经有一套自己的图片管理机制

上一版我判断错了。项目里确实有自己写的图片缓存系统，
包含**内存缓存、磁盘缓存、大图自动缩小**这几个关键能力，做得是到位的。

但它有个边界：这套机制是围绕「本地文件」设计的。
它现在的远程能力走的是 **iCloud 文件同步**——那是**每个用户自己的私有空间**，
适合「用户自己的衣橱照片在自己几台设备间同步」，
**不适合「让所有用户看同一张品牌上新图」**。

所以要让所有人看到同一批图，图得放进 **CloudKit 公共库**。
而我们现有的缓存机制**不用推翻**，只需要在前面补一步「把云端的图取回本地」，
之后的缓存、缩略图、自动清理全部复用现成的。

## 分层存储

| 层 | 放什么 | 容量 | 会不会涨 |
|:--|:--|:--|:--|
| 设备内存 | 当前屏幕这几张 | ≤ 100 MB | 不会 |
| 设备磁盘缓存 | 最近看过的图 | ≤ 500 MB，可一键清除 | 不会（有上限） |
| App 安装包 | 首屏精选缩略图 | 固定 30-50 MB | **永不增长** |
| 云端 CDN | 全部几十万张 | 无限 | 会涨，但不在用户手机上 |

## 大概花多少钱

按 **10 万张图**估算（存储约 40GB）：

- 对象存储：约 ¥5/月
- CDN 流量：取决于访问量，初期每月几十元
- **远低于现在 318MB 安装包带来的下载转化率损失**

## 需要你拍板的一件事

**图片放哪里？**（技术上讲，两种都可行，只是取舍不同）

| | 放苹果 CloudKit | 放云存储 + CDN |
|:--|:--|:--|
| 省事程度 | ✅ 现成，零额外接入 | 需要申请一个云存储 |
| 容量 | 占苹果给的容器配额 | 按量付费，几乎无限 |
| 自动生成缩略图 | ❌ 没有这功能 | ✅ 有，能省一大半存储和存储费 |
| 以后换方案 | — | 只要 URL 没写死，切换无痛 |

**我的建议**：第一期图少可以先用苹果 CloudKit 顶着，但**图片地址必须设计成可配置的**，
这样将来切换只要改一个配置，不用改代码、不用重新传图。

# Part B · 技术规格（Agent 执行版）

## 1. 现状实测数据

```
ItemManager/Resources/TimeHall/
  图片 5328 张 · 288.6 MB · 平均 55 KB · 最大 2325 KB
  catalog.json 4.4 MB
  实体：events 721 · commerceItems 308 · coordinates 150 · items 74 · stories 36
Bundle 总计 318 MB
SPM 依赖：仅 generative-ai-swift（无 Kingfisher / SDWebImage / Nuke）
```

### 自研图片体系盘点（2026-09-14 复核，修正初版误判）

| 组件 | 能力 |
|:--|:--|
| `ItemManager/ImageManager.swift` | 内存缓存（按机型自适应 40-300 MB，:111-142）+ 磁盘缓存目录 + 单图上限保护（:163） |
| `Services/OptimizedImageLoader.swift` | `actor` 异步加载器 + NSCache |
| `Components/AsyncDownsampledImage.swift` | 降采样加载（大图正确的处理方式） |
| `Services/TimeHall/TimeHallCatalogStore.swift:59` | 时光馆独立缓存：96 张 / 80 MB |

**结论：不引入 Kingfisher，扩展 `ImageManager`。**

### 能力边界（这才是真问题）

体系基于**本地文件名**：`cachedImage(fileName:targetSize:)`。
唯一的远程路径 `downloadFileIfNeeded()`（:290）调用的是
`FileManager.startDownloadingUbiquitousItem` —— **iCloud Documents 文件同步**。

**iCloud Documents 是每用户私有空间，不能公共分发。**
它适合同步用户自己的衣橱照片，不适合让所有用户看同一张品牌上新图。

→ 公共分发走 CloudKit Public DB + `CKAsset`；
`ImageManager` 只需补一段「云端资源落地到本地缓存目录」的前置，
后续缓存 / 降采样 / 淘汰全部复用。

### 三个硬伤

1. `ImageManager` 无 HTTP URL 加载路径 → 无法直接消费 CDN / CKAsset
2. `save_image()` 直存原图，单图最大 2.3 MB
3. Bundle 318 MB，已逼近蜂窝下载与转化率红线

## 2. 六层优化

### L1 · 图片格式与尺寸

- **格式统一 WebP**（q80）。不用 HEIC 的原因：项目存在 `android/` 与 `harmony_next/`，
  多端场景下 WebP 兼容性最好；iOS 端由图片库内置解码，不依赖系统 ImageIO
- **三档尺寸**（或见 L5 用云端实时处理替代预生成）：

  | 档位 | 长边 | 用途 | 目标体积 |
  |:--|:--|:--|:--|
  | `thumb` | 480px | 列表、网格 | ≤ 25 KB |
  | `medium` | 800px | 详情页 | ≤ 100 KB |
  | `full` | 1600px | 点开大图 | ≤ 400 KB |

- **列表页永远只加载 `thumb`** —— 这一条解决 80% 的滚动卡顿
- 复用现有 `tools/time_hall/optimize_images.py`，补 WebP 输出与三档生成

### L2 · 扩展 `ImageManager` 支持远程资源（不是引入第三方库）

~~引入 Kingfisher~~（初版误判，项目已有自研体系，见第 1 节）。

需要补的是**一条「远程 → 本地落地」的通道**，而不是替换缓存层：

```
CloudKit CKAsset（或 CDN URL）
        ↓  新增：RemoteAssetStore
   落到 ImageManager 的磁盘缓存目录，文件名 = 图片稳定 id
        ↓  完全复用
   ImageManager 内存缓存 / 降采样 / 淘汰
```

`RemoteAssetStore` 职责：

- 入参：图片稳定 id（**不是 URL**）
- 命中本地缓存目录 → 直接返回，走原有 `cachedImage(fileName:)`
- 未命中 → 取云端资源 → 写入缓存目录 → 再走原有路径
- 下载失败降级：占位图，不阻塞列表
- 配合 `AsyncDownsampledImage` 做降采样，避免 2.3 MB 大图直出

必须启用/补齐：

- 磁盘缓存**总大小上限 + LRU**（现有实现未见显式上限，是主要缺口）
- 收到 `didReceiveMemoryWarning` 时清空内存缓存（现有 `ImageManager` 已按机型自适应）
- 设置页「清除缓存」入口（复用现有清理逻辑）

### L3 · 缓存策略

- 磁盘缓存**必须有上限**，否则 App 体积随时间无限膨胀，最终被用户卸载
- 设置页提供「清除缓存」入口，显示当前占用
- 缓存 key 用**图片稳定 id**，不要用 URL（URL 会因 CDN 迁移、参数变化而失效，
  导致缓存全 miss）

### L4 · 列表与查询性能（容易被忽略的卡顿源）

几万条的卡顿，常常不是图片，而是**全量加载与内存过滤**：

- SwiftUI 用 `LazyVStack`，**不要用 `VStack`**
- SwiftData 的 `@Query` 不分页会**全量加载**，几万条直接卡死。
  改用 `FetchDescriptor` + `fetchLimit` / `fetchOffset` 分页（每页 20-30 条）
- 索引：给 `brandID` / `year` / `series` / `stage` 加 `#Index`（图书馆检索必需）
- 搜索走索引查询，**禁止内存 `filter`**
- 列表只 fetch 展示所需字段，详情再取完整对象
- iPhone 上列表 id 必须稳定，避免 `.id()` 无谓变更触发重绘

### L5 · 分发：Bundle 反向瘦身

- Bundle 只保留「首屏精选」：最近 50 条 + 每品牌 1 张代表图，目标 **30-50 MB**
- 存量 5328 张批量转 WebP + 生成三档，288 MB → 约 60 MB（thumb + medium）
- 其余全部迁云端，按需加载

### L6 · 上传侧（运营传图）

- 运营上传前强制压缩：长边 ≤ 1600、WebP q82
- 国牌图不要存淘宝外链（防盗链），传本地图
- 采集脚本 `save_image()` 同步改造，不再直存原图

## 3 · 图片上云：CloudKit Public DB 实操

### 3.1 先分清苹果的两朵云

| | iCloud Documents | CloudKit Public DB |
|:--|:--|:--|
| 本质 | 文件同步 | 结构化数据库 |
| 可见范围 | **每个用户私有** | **所有用户共享** |
| 项目现状 | `ImageManager.downloadFileIfNeeded()` 已用 | `NoticeCloudKitService` 已用 |
| 适合 | 用户自己的衣橱照片跨设备同步 | 品牌上新图（所有人看同一张） |

**品牌上新图必须走 CloudKit Public DB，没有替代方案。**

### 3.2 上传三条路

| 方式 | 适用 | 工具 |
|:--|:--|:--|
| App 内 admin 上传 | 国牌手动录入、日常增量（每天几条） | `CKAsset(fileURL:)`，复用 `NoticeAdminView` |
| **Mac 脚本批量导入** | 存量 5328 张 + 日牌批量 | `cktool`（Xcode 自带 CLI）或 CloudKit Web Services |
| CloudKit Console 手点 | 仅调试 | 不用于生产 |

**存量迁移只能走脚本**——5328 张图不可能在 App 里点完。
`cktool` 需要 CloudKit Management Token（CloudKit Console 生成），支持 `save-records` 批量导入。

### 3.3 ⚠️ 最大的坑：CKAsset 没有可预测的公开 URL

- 不能像对象存储那样在 `catalog.json` 里存 `https://…/xxx.webp` 直接丢给图片库
- 客户端必须：查询 `CKRecord` → 取 `CKAsset` → 拿到已下载的本地文件
- CloudKit Web Services 返回的 `downloadURL` 是**带签名的临时地址，会过期**

**这直接决定缓存设计**：

- 缓存 key 绝不能用 URL（本来就变，这里更是每次都变）
- 必须用**图片稳定 id**（如 `assetID` + 档位），落地到本地缓存目录后按文件名寻址
- 正好与 L2 的 `RemoteAssetStore` 一致 —— 这就是为什么「云端资源 → 本地文件名」这层抽象是必需的

### 3.4 落地步骤

1. CloudKit Console 建 `TimeHallAsset` 记录类型（或直接在 `TimeHallEntry` 上加 asset 字段）
   - 字段：`assetID`（String，Queryable）、`variant`（String：thumb/medium/full）、`file`（Asset）
2. Console 确认容器存储配额（会显示当前用量与上限）
3. 生成 Management Token → 用 `cktool` 写批量导入脚本，存量图压缩后导入
4. 客户端 `RemoteAssetStore`：按 `assetID + variant` 查记录 → 取 asset → 落盘 → 交 `ImageManager`
5. App 内 admin 入口支持单图上传（国牌）

### 3.5 配额与成本

- 存储计入 CloudKit 容器配额，**随 App 活跃用户数增长**（具体额度在 CloudKit Console 查看）
- 只传压缩后的 thumb + medium，不传 full，可省一大半
- 若将来配额吃紧或需要实时缩略图，按第 4 节切对象存储（URL 可配置则无痛）

## 4. 图片存储选型（决策点）

| 维度 | CloudKit `CKAsset` | 对象存储 + CDN |
|:--|:--|:--|
| 元数据 | ✅ 现成，零成本 | 需另建 |
| 配额 | 占容器配额 | 按量付费，几乎无限 |
| CDN | 有，不可控 | 可选，可控 |
| 图片处理（实时缩放/转格式） | ❌ 无 | ✅ URL 参数实时出图 |
| 10 万张（~40GB）成本 | 吃容器配额 | ~¥5/月存储 + 流量 |
| 迁移成本 | — | URL 可配置则无痛 |

**关键优化点**：对象存储支持 `?imageMogr2/thumbnail/…`（腾讯云 COS）或
`?x-oss-process=image/resize,w_480/format,webp`（阿里云 OSS）**实时出图**。
这意味着**只需存一张原图**，展示时用 URL 参数要任意尺寸 —— 省掉预生成三档的存储与管理成本。

**推荐路径**：

1. 第一期（图 < 5000 张）：图走 `CKAsset`，零接入成本
2. **但 URL 一律走可配置的 `imageBaseURL`**，不写死域名
3. 图量上来或需要缩略图能力时，切对象存储，只改配置

## 5. 现在必须做对的 5 件事（防止推倒重来）

这 5 条如果现在不做，以后改是伤筋动骨的：

1. **图片 URL 可配置** —— 存 `imageBaseURL` 配置项，不写死域名
2. **元数据与图片彻底分离** —— `catalog.json` 只存 URL，不存图
3. **列表第一天就分页** —— UI 层分页是后期改动最痛的一环
4. **磁盘缓存设上限 + 清除入口** —— 不做就只能靠用户删 App
5. **每张图有稳定唯一 id 作缓存 key** —— 不用 URL 当 key

## 6. 验收指标（可量化）

| 指标 | 目标 |
|:--|:--|
| App 安装包 | < 100 MB（目标 50 MB） |
| 冷启动 | < 2 s |
| 列表滚动帧率 | ≥ 55 FPS（Instruments 实测） |
| 首屏图片出图 | < 1 s |
| 内存峰值 | < 300 MB |
| 磁盘缓存 | ≤ 500 MB，超限 LRU 淘汰 |
| 10 万条数据检索 | 单次查询 < 300 ms |

## 7. 实施顺序

| 阶段 | 内容 | 依赖 |
|:--|:--|:--|
| **P0** | 图片上云：CloudKit `TimeHallAsset` schema + `cktool` 批量导入存量压缩图 | Management Token |
| P0.5 | `RemoteAssetStore`：按 `assetID + variant` 取回并落盘，交 `ImageManager` | P0 |
| P1 | 磁盘缓存补总大小上限 + LRU + 清除入口（现有实现缺上限，是主要缺口） | P0.5 |
| P2 | 存量图批量转 WebP + 三档，Bundle 瘦身 318 MB → 50 MB | `optimize_images.py` |
| P3 | 列表分页 + SwiftData 索引（图书馆检索） | 检索设计定稿 |
| P4 | 上传侧压缩（运营 + 采集脚本 `save_image`） | P2 |
| P5 | 图片迁对象存储 + CDN（按需，图量上来再做） | URL 可配置（第 5 节第 1 条） |

**P0 / P0.5 是地基**：不先把「图片上云 + 取回落地」跑通，后续所有优化都没有落点。
P1 的磁盘缓存上限是**现有代码唯一的实质缺口**，必须补。
