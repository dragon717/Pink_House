## 一、结论先说

| # | 位置 | 遮挡现象 | 根因 | 修法 |
|---|---|---|---|---|
| 1 | 商品详情（截图 1）：轮播左下「颜色胶囊」+ 底部「分页胶囊」 | 颜色胶囊**整个半埋进信息卡顶边**并压到标题首行；分页胶囊横跨卡片顶边 | 卡片靠 `.offset(y: -36)` 上提覆盖图片下沿，而两个标注是轮播 ZStack 的**底对齐**浮层 → 落进同一条覆盖带；且两者底部留白不一致（胶囊 0、分页 12），本身也没对齐 | 抽出常量 `cardLiftOverCarousel` / `cardStackSpacing`，两个标注共用 `carouselOverlayBottomInset = 36 − 16 + 12 = 32`，整体抬到卡片顶边之上 |
| 2 | 系列商品管理（截图 2）：最后一行「毛绒拉夫领针织内搭」 | 被底部悬浮 Dock 完全盖住、点不到 | 该页 `List` **完全没有为 Dock 预留底部空间** | 统一走新增修饰器 `avoidingBottomDock()` |
| 3 | **同类问题共覆盖 35 处落点 / 28 个文件**（见第四节清单；`Group` 上挂一处可覆盖多个 List，故落点数 > 页面数） | 滚动内容最后一个元素被 Dock 盖住 | 同一个根因：Dock 是覆盖层，不参与安全区；各页面要么没预留、要么预留量在 iOS 26+ 被判定为 0 | 全部改为唯一修饰器 `avoidingBottomDock()` |

**为什么会大面积中招（真正的根因）**：`MainTabView` 的底部导航 Dock（`customTabBar`）放在 `body` 的 `ZStack` 里叠在 `contentView` **之上**，**不是**系统 `TabBar`、**不参与安全区计算**。因此「为 Dock 留出底部空间」是每个可滚动页面自己的责任。而工程里有两份重复实现：

```swift
/// ItemManager/Views/Settings/Components/AdaptiveSettingsComponents.swift（旧）
/// ItemManager/Views/Wealth/WealthView.swift（旧）
private func legacyCustomTabBarAvoidanceInset(safeAreaBottom: CGFloat) -> CGFloat {
    if #available(iOS 26.0, *) { return 0 }   // ← iOS 26+ 直接不给空间
    ...
}
```

本 App 自己画 Dock，iOS 26+ 不会有系统组件替我们留空间 —— 于是**所有走 `AdaptiveSettingsView` 的设置页 + 「安财」页在新系统上底部预留恒为 0**，最后一行被 Dock 吞掉。这是这次最大的一片「同类遮挡」。

## 二、唯一口径（本次建立的机制）

新增 `ItemManager/Views/Components/BottomDockAvoidance.swift`：

```swift
extension View {
    /// 让滚动内容为底部悬浮 Dock 让出空间，保证最后一个元素完整可见、可点。
    func avoidingBottomDock() -> some View { modifier(BottomDockAvoidanceModifier()) }
}
```

- 预留高度**只有一处定义**：`LegacyCustomTabBarLayout.floatingSurfaceBottomInset` = `56`(Dock 高) + `max(2, 4)`(贴底) + `12`(视觉间隙) = **72**（注意取的是 `max`，不是 `bottomSpacingWithSafeArea` 的 2），由 `MainTabView` 通过 `\.customBottomNavigationAvoidanceInset` 下发。页面**不写数字**、**不判断系统版本**。
- 在 tab 之外（`.sheet` / `.fullScreenCover`）环境值退化为 0，误加也不会产生留白。
- 使用边界（写在文件头注释里）：
  - 只用于 **tab 根页面** 与 **在 tab 内 push 的页面**；模态页浮在 Dock 之上，不需要。
  - 页面若自带贴底常驻操作条（如 `ShopCatalogSeriesMenuView` 的 `safeAreaInset` 选择条），两者叠加会双倍留白 —— 二选一。
  - 尾部已有 `padding(.bottom, N)`（N ≥ 70）的页面不要重复添加（`WardrobeView` 100 / `DepositPlanView` 100 / `ClothingDetailView` 80 / `ThemeSkinStoreView` 126 保持原样）。

**Dock 几何（实测 + 代码双向确认）**：Dock 胶囊占 `[屏高 − 92, 屏高 − 36]`（iPhone 18 Pro：屏高 874、底部安全区 34）。预留 70 后内容底边落在 `屏高 − 104`，比 Dock 顶边高 12pt。截图实测胶囊顶边 782pt ≈ `874 − 92` ✓。

## 三、截图 1 的几何推导（为什么必须抬 32pt）

修复前（`ShopCatalogProductView`）：

| 元素 | 相对轮播底边的位置 |
|---|---|
| 轮播底边 | 0（基准） |
| 信息卡顶边 | `−卡` 上提 36 − 卡片间距 16 = **−20**（在轮播底边之上） |
| 颜色胶囊（只有 `.padding(.leading, 12)`） | **0 → −21**（完全落进覆盖带） |
| 分页胶囊（`.padding(.bottom, 12)`） | −12 → −33（跨在卡片顶边上） |
| 标题首行（卡内 16pt padding） | 卡片顶边 + 16 = **−4** |

截图 1 实测：轮播底边 459pt、卡片顶边 439pt（= 459 − 20 ✓）、颜色胶囊 438.3 → 457.2pt。三者完全吻合 —— 颜色胶囊底边（457.2）已经越过标题首行顶边（455），所以看起来「胶囊压在标题上」。

修复后：两个标注底边 = 轮播底边 − 32，比卡片顶边高 **12pt**，整体落在图片区内。

### 6.5 未完成项：模拟器端到端验收（原因 / 复跑）

**现象**：`xcodebuild` 的 **test 动作**（`test` 与 `test-without-building`、以及
`-xctestrun` 直跑三种形式）都在 **`Resolved source packages` 之后完全静止**：
日志不再增长、`build/DerivedData` 无任何新产物、模拟器里也从未出现 App 进程。
**但这不是代码错误** —— 同一次改动 `build-for-testing` 干净通过（0 error）。

**根因（已定位）**：本机 **swap 总量 7168 MB、已用 6305 MB、仅剩 863 MB**。
- `xcodebuild test` 会触发 `PruneExplicitPrecompiledModules`，清掉显式模块缓存 →
  441 个 Swift 文件**整模块全量重编**（单个 `SwiftEmitModule` 进程要数 GB）→
  swap 打满后**静默卡死**（进程还在、日志与产物双双冻结，看起来只是「慢」）。
- 期间连普通 shell 命令都开始报 `resource temporarily unavailable: /dev/null`。

**已确认无关**：`testmanagerd`（宿主 + 模拟器运行时）两个进程都在跑、`.xctestrun` 存在、
模拟器 `Booted`、`simctl install` 可用、无第二个 `xcodebuild` 抢同一台 UDID。

**复跑建议（省内存顺序，已写进 `RULES.md`）**：

```bash
xcrun simctl shutdown all                      # 1. 先关模拟器（它自己吃 2–4G）
xcodebuild … build-for-testing                 # 2. 只编译，此时不要开模拟器
xcrun simctl boot <UDID> && xcrun simctl bootstatus <UDID> -b
python3 /tmp/inject_seed.py <…>/ItemManager.app # 3. 编完再注入种子
xcodebuild … -only-testing:ItemManagerTests/BottomDockAvoidanceTests \
             -only-testing:ItemManagerUITests/BottomDockOcclusionUITests \
             test-without-building              # 4. 只跑，不重编
```

判「卡死」的判据（避免误杀）：`wc -c <log>` 与 `find build/DerivedData -newermt` **双双静止
5 分钟以上**才算挂；只看时间长会误杀正常的 Prune 静默期。
