# 补录表单改造：款式（SPU）+ 多颜色（SKU）一体化录入（2026-09-23）

针对反馈：

> 「现在的表单结构不够合理，请实现在当前页面内添加多颜色 SKU 的功能。不需要让用户通过
> 『新建单品』来建颜色。把 designName（款式名）和多个 product（颜色）的录入整合在同一个
> 表单里，让公共资料实现跨颜色复用，图片单独上传。」
>
> 「请在颜色 SKU 添加区，将图片上传组件与颜色字段直接绑定。让用户点颜色的同时就能直接传图，
> 实现图片与 SKU 的强关联。不要单独弄一个图片上传区让用户去对应，太麻烦了。
> 前端详情页切换颜色时，直接读这个对应绑定好的图。」

---

## 一、结论先行

上一轮（需求 J）解决的是「**已经录成多条**之后怎么把公共资料补过去」——分组 + 一键同步。
这一次解决的是**更上游**的问题：**根本不该让用户录成多条**。

所以本次没有再加一个同步按钮，而是把「补录草稿」表单本身从

```
一条草稿 = 一个颜色（公共资料要重填 N 次，图片另开一个文本区自己对应）
```

改成

```
一个表单 = 一个款式 + N 个颜色行（公共资料填一次；每色的图片就在它自己那一行里上传）
```

同步（`syncStyleInfo`）仍然保留，用于「确实分开录了」的历史数据 —— 两条链路互补，不互相替代。

---

## 二、表单结构（改造后）

| 区块 | 内容 | 层级 |
| --- | --- | --- |
| 商品（款式） | 款式名、分类 | 款式层 |
| 款式公共资料（同款共用，只需填一次） | 面料成分、款式描述、尺码表（列 / 行 / 单位 / 原图） | 款式层 |
| 价格（同款同价，按款式录一次） | 预约价、定金、尾款、现货价、币种 | 款式层 |
| **颜色（N 色，每色传图 + 勾尺码）** | **每行**：颜色名 · 配色图（行内缩略图 / 传图 / 删图）· 尺码勾选 · 「将发布为：X」预览 | 颜色层 |
| 店家 / 系列 | 归属 | 批次归属 |

**移除**的两处旧结构：

- 「颜色差异资料」里的**多行图片文本区**和**配色尺码文本区** —— 被颜色行取代；
- 「同款其他颜色 → 复制到同款其他 N 个颜色」 —— 表单里已经能直接管全部颜色，留着是第二个入口。

---

## 三、图片与 SKU 的强关联（需求第二条）

颜色行内的图片组件（`ShopCatalogColorImageRow`）绑定的是**该颜色行自己的引用数组**，
而不是一整块多行文本：

```
[缩略图 1 ×] [缩略图 2 ×] [＋ 传配色图]
```

- 传完的图**直接就是这一色的配色图**，不需要用户再去别处把文件名抄一遍；
- 第一张标「主图」；
- 已发布 / 已归档的颜色行只读，不给改图入口（改草稿不影响线上，改了会让人以为生效了）。

保存后这条链是：

```
颜色行 imageRefs
  → 草稿 draft.images（CatalogAsset，id = asset-<草稿id前8位>-<序号>）
  → 每个 variant.imageAssetID 指向本颜色主图
  → 发布后落到商品 images / variants
  → 前端详情页（ShopCatalogProductDetailView）
```

前端详情页切色时读的就是这条链：轮播 slide 取**本商品** images（= 当前所选颜色的图），
后面再追加同款其他颜色的主图，slide 上带颜色标注。所以「切到哪个颜色就看到哪张图」
是数据本身决定的，不依赖运营把文件名对齐。

## 四、关键口径

1. **商品名 = 颜色名 + 款式名**，由表单自动组合并在每行显示「将发布为：…」。
   存量草稿的商品名本来就是「颜色 + 款式」的形式，派生款名再组合回去得到原值 ——
   **打开一次表单不会改名**（幂等，有测试锁死）。

2. **款式名一处决议**（`ShopCatalogDraftStyleForm.resolveStyleName`）：显式填写优先，
   否则按源草稿派生，再交给**所有**颜色共用。
   绝不能让每条草稿各自派生 —— 新加的颜色草稿商品名还空着，派生结果是空款名 →
   商品名退化成只有颜色词 → 「在这个表单里加一个颜色」反而变成两个款式。
   这是本次最容易出的坑，有专门回归测试。

3. **多颜色必须填款式名**：款式名是「同款共用一份公共资料」的归属键。单色允许留空
   （沿用「按名称自动识别」的旧行为）。

4. **价格整组写入**：预约价 / 现货价 / 定金 / 尾款 / 币种一起搬，
   避免出现「预约价 498、定金还是 0」这种发布时被对账拦下的草稿。

5. **尺码表 id 逐条重编**为 `sizechart-draft-<草稿 id 前 6 位>`：
   多条草稿共用同一 id 会在发布时互相覆盖（发布按 id 落覆盖层），最后一个颜色赢家通吃。

6. **移除颜色 = 删除它的未发布草稿**。与「删批次不连带删草稿」不矛盾：
   批次只是归组记录，而颜色行**就是**这份草稿本身，删掉它是用户的明确意图，
   留着会变成草稿箱里的孤儿。已发布的草稿保留（那是发布回执），只计入「跳过已上线」。

7. **一次落盘**：新增 / 更新 / 移除三种去向在同一次 `persist` 里完成，要么全成功、
   要么磁盘上一条都没变。

8. **同款家族口径唯一**（`ShopCatalogDraftStyleForm.sameStyleFamily`）：
   表单展示的范围与仓库落盘的范围必须同源。若两处口径不一致，
   「表单没显示、仓库却认为该移除」的草稿会被当成「用户删掉了这个颜色」而**误删**。
   原先私有的 `syncStyleIdentity` / `isSameStyleForSync` 已删除，只留这一份。

## 六、明确没做的事

- **没有**引入「款式草稿挂 N 个颜色草稿」的新实体。同款不同色发布后本来就是 N 个独立商品
  （要能单独加购、单独进心愿），再引入一层等于给同一份事实造第二个真相来源。
  本次用「一个表单管 N 条颜色草稿」拿到同样的录入体验。
- **没有**动前端详情页：切色读图本来就是按数据走的，本次只是保证录入端把图正确地
  绑到颜色上（`variant.imageAssetID` → 主图）。
