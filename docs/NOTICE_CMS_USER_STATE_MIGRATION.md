# 公告用户状态迁移设计（B2）

> 更新时间：2026-04-06  
> 对应任务：`NOTICE_CMS_DEV_TASKS.md` 中 B2  
> 用途：定义现有“已展示/已读”逻辑如何迁移为新公告用户状态模型，保证升级后不出现大面积误判未读或重复提示。

## 1. 目标

把当前偏“是否展示过”的状态体系，升级为可表达以下语义的用户状态模型：

- `unseen`
- `read`
- `acknowledged`
- `dismissed`

同时保留现有跨设备同步能力。

---

## 2. 现状概况

当前用户状态能力主要包括：

- 本地 `UserDefaults` 缓存已读 key
- `CloudKit Private Database` 同步已读状态
- 兼容 `readTrackingKey` 和部分 legacy key
- 用“是否已展示过”决定是否再次弹窗

当前问题：

1. “已展示”与“已读”混在一起
2. “已读”与“已确认”无法区分
3. “关闭弹窗”与“真正看过内容”无法区分
4. 弹窗展示次数没有完整模型化

---

## 3. 新状态模型定义

| 状态 | 含义 |
|---|---|
| `unseen` | 从未在任何正式入口看到过 |
| `read` | 已查看过内容，但未确认 |
| `acknowledged` | 已执行显式确认 |
| `dismissed` | 关闭过前台提示，但不保证阅读详情 |

---

## 4. 旧状态到新状态映射

### 4.1 旧已读记录

若旧系统中命中以下任意一种 key：

- `readTrackingKey`
- `legacyReadTrackingKeys`
- 旧 `noticeID`
- 旧 `recordName`

则新系统默认映射为：

- `state = read`

原因：

- 旧系统无法可靠区分“已确认”
- 旧系统也无法可靠区分“仅弹过未读”
- `read` 是最保守且最安全的中间态

### 4.2 旧未命中记录

若旧系统中不存在任何已读痕迹，则映射为：

- `state = unseen`

### 4.3 旧重置记录

若旧系统存在“重置已读历史”记录，则：

- 重置时间之后的公告重新视为 `unseen`
- 重置时间之前命中的旧 key 不继续生效

---

## 5. 迁移字段映射

| 旧信息 | 新字段 | 映射规则 |
|---|---|---|
| 已读 key 集合 | `noticeID` | 用稳定标识回填 |
| 已读行为 | `state` | 映射为 `read` |
| 已读时间 | `readAt` | 若旧记录可取到，则迁移；否则可空 |
| 弹窗已出现 | `presentationCount` | 若无法可靠取值，默认 `1` 或 `0`，依实现方式决定 |
| 最近提示时间 | `lastPresentedAt` | 若旧数据无记录，可空 |

---

## 6. 稳定标识策略

用户状态必须优先使用稳定公告标识，推荐顺序：

1. `recordName`
2. `id`
3. 兼容 legacy key 作为历史辅助

规则：

- 新状态系统不再长期依赖多种松散 key 混用
- legacy key 仅作为迁移兼容，不作为新系统长期主键

---

## 7. 迁移后交互规则

### 公告中心查看

- 用户打开公告详情时：
  - `unseen -> read`
  - `dismissed -> read`

### 确认公告

- 用户点击“我已知晓”时：
  - `read -> acknowledged`
  - `dismissed -> acknowledged`

### 前台提示关闭

- 用户关闭 `banner/modal`，但未进入详情时：
  - `unseen -> dismissed`

---

## 8. 提示逻辑与状态关系

| 状态 | banner | modal | inbox |
|---|---|---|---|
| `unseen` | 可显示 | 可显示 | 显示 |
| `read` | 默认不再显示 | 默认不再显示 | 显示 |
| `acknowledged` | 不显示 | 不显示 | 显示 |
| `dismissed` | 按规则可不再显示 | 不再显示 | 显示 |

---

## 9. 重复提示控制

迁移后必须保证：

1. 旧已读公告不因升级重新弹出 `modal`
2. 旧已读公告不因 key 变化全部重新变未读
3. 旧重置行为继续有效

---

## 10. 跨设备同步要求

迁移后的用户状态仍应：

- 存于 `CloudKit Private Database`
- 本地可缓存
- 换设备可恢复
- 网络不可用时本地先兜底

---

## 11. 迁移实施建议

1. 保留旧 key 识别逻辑一段时间
2. 首次迁移时批量将旧已读记录写入新状态模型
3. 新状态模型稳定后，再逐步缩减对 legacy key 的依赖

---

## 12. 验收标准

- 用户升级后不会看到大量旧公告重新变未读
- 旧已读用户不会被重复 `modal` 打断
- 确认型公告能独立进入 `acknowledged`
- 关闭提示但未读详情的用户可被识别为 `dismissed`

---

## 13. 冻结结论

本迁移方案冻结以下共识：

1. 旧“已读/已展示”统一先映射为 `read`。
2. `acknowledged` 是新系统新增能力，不从旧数据臆测。
3. 迁移优先保证“不重复打扰用户”，而不是“绝对精确恢复每个动作细节”。
