## 4. 数据模型

### 4.1 CloudKit：复用 `TimeHallEntry`，不新建 record type

新增字段（类型按 CloudKit 惯例）：

| 字段 | CloudKit 类型 | 索引 | 说明 |
|:--|:--|:--|:--|
| `stage` | String | Queryable | 图透 / 定金 / 尾款 / 出货 / 再贩 / 现货 |
| `sourceURL` | String | — | 原文链接，**必填**（Apple 5.2 合规） |
| `itemURL` | String | — | 商品购买链接 |
| `price` | Double | — | 总价 |
| `deposit` | Double | — | 定金 |
| `balance` | Double | — | 尾款 |
| `deadlineAt` | Date/Time | Queryable + Sortable | 定金/尾款截止，驱动日历提醒 |
| `brandRegion` | String | Queryable | `jp` / `cn` |

已有字段沿用：`status`、`sourceKind`、`createdBy`、`moderationNote`、`coverImage`。

写入约定：运营发布即 `sourceKind = "editorial"`、`status = "published"`。

### 4.2 SwiftData：新增 `BrandSubscription`

放 `ItemManager/Models/`，**不要放项目根目录**（项目约定见 `AGENTS.md`）。

字段：`brandID: String`、`subscribedAt: Date`、`notifyBeforeDeadline: Bool`。

### 4.3 图书馆式全量检索（2026-09-14 用户确认）

用户确认：本功能不只是「今天上新了什么」的时间线，还要能**按品牌 / 年份 / 系列检索全部历史款式**。

**核心判断：这是同一份数据的两种读法，不要建成两套数据。**

| 视图 | 排序 / 范围 | 特点 |
|:--|:--|:--|
| 上新时间线 | 时间倒序，增量 | 时效性强，量小 |
| 图书馆检索 | 按 brandID / year / series 筛选，全量 | 长期留存，量大 |

实现要点：

1. **索引**：`brandID`、`year`、`series`、`stage` 必须 Queryable；`publishedAt` Sortable
2. **分页强制**：两种视图都要分页（每页 20-30 条），`@Query` 全量加载在万级数据下必卡，
   改用 `FetchDescriptor` + `fetchLimit` / `fetchOffset`
3. **历史不可丢** —— 与 T1-c 强相关：抓取窗口 `range(1, 62)` 若不改为自适应，
   每新增 1 条就把最老 1 条挤出窗口，图书馆会随时间静默缺数据
4. **图片不进 Bundle**：全量检索意味着图片量会涨到十万级，
   图片策略见《图片与性能扩展方案.md》，本节不重复

### 5.1 Schema

### 5.3 Security Roles —— 本期最关键的一步

**问题**：`docs/CloudKitDashboardSetup.md:110-116` 给 `_icloud` 角色配的是 **Write ✅**，
即任何登录 iCloud 的用户都能绕过 App 直接写记录。客户端 `adminIDs` 只是 UI 开关，不是安全边界。
上新流带商品跳转链接，被注入钓鱼/劫持转链的影响面是全体用户。

**动作**：

1. CloudKit Console → Security Roles → 新建自定义角色（建议名 `BrandFeedEditor`）
2. 成员用 `recordID.recordName` 添加（即 `getCurrentUserID()` 输出的那串，形如 `_819804d9...`）
3. `TimeHallEntry` 与 `Notice` 的 **Create / Write 只给 `BrandFeedEditor`**
4. `_icloud` 与 `_world` 一律改为 **Read-only**
5. **Development 与 Production 两个环境各配一次**，只配一个等于没配

**运营 onboarding**：运营用专用 Apple ID 登录 → App 内调用 `getCurrentUserID()` →
控制台输出形如 `🔑 当前用户 iCloud ID: _xxxx` → 记档 → 加入自定义角色成员。
该 ID 绑定「Apple ID + 容器」，**换号即失效**，需重新走一遍。

### T1 · 放开硬断言 + 增量 diff（预估 2-3 天）

#### T1-a · 为什么不能直接把 `!= 721` 改成 `>=`

写回逻辑（`:207-214`）是「先删掉上次同批次**全部** eventIDs，再整体插入」：

```python
old_event_ids = {...来自 catalog 的 importBatches...}
catalog["events"] = [v for v in catalog["events"] if v["id"] not in old_event_ids] + events
```

第 163 行的断言正是这个「整体替换」的保险。**改成 `>=` 等于拆掉保险**：
一旦官网改版或网络异常只解析出 20 条，这 20 条会把 721 条整体替换掉，数据直接丢失且不报错。

正确做法是「区间校验 + 写前中止 + 快照备份」三件套，不是删掉校验。

#### T1-b · 三层防护（替换硬断言）

1. **状态文件** `tools/time_hall/import_state.json`
   ```json
   { "news-timeline": { "lastCount": 721, "lastRunAt": "2026-09-14", "lastIDs": ["…"] } }
   ```
2. **三条校验规则**（必须在写 catalog **之前**执行）：

   | 情况 | 判定 | 动作 |
   |:--|:--|:--|
   | 新条数 < 上次条数 | 异常：官网只增不减 → 疑似解析失败 / 改版 | 中止，退出码非 0，**不动 catalog** |
   | 新条数 > 上次 × 1.5 | 异常：暴增 → 疑似抓进了非目标内容 | 同上 |
   | 0 ≤ 增长 ≤ 50% | 正常 | 通过 |

3. **写前快照**：写 `catalog.json` 前先复制为 `catalog.json.bak`，写失败可回滚
4. **`--expected-count N`**：官网真改版后用它手动重建基线，覆盖状态文件
5. **中止信息要可读**：打印「上次 721 / 本次 12 / 差异 -709，疑似解析失败，已中止，catalog.json 未改动」

#### T1-c · 抓取窗口自适应（「图书馆」场景必做）

`:157` 硬编码 `range(1, 62)`，只翻 61 页。官网新内容插在最前面，
**每新增 1 条，最老的 1 条就被挤出窗口**——跑一年会静默丢失几百条历史。

改为：持续翻页直到「连续 2 页无新 ID」或达到 `--max-pages`（默认 80）为止。

#### T1-d · 增量 diff 输出

- 新增 `--diff`：与 `catalog.json` 现有 id 集合比对，输出 `pending_updates.json`，**不写回 catalog**
- diff 输出**三类**，不只「新增」：
  - `added` —— 本次新增（运营要发布的）
  - `removed` —— 上次有这次没有（需人工判断：官网真删了 / 窗口不够 / 解析失败）
  - `changed` —— id 在但字段变了（标题、图片、价格）
- 维护 `published_ids.json` 记录已发布 id，避免运营重复导入
- `--diff` 与 `--dry-run` 可叠加，先只打印「新增 N / 消失 M / 变更 K」不落盘
- 输出字段需与 T3 的 App 导入页解析对齐
