# 系列「年月」根源修复 + 预约期/尾款期「开始 + 结束」需求实现说明

> 需求五 · 2026-09-24
> 用户原文：
> 1. 「其他系列都带有月份，为什么只有它不带月份？请让它也带上月份。**从根源去修复**」
> 2. 「在预约功能中，『预约中』和『尾款中』这两个状态都需要**同时包含开始时间和结束时间**，不能只提供开始时间」
> 3. 「请明确说明修改的具体范围和预期效果」

---

## 0. 结论先行

| 现象 | 根因（一句话） | 修法（三层） |
|---|---|---|
| 其他系列都带月份，只有它不带 | 批次 / 草稿链路**只承载年份**，建系列的两处（`publish` / `ensureAttributionEntities`）都只写 `year:` —— 经这条链路诞生的系列 `month` **恒为 nil** | ① 补月份通道 ② 建系列时写 `month` ③ 存量「只填空不覆盖」补全 |
| 「预约中 / 尾款中」只有一个时间点 | 「预约」原先只有**结束**点（`reservationEndAt`）、「尾款」原先只有**开始**点（`balanceDueAt`） | 预约期 = 开始 + 结束；尾款期 = 开始 + 结束（大致 / 具体两种粒度都有起止） |

两条贯穿始终的原则：

* **年月/区间都是「事实」，只补空缺、绝不改写运营已声明的值**（补全逻辑一句 `if series.month == nil` 之外没有任何覆盖路径）。
* **结束时间不驱动任何状态流转**：能驱动流转的仍然只有「预约结束时间」与「尾款开始时间」（尾款是否收齐在数据里没有判据）。

## 1. 问题一：只有它不带月份

### 1.1 证据链（根因定位）

系列列表的「年月」列读 `CatalogSeries.yearMonthText`（= `year` + `month`）。`month` 是本次之前新增的 Optional 字段，**只有系列编辑页会写它**；而经「批量录入 → 批次归属 → 发布」诞生的系列，两处建系列代码都只写年份：

| 位置 | 原代码 | 说明 |
|---|---|---|
| `ShopCatalogOps.swift` `ensureAttributionEntities` | `CatalogSeries(id: "series-ops-…", …, year: session.newSeriesYear, …)` | 批次详情页「创建 / 确认系列并开始配置」 |
| `ShopCatalogOps.swift` `publish(_:store:)` | `CatalogSeries(id: "series-ops-…", …, year: draft.newSeriesYear, …)` | 发布时新建系列 |

而这两处的**输入侧根本没有月份可传**：

```
CatalogProductDraft.newSeriesYear: Int?          // 只有年
CatalogBatchEntrySession.newSeriesYear: Int?     // 只有年
applyBatchAttribution(..., newSeriesYear: Int?)  // 只传年
ShopCatalogDraftStyleForm.StyleInput.newSeriesYear: Int?   // 只有年
UI：ShopCatalogBatchDetailView  TextField("年份（选填，如 2026）", keyboardType: .numberPad)
UI：ShopCatalogOpsView          TextField("年份", value: $draftBox.newSeriesYear, …)
```

⇒ **凡经这条链路建的系列，`month` 永远为空**，列表里就只有那一批显示「2026」、其它（系列编辑页建的）显示「2026-10」。这就是「为什么只有它不带月份」的全部原因。

### 1.2 三层修复

**第一层 · 通道 —— 让月份能带过来**

* 新增 `CatalogProductDraft.newSeriesMonth: Int?`
* 新增 `CatalogBatchEntrySession.newSeriesMonth: Int?`
* 新增 `ShopCatalogDraftStyleForm.StyleInput.newSeriesMonth: Int?`
* 贯通：`createBatch` → `applyBatchAttribution(batchID:…, newSeriesMonth:)` → 两个录入入口

> 三者都是 **Optional 且无默认值的存值属性** → 合成 `Decodable` 走 `decodeIfPresent`，旧草稿 / 旧批次 JSON 缺键自动置 nil，**零迁移**（这条是本项目的硬规则：Codable 结构新增字段一律 Optional）。

**第二层 · 写入 —— 建系列时落 `month`**

* `ensureAttributionEntities` 建系列 → 写 `month: session.newSeriesMonth`
* `publish` 建系列 → 写 `month: draft.newSeriesMonth`
* 复用既有系列的两条分支 → 调用 `completingYearMonth(...)`（见下）

**第三层 · 存量补全 —— 已存在但缺月份的系列怎么救**

唯一判定实现（`nonisolated`，可单测）：

```swift
ShopCatalogDraftStore.seriesCompletingYearMonth(_ series: CatalogSeries, year: Int?, month: Int?) -> CatalogSeries?
```

规则三条：

1. **系列没有年** → 补年，月**一并**补（年月必须同源，否则会出现「2026 + 空月」和「空年 + 10 月」这种半截数据）；
2. **系列有年、与输入同年、但没有月** → 只补月；
3. **其余一律不动** —— 已有月份不覆盖（那是运营声明）；年份不一致不补月（同名不同年 = 另一条系列，硬补就是脏数据）。

三个触发点（都走同一份判定，不留第二套）：

| 触发点 | 场景 |
|---|---|
| `completeSeriesYearMonth(seriesID:year:month:)`（新方法，返回「是否真的写了盘」） | 批次详情页「应用到整批」时，若选中的**既有系列**缺年月 → 顺带补齐（`applyBatchAttribution` 只写批次与草稿、不碰实体，所以需要这条明确入口） |
| `ensureAttributionEntities` | 批次详情页「创建 / 确认系列并开始配置」 |
| `publish` 的两条路径（首发 + `recoverPendingPublish` 半成功恢复） | 发布时新建或复用系列 |

### 1.3 指纹兼容（为什么不会重复发布）

月份进了 `publishOperationKey`（本项目固定规则：会改变发布产物的字段必须进指纹，否则「改了再发布」会被幂等入口吞掉）。但指纹段的形态是：

```swift
CatalogProductDraft.yearMonthKey(year:month:)   //  "-" / "2026" / "2026-10"
```

* **只有年份时输出与旧实现逐字相同**（`"2026"`，都没有则 `"-"`）⇒ 存量已发布草稿的 `publishOperationKey` **一个字符都没变**，不会被判成「内容变了」而重新发布；
* 补了月份 → 指纹变化 → 这是一次真实的新内容，改动会落库；
* 又因为单条销售事件指纹（`saleEventKey`）**不含年月**，事件 ID 不变 ⇒ 命中 `recoverPendingPublish` 的「产物已写、只补收尾」分支，**不会重复生成销售记录**；
* 该恢复分支里也补了年月（否则「填了月份点发布」会停在恢复分支，永远落不到系列上，界面却显示「已发布」）。

### 1.4 录入入口

两个旧入口的「年份数字框」升级成「年月文本框」，校验与解析**共用系列编辑页的同一口径** `CatalogYearMonthText`：

| 入口 | 改后 |
|---|---|
| 批次详情页「整批归属」 | `TextField("年月（选填，如 2026-10 或 2026年10月）")` + 同源红字校验；选中**缺年月的既有系列**时该框也会出现，下方一句「该系列还没有年月，在这里补上即可（只补空缺，不会覆盖已有值）」 |
| 草稿编辑器「系列」段 | 同上（`2026` / `2026-10` / `2026年10月` 都认） |
| 草稿编辑器「关联系列」选择器 | 改为「年月 · 系列名」，与系列列表同口径 —— 少一个月一眼就能看出来 |

解析失败**不改动已存值**（打字途中「2026-」是半成品，此时擦掉已填的月份会让输入框与存储来回打架），只给红字；文本框清空 = 显式清除年月。换系列时输入框跟着回填该系列的值（否则会残留上一段输入，把月份写到另一个系列上）。

## 2. 问题二：预约中 / 尾款中都要「开始 + 结束」

### 2.1 数据模型（全部新增 Optional，零迁移）

| 字段 | 含义 | 必填性 |
|---|---|---|
| `reservationStartAt: Date?` | **新增**：预约开始时间 | 选填 |
| `reservationEndAt: Date?`（既有） | 预约结束时间 | 预约中必填（既有规则，是自动流转依据） |
| `balanceDueAt: Date?`（既有，**key 不变**） | 尾款**开始**时间 | 具体粒度必填 |
| `balanceDueEndAt: Date?` | **新增**：尾款结束时间 | 选填 |
| `balanceDueText`（既有）/ `balanceDueEndText`（**新增**） | 大致粒度的开始 / 结束描述 | 开始必填、结束选填 |

> `balanceDueAt` 的 Codable key **刻意不改名**：改 key = 存量覆盖层里的字段全丢。它的语义本来就精确等于「开始收尾款」，直接当区间起点用。

### 2.2 为什么「开始必填、结束选填」

1. 开始是自动流转的**唯一**依据（`CatalogSeriesBalanceDue.isDue` 只看开始），必须是确定时刻；
2. 结束若必填，**存量系列**（只有开始、没有结束）一打开表单就会因为空值报错 ——「什么都没改也保存不了」；
3. 缺结束就给一个默认日期 = 替运营编一条事实，与全项目「缺依据就不猜」的口径冲突。

所以表单用**显式开关**声明（与加购弹窗「已公布尾款时间」同一写法）：`Toggle("已设置预约开始时间")` / `Toggle("已设置尾款结束时间")`，关闭 = 未声明，绝不预填一个假日期。

### 2.3 校验规则（唯一口径，两处 UI 共用）

**预约期** — `CatalogSeriesReservationWindow.validationErrorText(start:end:)`（新文件）

* 开始未填 → 通过；
* 两者都有且 `start > end` → 拦截：「预约开始时间不能晚于预约结束时间（预约结束：yyyy-MM-dd）」；
* **相等放行**（同一天 00:00 开、00:00 结是运营的真实写法）；
* 只在**「预约中」**阶段校验 —— 那是两个字段同时录入、结束时间就在眼前可改的唯一阶段。

**尾款期** — `CatalogSeriesBalanceDue.validationErrorText(kind:text:endText:exactAt:endAt:endDeclared:reservationEndAt:)`

* 大致：开始**必填**、≤30 字；结束选填、填了同样 ≤30 字（超长提示单独一句，指出是「尾款结束（大致）」）；
* 具体：开始必须**严格晚于**预约结束时间（无基准不比对，既有口径）；结束**若声明**则不得早于开始（同日允许）；
* 「未填写」= 显式清空五个字段（没选它就不能撤，这是运营需要的一条路径）；
* 切换粒度清空另一种载体（避免「两份真值」，界面就得替用户挑一个说，一定会说错）。

### 2.4 状态流转：口径**零变化** + 一条新提示

* 流转链不变：`未声明 → 沿用销售记录` / `预约中 →（过 reservationEndAt）预约已结束 →（到尾款开始时间）尾款中`；显式声明的「尾款中 / 现货」不被时间改写；
* **尾款结束时间不参与任何自动流转**：尾款期的出口只能由运营声明（`balancePhaseExitsByDeclarationOnly`），因为「尾款收齐没有」在这套数据里没有可判定依据。表单里新增一条橙色提示：
  > 尾款期已过声明的结束时间。若尾款已收齐，可把发售阶段改为「现货」——系统不会自动改。
* **预约开始时间同样不参与流转**：开始时间在未来时，生效阶段仍是「预约中」。**不新增「预约未开始」阶段** —— 加一个阶段要动 `allCases`、动持久化 enum 语义、动所有 `switch`，而需求只要求「同时能填开始与结束」。

### 2.5 展示

| 位置 | 展示 |
|---|---|
| 系列列表行（运营） | 新增「预约期：2026-03-01 — 2026-03-31」；尾款行前缀随内容变：只声明了开始 → 「尾款时间：…」，声明了结束 → 「尾款期：起 — 止」 |
| 商品详情页（用户） | 「预约中 / 预约已结束」状态说明追加「；预约期：…」；「尾款中」标签与状态说明追加「；尾款期：…」 |
| 批次详情页 / 草稿编辑器 | 系列选择器显示「年月 · 名称」 |

## 4. 预期效果

### 4.1 「只有它不带月份」

| | 改前 | 改后 |
|---|---|---|
| 批次详情页「整批归属」 | 只有「年份（选填，如 2026）」 | 「年月（选填，如 2026-10 或 2026年10月）」，格式不对给红字 |
| 经批次 / 发布新建的系列 | 列表显示「2026」 | 显示「2026-10」 |
| 已存在但缺月份的系列 | 只能去系列编辑页改 | 在批次详情页选中它 → 出现补全框（明确写着「只补空缺，不会覆盖已有值」）→ 点「应用到整批」即补齐；发布链路也会顺带补齐 |
| 已有月份的系列 | — | **一个字节都不会被改写**（单测钉死） |
| 存量已发布草稿 | — | 指纹不变，不会因为这次改动被重新发布一遍 |

### 4.2 「预约中 / 尾款中都要开始 + 结束」

| 声明阶段 | 表单里能看到并填写的 |
|---|---|
| 预约中 | 预约开始时间（开关 + 日期）、预约结束时间（必填，驱动流转）、尾款期（未填写 / 大致：开始+结束 / 具体：开始+结束） |
| 尾款中 | 尾款期（开始 + 结束，可修正） |
| 预约已结束 / 现货 / 未设置 | 不显示这些时间输入（**不显示 ≠ 清除**：事实原样保留） |

* 系列列表一眼可见「预约期：起 — 止」「尾款期：起 — 止」（或只有一点时的「尾款时间：…」）；
* 商品详情页的状态说明里带上完整区间；
* 尾款期过了声明的结束时间 → 只提示、不自动改阶段（出口仍由运营声明）。

## 5. 兼容与零迁移

* 新增 6 个存储字段（`reservationStartAt` / `balanceDueEndText` / `balanceDueEndAt` / `newSeriesMonth` ×2 / `StyleInput` 的对应项）**全部 Optional** → 旧 JSON 缺键自动 nil；
* `balanceDueAt` 等既有 Codable key **一个都没改名**；
* 旧签名（`validationErrorText(kind:text:exactAt:reservationEndAt:)`、`stored(kind:text:exactAt:)`、`formValues(kind:text:at:fallbackExactAt:)`、`valueText(kind:text:at:locale:)`、`effectivePhase(declared:reservationEndAt:now:)`）**全部保留**并转调新实现 —— 既有调用方与既有单测行为逐字不变；
* 只有年份的存量草稿指纹不变；只有年份的存量系列照旧显示「2026」，补一次月份即显示「2026-10」。

## 6. 边界与未做

* **不新增阶段**：没有「预约未开始」这个状态（开始时间在未来时仍是「预约中」）；
* **不做定时任务回写**：所有「到点变阶段」仍是读取时判定（沿用 09-23 拍板，避免覆盖运营声明）；
* **尾款结束不驱动流转**（理由见 2.4）；
* 尾款期在「预约已结束 / 现货」阶段不显示（前者尾款还没开始收、后者已收完），退出这些阶段时数据原样保留；
* UI 版式（Form 里两组时间输入的排列、开关观感）只到编译级 + 逻辑级验证，未做模拟器目视（`Form` 无法离线快照渲染）。
