文中的“目标”“新增”“应改”为建议，不代表已经实现；不是阿里官方内部计划，也不是已验证的千牛最新界面像素复刻。

1. 结论与交付边界

不重建一个 Mac App，不重建一套 Catalog，不重写已有发布器。把现有 PinkHouseOps 从“离线目录编辑与导出工具”，补成“以商品为中心的上新工作台”，并接通现有受控发布链路。

现有 Mac 入口已明确：导入 JSON/图片 → 本地编辑 → 离线校验 → 导出待发布包；真正写公共库由 tools/time_hall/publication/ 执行。Mac 本地数据容器显式关闭 CloudKit 自动同步。[E01][E02]

本轮“完整复刻”采用可验收定义：运营在 Mac 内完成新建/复制商品、编辑完整信息、选择素材、维护规格与价格、存草稿、校验预览、确认发布、看到真实回执、编辑已发布内容、归档恢复和追踪失败。不把“能导出 tar”当作完成发布，也不把“已有上传任务列表”当作已经有上传执行器。[E05][E06]

不扩大到客服聊天、交易订单、付款、物流、退款、营销投放和真实扣库存。它们属于另一套业务，不是当前时光馆上新的必需项。普通用户继续消费公共目录并使用已有心愿、心愿尾款和衣橱；不变更 iOS 主导航与视觉风格，不恢复此前已下线的淘宝分享文本自动导入流程。

**像素级对齐另设证据门槛：**本次核实的是千牛官方公开能力介绍，没有登录你的千牛 Mac，也没有当前账号、类目、版本对应的录屏。因此下面是可执行的千牛式交互方案，不将推测的表单顺序、按钮位置或样式标成官方事实。[Q01][Q02]

2. 千牛能力如何映射到 Pink House

千牛参考能力 Pink House 本轮落点 不直接照搬的部分
工作台、分类导航、待处理事项 上新概览、草稿数、待校验、发布异常、最近发布 不虚构 GMV、订单量、库存周转率
商品发布与已发布商品维护 一个商品编辑器贯穿新建、草稿、修改、复制 不把 JSON 文件编辑当成用户主流程
图片空间与选图 可视化素材库、主图排序、规格图、尺码原图与系列封面 不要求运营认识 hash、assetID、local:
多规格与批量操作 规格矩阵、确认真实组合、批量填充、复制同款 不凭颜色×尺码自动断言所有组合都在售
草稿和上下架管理 商品工作副本、归档/恢复、发布版本追踪 不把普通归档等同于强制删除墓碑
预售信息 预约价/现货价、定金尾款、预约阶段与尾款时间 不引入真实付款、发货及扣库存

千牛桌面版的表单发品、商品编辑、上下架和预售能力由官方介绍直接支持；图片空间、草稿、复制同款及批量规格的细节以官方移动版能力介绍作为参考，不能据此声称 Mac 最新页面完全相同。[Q01][Q02]

3. 目标工作台结构

Pink House 运营
├─ 工作台             待处理事项、最近发布、恢复上次草稿
├─ 商品管理           搜索 / 店家 / 系列 / 品类 / 发布状态
│  ├─ 全部商品
│  ├─ 草稿与待发布
│  ├─ 已发布
│  └─ 已归档
├─ 店家与系列         店家资料、系列阶段、系列价格表、款式档案
├─ 素材库             缩略图、用途、引用关系、导入异常
└─ 发布中心           校验、差异确认、真实任务、回执、回滚

保留现有 NavigationSplitView、本机工作区、页面级 sheet 和统一状态反馈。把“目录编辑”三级列表保留为店家/系列维护的辅助视图，主工作流改成商品管理 → 商品编辑页。不能为了高仿把现有 SwiftUI 工程另换成 Electron/Web，也不新建第四套商品数据。[E03][E04]

商品列表建议列：缩略图、商品名、店家/系列、品类、款式名、规格数、预约/现货价格、销售阶段、编辑状态、最近成功发布版本。列表标签必须区分“本地已改”“已经上线”“线上待回读”，不能只放一个含义模糊的“已保存”。

4. 商品编辑页：一页闭环，不再多处寻找

编辑器采用左侧章节索引、中间编辑区、右侧当前商品预览、底部固定动作栏。建议章节如下：

章节 必须能维护 现有模型落点
基础信息 店家、系列、商品名、品类、款式名、说明 CatalogShop / CatalogSeries / CatalogProduct.designName、description
图文素材 有序主图、首图、详情图、规格图、来源说明 CatalogProduct.images / CatalogAsset / CatalogProductVariant.imageAssetID
规格 颜色、尺码、真实组合、规格图、批量填充 CatalogProductVariant
价格与历史 预约价与现货价并存、定金尾款、币种、再贩 CatalogSaleEvent 与 CatalogPriceCorrection 分离
系列档期 预约中/结束、尾款中、现货；起止时间与大致说明 CatalogSeries.salePhase 与预约/尾款字段
两类表格 商品尺码表与原图；系列共用价格表 CatalogSizeChart / CatalogSeries.priceChart
发布检查 引用、价格、图片、来源、版本差异、目标环境 SharedCatalog 门禁 + 发布任务记录

这些领域字段多数已在共享模型里；缺的是 Mac 的编辑入口和部分可复用业务规则，不是从零设计全部数据结构。[E08]

底部固定动作：保存草稿｜预览｜检查问题｜提交发布。保存失败保留编辑内容，不关闭编辑页；发布不是本地保存的同义词。

4.1 价格必须保留现有业务语义

“修正当前价格”和“新增一次预约/现货/再贩事件”必须是两个明确动作。修价写 priceCorrection，业务历史写 saleEvents，不能每次点保存都追加一条销售记录。金额与币种一起显示和验证；未知价留未知，不能写成 0；未知币种不静默当 CNY。[E08]

**SKU 精确价格是一个真实协议缺口，不能用界面掩盖。**当前 CatalogProductVariant 只有配色、尺码与规格图，没有每 SKU 的价格和库存；销售记录是商品级，价格分档只保留区间。若要做到“每个规格一行不同价格”的千牛式矩阵，必须扩展共享合同，例如在销售事件上新增可选规格价格明细（variantID、价格、定金、尾款；币种继承该事件），再补消费者读取、导入导出与版本兼容。不能把 min/max 区间冒充每个 SKU 的实际报价。[E08]

新规格价格扩展默认不启用；在明确来源数据和读者兼容前，只展示当前模型真实支持的商品级价格与区间。真实库存不在本轮范围，不伪造 0、999 或“无限库存”。

4.2 商品、款式与规格身份

保留已有实体 ID；改名、改价、换图都不重建 ID。复制同款是新商品，生成新商品/规格/新事件身份，复用有权限使用的素材引用，但不得复制旧发布回执或旧销售历史作为新发生的事实。多选加入衣橱的主衣物/小物规则不重写。

已有同款不同色归组沿用 designName 与现行展示逻辑；不为了套用通用 SPU/SKU 教科书模型合并掉已经被个人衣橱引用的商品。[E08]

4.3 素材操作

商品图应直接拖入当前编辑器，自动入 staging 并选中为该商品素材；也可以从素材库复用。主图顺序是每个商品自己的有序数组，不是素材库的全局顺序。支持缩略图、放大、拖拽排序、设首图、解除绑定、查看被谁使用。

目前 BindImagesSheet 用 Set 选图，再按全局 assets 顺序回写，不能稳定保存每件商品自己的图片排序；同时仍显示 assetID 与 URL，而非缩略图。这是 Mac 的明确改造点，不能根据最近提交标题就认定 Mac 已完成缩略图改造。[E04]

继续复用已有图片规范化、内容 hash、立即拷贝到 staging、断点台账。当前规范化结果被同时用作 thumbnail/preview/original 引用；若产品承诺下载“原始上传文件”，需另存源文件或明确称为“发布高清图”，不要把重编码结果描述为字节不变的原图。[E02]

5. 两个范围必须分开：操作单位是商品，发布单位仍是整包

当前商店目录使用完整 shopCatalog 分片，和其他时光馆内容共用发布头。Mac 草稿也以完整 Catalog JSON 存储，coverageStatus 默认 complete。[E07][E11]

因此不能把某个商品的新草稿直接标 complete 发出去。正确做法是：

当前线上完整基线 + 本次商品变更集 + 显式归档/删除意图
                     ↓
合成新的完整 ShopCatalog，保留未改动店家/系列/商品
                     ↓
构建完整发布根清单，保留不属于本轮的其他时光馆分片

本地草稿应记录 baseReleaseSeq、baseRootIndexHash、draftRevision。本次编辑不能悄悄覆盖其他运营或其他设备后来发布的修改。发布前比较基线，过期时展示差异并合并/重新确认；不能只自动把 releaseSeq 加一继续覆盖。

第一阶段仍可保持“一份完整目录工作区”，先把编辑体验商品化，不急着把 SwiftData 改成复杂实体关系库。之后的每商品工作副本也只是编辑层数据，不得成为第二套公共 Catalog。

6. 发布方案：复用本机受控发布器，先不强加一个服务器

**优先路线：Mac 原生工作台 → 受控本地发布桥接器 → 现有 Python 发布流水线 → CloudKit。**这与入口文件和 entitlements 中的既有本地发布方向一致。[E01][E12]

需要新增的是任务编排与可观测回执，不是第二份 CloudKit 协议。桥接器只接受固定动作和经过验证的产物路径，调用固定可执行程序及参数列表；禁止把用户文本拼成 shell 命令。私钥由原发布器从受控凭证位置读取，不能进入 App 资源、Catalog、导出包、命令行或日志。

**沙箱与打包是前置验收项。**当前已打开网络和用户选中文件读写权限，但这不等于外部 Python、依赖、Keychain 和 staging 访问已经全部可用。先在真实签名构建上验证固定运行时、文件访问、凭证读取和子进程回执；不允许静默依赖运营电脑上随意安装的 Python。若实际沙箱/签名方案不适配，再引入签名伴随发布助手，仍只保留一份 Python 发布逻辑。不能把取消沙箱、复制长期密钥进 App 当作修复。

多名运营并发、无人值守定时发布、跨设备审批属于后续扩展，再把同一发布器搬到受控服务端。没有持续运行的执行器时，不能提供“关机后保证定时发布”的承诺；暂时只提供到时提醒，或把定时发布明确列为未开放能力。

6.1 真实发布顺序

现有 Python 已实现以下主顺序，应保留：[E10]

  1. 复校验不可变产物。
  2. 读当前 THRelease 与 changeTag。
  3. 上传缺失 THMedia。
  4. 上传缺失 THDataPack。
  5. 回读校验资源可获取性与摘要。
  6. 带 changeTag 条件更新 THRelease。
  7. 回读确认新发布头。

只有第 6 步之后线上头指向新版本；只有回读确认后 Mac 才显示“发布已确认”。这是一套应用层提交协议，不是对整个 CloudKit 公共库多记录事务能力的宣称。终端出现成功字符串也不等于每个离线用户已经刷新。

要补的可靠性：结构化进度、持久化 jobID/产物 hash/目标环境、幂等请求、提交结果不明时先回读、发布回执入库、和草稿版本关联。现有 CLI 对小于等于线上版本号的请求直接拒绝；新增桥接幂等逻辑必须识别“同一产物已经成功”与“新版本已经取代它”，而不是失败后无脑换号重发。[E10]

6.2 状态设计

已有 CatalogPublicationStatus 不要复制一份同义模型。[E08] 另外两条不同状态轴必须独立：

状态轴 语义
编辑/审核状态 本地未保存、草稿、已提交审核、已审核；绑定 draftRevision
发布执行状态 等待、构建、上传、验证、切头、结果待确认、已确认、可重试失败、冲突
系列销售阶段 预约中、预约已结束、尾款中、现货；沿用共享领域规则

“已发布”不代表“现货”；“有现货价”不代表预约历史应消失；“本地保存成功”不代表用户已经能看到。

7. 实施顺序与完成闸门

阶段 交付内容 必须拿到的证据
M0 基线与范围 当前 HEAD/工作区记录、草稿与 staging 备份、现有测试基线、必要的千牛授权参考截图 基线报告；不覆盖你的本地未提交代码；参考版本与类目可追溯
M1 可靠性地基 保存错误不吞、坏草稿隔离、真实 dirty/revision、所有变更使校验失效、导出服务复校验 故障注入失败用例转绿；关闭重启仍可恢复
M2 商品编辑闭环 商品列表、完整编辑器、素材可视化、规格、价格双流程、系列档期、两种表格 同一份输入 Mac 编辑后 iOS 无损读取；图片顺序与币种正确
M3 真实发布闭环 本地受控桥接、基线差异、结构化任务、回读回执、断点与冲突处理 Mac 点发布后无需手开终端；Development 中另一台设备可读到一致数据
M4 运营效率与维护 复制、批量修改、归档恢复、发布历史、回滚、可选 SKU 精确价扩展 批量差异可审计、身份不漂移、旧个人记录不受影响
M5 上线 权限、签名运行时、Production 独立检查、消费者回归、文档统一 实际验证记录，不用截图或旧“测试通过”文字代替真实测试

M1 不能被“先把页面画得像”挤到最后；M3 未通过前，整体只能称“编辑端完成”，不能称“千牛式上新完整复刻完成”。

8. 给 Agent 的最终边界

先修可靠性，再完善编辑器，再接发布器，最后补批量和维护。遇到已有同等能力优先收口，不照建议路径重复造文件。只迁出 iOS 中可以共享的纯规则，不能把整个 iOS 界面和个人数据服务塞进共享包。保留原有商品、规格、销售事件和个人引用；新草稿不是重新编号的理由。

2. 必须先修的代码问题

R01｜校验结果可能过期，但导出仍使用它（P0）

证据：OpsWorkspace.markDirty() 只写状态文案，不清空 review、不递增已审查版本。OpsValidationView.export() 依赖已存在的 review。makePublicationArchive() 检查缺失本地图片，但不重新调用完整结构门禁。[E02][E06]

**修改：**统一编辑命令入口递增 draftRevision；任何新增/删除/移动/换图/导入都使 review 失效。review 绑定当前规范化 Catalog hash 与素材指纹。导出/发布服务入口重新校验当前冻结快照，不能只靠按钮禁用；生成产物使用同一个快照，避免“校验 A，导出 B”。

**验收：**先校验成功，再制造一个无效父子引用，即使直接调用导出服务也失败；先校验后删除 staging 图也失败；未修改内容的重复校验结果稳定。

R02｜保存失败有被后续成功文案覆盖的路径（P0）

证据：saveDraft() 内部捕获保存异常但返回 Void；importImages() 调用它后又基于图片导入 failures 重写 lastError。于是图片导入成功而草稿保存失败时，保存错误可能被清除。createDraft() / persist() 等还存在 try? context.save()。[E02]

**修改：**保存返回 Result 或 throws；事务失败不更新已保存 revision，不报告成功；导图的“处理成功”与“落盘成功”分开汇总。SwiftData 内存对象在失败后的状态需恢复/标脏，不能仅改一条字符串。

**验收：**模拟磁盘/持久化失败，仍保留输入并显示失败；重启不会把未落盘状态冒充已保存；错误不能被“新增 N 张”覆盖。

R03｜损坏草稿应硬隔离，不能只靠提示“不覆盖”（P0）

证据：adopt() 解码失败后把 catalog 设为空，但仍保留 draft 记录；后续保存路径没有解码失败只读状态保护。当前注释“不自动覆盖”不等于已从代码上禁止覆盖原始内容。[E02]

**修改：**增加损坏草稿状态、原始字节备份与只读恢复界面。默认保存/导图/导出均不可覆盖损坏记录；恢复必须另存一份新草稿。加载失败不是合法空目录。

**验收：**截断 catalogJSON 后打开，再点击所有可能保存的入口，原损坏字节及备份仍保留；显式恢复到新 ID 才能编辑。

R04｜图片排序被 Set 与全局顺序吞掉（P1）

证据：BindImagesSheet 读取产品 images 后转成 Set，提交时按 catalog.assets 的全局顺序输出。[E04]

**修改：**每个商品维护有序选图数组；取消勾选仅删该项，新勾选追加，拖拽更新顺序；首图显式可见。素材库排序变化不得改变商品图顺序。

**验收：**两个商品共享同三张图但顺序不同；重开绑定页、保存、导出、iOS 读取后顺序各自保持。

R05｜编辑完成不等于操作成功（P1）

**证据：**商品/系列 sheet 调用 workspace 更新后无条件 dismiss；workspace 部分验证失败只赋 lastError。系列新建表单有 season，但新建调用 addSeries 未传 season。当前 Workspace 中 addSeries 也未接收 season。[E02][E04]

**修改：**编辑命令返回明确结果，成功才关闭。新增/编辑系列使用同一字段提交合同，包含 season 及新接入的档期字段。父子归属校验收口到命令层，不仅放 Picker 的 onChange。

**验收：**无效名称留在编辑器；新建系列季节保存后可回显；改变系列店家时，要求显式迁移其子项或拒绝，不能留下产品与系列店家不一致。

R06｜父子选择变化缺少明确联动（P1，交互待运行复核）

**证据：**目录主页面的 clampSelection 由 onAppear 和实体数量变化触发；已读代码没有在 selectedShopID/selectedSeriesID 变化时相应收敛下级选择。[E04]

**修改：**父选择变化时显式重设/收敛子选择，并在数据更新后重新验证当前 ID；列表不依赖“数量变化”来表达身份或归属变化。

**验收：**两个同样商品数量的系列来回切换；不会继续操作旧系列的产品或出现假空态。本条为静态风险，未做 UI 运行复现。

R07｜本机可以编辑，不代表这份完整包能安全覆盖线上（P0）

**证据：**草稿是完整 JSON、coverageStatus 默认 complete；同一个发布头覆盖不止一类内容；现有发布器的 changeTag 读取发生在发布执行阶段，不能自动识别更早创建的草稿已落后。[E07][E10][E11]

**修改：**草稿冻结 baseReleaseSeq/rootHash；单商品变更必须先合成完整 Catalog，保留未改内容与其他根分片；发布前检测过期基线，再使用现有 CAS 保护执行阶段并发。

**验收：**A/B 从同一基线编辑不同商品，A 先发后 B 发，B 不能覆盖 A；仅改一家商品不能让其他店家或画册消失。

R08｜既有媒体键只是引用，不等于远端已验证（P1）

**证据：**离线门禁把符合形式的 mediaKey/thmedia 引用视为已远端化；它不读远端。对悬空 assetID/裸名称采用兼容性告警而非统一阻断。[E09]

**修改：**保留旧包兼容读；为新创建/修改内容增加明确的严格发布策略：引用必须可解析，已上传状态需按目标环境回读确认，不能因有一串 hash 就跳过验证。若仍保留外链/内置资源，必须展示来源与兼容理由；严格策略同时落实到 Mac 与 Python 自检，不是只改 UI。

**验收：**合法 hash 但远端无文件被阻断；Development 有图而 Production 无图不能误判已上传；旧数据兼容异常有明确迁移报告。

R09｜发布响应丢失需要“待确认”，不能一律重发（P0）

5. 接口约束（设计合同，不是假定现有接口）

5.1 编辑命令

所有增删改经统一入口返回成功/失败与变更范围。成功后更新 revision、使 review 失效；失败不关闭编辑器、不报告成功。自动保存如加入，采用合并保存、恢复点和撤销；不能用“自动保存会无法撤销”的旧注释否定恢复设计。

5.2 发布请求与回执

发布请求至少带：requestID、draftID、draftRevision、baseReleaseSeq、baseRootIndexHash、targetEnvironment、输入包摘要及受控文件句柄/路径。输入包不是可执行指令，禁止内含命令和凭证。

进度事件至少带：jobID、stage、entityKey、completed/total、可重试分类、脱敏错误。回执至少带：environment、releaseSeq、rootIndexHash、实际生效状态、verifiedAt、产物摘要。上述是新增协议设计，不代表现有脚本已经接受这些字段。

多次点击同一冻结快照重用 requestID；修改内容是新 revision/new request。素材内容幂等与发布请求幂等是两个问题，不能因为已有 mediaKey 就声称整条发布链路幂等。

5.3 发布与删除

默认普通下架走明确归档/隐藏语义，恢复保留商品身份；当前 force remove 会删关联公共子项并写墓碑，应保留为独立危险操作，展示范围并确认。强制删除不能删除用户已确认的私有衣橱和心愿事实。恢复已下架商品与回滚整版不是同一个按钮。

5.4 安全与性能

选择环境后固定本任务环境；任务中途不能切换。权限结果以真实受控发布通道为准，不能只靠客户端显示“管理员”。不在本次文档里擅自修改你已配置的 CloudKit 角色；Development/Production 分别实测并记录。

导图当前在 @MainActor 同步读字节和规范化，批量大图可能影响交互；这是性能风险而非本次测得时长。将 I/O 与图片处理移到受控后台工作单元，保持限并发和可取消；UI 状态与 SwiftData 所属隔离域正确更新。不要为了速度一次性读入全部原图。[E02]
