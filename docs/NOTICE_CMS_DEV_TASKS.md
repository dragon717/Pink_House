# 公告系统研发任务单（执行分组版）

> 更新时间：2026-04-06  
> 对应文档：`docs/NOTICE_CMS_PRD_EXECUTION.md`  
> 用途：将公告系统 PRD 压缩为可直接分配、可跟踪、可验收的研发任务清单。

## 1. 执行总原则

1. 先定模型与规则，再做页面与交互。
2. 先建立公告中心主入口，再治理弹窗逻辑。
3. 先明确 `Development / Production` 边界，再做发布流程。
4. 先补生命周期、权限、过期治理，再谈运营化增强。
5. 本任务单优先覆盖公告系统，不扩散到其他通知系统。

---

## 2. 关键路径

以下任务属于关键路径，必须优先完成：

1. 数据模型重构方案冻结
2. 生命周期与展示规则冻结
3. 公告中心列表与详情落地
4. 弹窗逻辑降级为“规则驱动渠道”
5. 权限从硬编码过渡到可配置方案
6. 过期治理与迁移兼容方案落地

---

## 3. 任务分组总览

| 分组 | 目标 | 优先级 | 是否关键路径 |
|---|---|---|---|
| A. 产品规则冻结 | 冻结模型、状态机、渠道矩阵 | P0 | 是 |
| B. 数据层改造 | 重构公告主模型与用户状态模型 | P0 | 是 |
| C. 用户前端 | 建立公告中心，弱化旧弹窗路径 | P0 | 是 |
| D. 管理前端 | 建立公告管理闭环页面 | P1 | 否 |

| H. 诊断与文档 | 建立故障排查和环境校验流程 | P1 | 否 |

## 4. A 组：产品规则冻结

### A1. 冻结公告字段表

- 目标：把 PRD 中的公告主模型字段冻结成研发字段表。
- 输出：
  - 字段名
  - 类型
  - 默认值
  - 是否必填
  - 是否参与查询/排序
  - 兼容旧字段映射
- 依赖：无
- 验收：
  - 数据、前端、CloudKit 三方能基于同一份字段表工作
  - 不再出现页面先写字段、模型后补字段的情况

### A2. 冻结生命周期状态机

- 目标：确定 `draft / scheduled / published / archived` 的流转规则。
- 输出：
  - 状态图
  - 每个状态可执行的操作
  - 状态切换条件
- 依赖：A1
- 验收：
  - 任一公告的操作路径可被唯一解释
  - “编辑即上线”被彻底禁止

### A3. 冻结展示渠道矩阵

- 目标：明确 `inbox / banner / modal` 的使用条件。
- 输出：
  - `severity -> channel` 矩阵
  - modal 节流规则
  - 冷启动与回前台策略
- 依赖：A2
- 验收：
  - 任何公告都能判断该去哪个渠道
  - 不再通过 `priority` 暗中决定“是否弹窗”

### A4. 冻结环境与角色规则

- 目标：明确环境职责和角色边界。
- 输出：
  - `Development / Production` 使用规则
  - `editor / publisher / admin` 权限边界
- 依赖：无
- 验收：
  - 正式发布和调试流程不再混淆
  - 管理入口可按角色区分能力

---

## 5. B 组：数据层改造

### B1. 公告主模型重构

- 目标：将旧 `Notice` 模型升级为可支持内容系统的新模型。
- 涉及方向：
  - 内容字段
  - 生命周期字段
  - 渠道字段
  - 动作字段
  - 审计字段
- 依赖：A1, A2, A3
- 验收：
  - 模型能表达草稿、定时、发布、归档
  - 模型能表达 `severity`、`channel`、`requiresAck`

### B2. 用户状态模型扩展

- 目标：将“已展示/已读”扩展为完整用户状态。
- 涉及方向：
  - `unseen / read / acknowledged / dismissed`
  - 弹窗展示次数
  - 最近展示时间
- 依赖：A3
- 验收：
  - 用户状态不再只有“展示过/没展示过”
  - “已读”和“已确认”在模型上可区分

### B3. 排序与查询策略重构

- 目标：从旧 `priority` 主导，改成多维排序。
- 建议排序：
  - `severity`
  - `pinned` 或等效置顶能力
  - `publishAt`
  - `updatedAt`
- 依赖：B1
- 验收：
  - 排序不再依赖单一字段承载所有语义

### B4. 过期治理字段落地

- 目标：补齐 `startAt / endAt / archivedAt` 的产品与数据支持。
- 依赖：B1
- 验收：
  - 文档中说“过期”的公告在产品和数据层都成立

---

## 6. C 组：用户前端

### C1. 建立公告中心列表页

- 目标：提供稳定主入口，替代“错过弹窗就找不到”的状态。
- 页面能力：
  - 公告列表
  - 未读态
  - 重要公告视觉区分
  - 下拉刷新或等效刷新能力
- 依赖：A3, B1, B3
- 验收：
  - 用户在不依赖弹窗的前提下能查看生效公告

### C2. 建立公告详情页

- 目标：承接完整内容展示与动作按钮。
- 页面能力：
  - 标题
  - 正文
  - 媒体
  - 发布时间
  - 动作按钮
  - 已确认按钮
- 依赖：C1, B1, B2
- 验收：
  - 任意公告都能稳定查看详情

### C3. 横幅渠道接入

- 目标：为 `important` 类公告提供轻提醒渠道。
- 页面能力：
  - 首页可展示 banner
  - 点击进入详情
  - 支持关闭或忽略
- 依赖：A3, C2
- 验收：
  - 横幅展示不影响主要交互流程

### C4. 弹窗逻辑治理

- 目标：把现有“最新一条弹窗”逻辑改为规则驱动。
- 重点：
  - 冷启动不立刻弹
  - 回前台不强制弹
  - 同公告展示频次受控
  - 仅 `critical` 公告允许 modal
- 依赖：A3, B2
- 验收：
  - 重复弹窗率显著下降
  - 弹窗从“默认行为”降级为“条件行为”

### C5. 未读角标与入口联动

- 目标：让公告中心在用户侧具备持续存在感。
- 页面能力：
  - 公告入口角标
  - 未读数量或未读态
- 依赖：C1, B2
- 验收：
  - 用户可感知有新公告，但不被强打断

## 7. D 组：管理前端

### D1. 管理列表页

- 目标：建立草稿、定时、已发布、已归档的统一列表页。
- 依赖：A2, B1
- 验收：
  - 管理员能查看所有状态的公告

### D2. 草稿编辑页

- 目标：建立完整编辑表单。
- 能力：
  - 标题
  - 正文
  - 媒体
  - 渠道
  - 时间窗
  - 动作
  - 确认型开关
- 依赖：D1, A1
- 验收：
  - 草稿能完整保存

### D3. 预览页

- 目标：支持 `inbox / banner / modal` 三类预览。
- 依赖：D2, A3
- 验收：
  - 发布前能看到真实渠道效果

### D4. 发布操作页

- 目标：支持立即发布、定时发布、下线、归档。
- 依赖：A2, D2
- 验收：
  - 生命周期操作完整闭环

### D5. 发布历史与回滚页

- 目标：查看版本记录、执行回滚。
- 依赖：F2
- 验收：
  - 历史记录可追踪
  - 回滚入口明确

## 8. E 组：CloudKit 与同步

### E1. 公告主数据同步重构

- 目标：让公告主数据同步匹配新模型。
- 存储位置：`CloudKit Public Database`
- 依赖：B1
- 验收：
  - 草稿、定时、发布、归档在公共数据层表达完整

### E2. 用户状态同步重构

- 目标：将用户公告状态从旧“已读/已展示”扩展成完整状态模型。
- 存储位置：`CloudKit Private Database`
- 依赖：B2
- 验收：
  - 换设备后能恢复已读/确认状态

### E3. 本地缓存与刷新策略重构

- 目标：明确本地缓存的职责与同步触发时机。
- 规则：
  - 冷启动轻量拉取
  - 回前台增量拉取
  - 手动刷新强制拉取
- 依赖：A3, B1, B2
- 验收：
  - 同步行为可预测
  - 展示决策不再直接绑死同步事件

### E4. Query 与索引方案整理

- 目标：补齐新字段对应的 CloudKit Schema 与索引需求。
- 依赖：A1, B1
- 验收：
  - 新字段可查询、可排序
  - 生产环境 Schema 有清晰部署清单

---

## 9. F 组：权限与审计

### F1. 角色配置方案落地

- 目标：从硬编码管理员 ID 过渡到可配置角色体系。
- 依赖：A4
- 验收：
  - 换管理员不需要发版
  - `editor / publisher / admin` 行为边界清晰

### F2. 审计日志方案落地

- 目标：记录创建、编辑、发布、下线、归档、回滚。
- 依赖：A4, B1
- 验收：
  - 任意公告都能追踪到责任人与操作时间

### F3. 管理端权限门控

- 目标：按角色控制页面可见性与操作按钮。
- 依赖：F1, D1
- 验收：
  - 非授权角色无法进入或执行超权限操作

---

## 10. G 组：迁移与兼容

### G1. 旧公告迁移策略

- 目标：把旧 `Notice` 数据映射到新模型。
- 规则示例：
  - `isActive == true` 映射为 `published`
  - `isActive == false` 映射为 `archived`
  - 旧 `priority` 不直接等同 `severity`
- 依赖：B1
- 验收：
  - 老数据升级后仍可展示

### G2. 旧已读状态兼容

- 目标：兼容当前 `readTrackingKey` 与历史 key 逻辑。
- 依赖：B2, E2
- 验收：
  - 用户升级后不会因为模型升级导致全部公告重新变未读

### G3. 旧客户端兼容策略

- 目标：定义旧版本客户端如何安全忽略新字段。
- 依赖：B1
- 验收：
  - 新字段下发不导致旧版本异常

---

## 11. H 组：诊断与文档

### H1. 诊断页角色重定义

- 目标：将实验室/测试页明确定位为“诊断工具”。
- 依赖：A4
- 验收：
  - 正式发布入口与诊断入口分离

### H2. 环境排查手册

- 依赖：E4, F1
- 验收：

### H3. 发布 SOP

- 目标：输出标准发布、下线、回滚操作流程。
- 依赖：D4, D5, F2
- 验收：
  - 运营与研发对公告上线流程理解一致

## 13. 上线前验收清单

- [ ] 公告中心可作为唯一正式入口查看公告
- [ ] 普通公告默认不走 modal
- [ ] modal 不在冷启动时立即展示
- [ ] `Development / Production` 使用边界明确
- [ ] 管理权限不再依赖硬编码发版
- [ ] 已读与确认状态跨设备可恢复
- [ ] 旧公告与旧已读兼容完成
- [ ] 过期公告能自动退出用户可见面
- [ ] 发布、下线、回滚都有文档和可执行路径

---

## 14. 本任务单的使用方式

- 产品评审时：用它确认范围和优先级。
- 研发排期时：按分组拆成具体开发项。
- 联调时：按关键路径推进，不并行做非关键 UI 优化。
- 测试时：以“上线前验收清单”为基线。
