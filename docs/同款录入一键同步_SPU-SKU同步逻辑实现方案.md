# 同款录入「一键同步」——SPU/SKU 同步逻辑实现方案（2026-09-23）

针对反馈：「批次详情」里录入了「天鹅之歌」系列 3 个单品（生成色 / 粉紫色 / 蓝色一字领 OP），
点「应用到整批 3 条单品」只能同步**店家**和**系列**，价格、尺码表、面料、详情描述都带不过去，
只能逐条重录。

---

## 一、结论先行

**底层结构其实已经是 SPU + SKU 了**，不需要再重构一次数据模型：

| 层级 | 已落地的事实 | 落在哪 |
| --- | --- | --- |
| 款式（SPU） | 尺码表整款共享（任一颜色填 → 全色可见） | `ShopCatalogSizeChartSharing`（需求 G） |
| 款式（SPU） | 面料 / 款式描述整款一份 | `CatalogStyleProfile` + `ShopCatalogStyleProfileSharing`（需求 H） |
| 颜色（SKU） | 同款不同色 = **多个独立商品实体**，只做展示层归组 | `ShopCatalogSameDesignGrouper` |

**真正的缺口是「录入期」缺一个把款式公共资料从一条颜色带到其他颜色的动作**，
以及**草稿模型里根本没有「面料 / 款式描述」这两个字段**（`CatalogProductDraft` 只有价格、
图片、配色尺码、尺码表）—— 所以想同步也没东西可同步。

这次补的就是这两件事，不引入新实体。

---

## 二、字段分层（本次硬口径）

| 字段 | 层级 | 一键同步会带走 | 说明 |
| --- | --- | --- | --- |
| 预约价 / 现货价 / 定金 / 尾款 / 档期 / 币种 | 款式公共 | ✅ **整组** | 同一套销售条件，拆开搬会留下对不上的定金尾款 |
| 尺码表（列 / 行 / 原图） | 款式公共 | ✅ | 逐条重编 id，各草稿持有自己那一行 |
| 面料成分 | 款式公共 | ✅ | 新字段 |
| 款式描述 | 款式公共 | ✅ | 新字段 |
| 商品名（含颜色词） | 颜色私有 | ❌ | 复制会把粉色改名成生成色 |
| 商品图片 / 配色尺码 | 颜色私有 | ❌ | 复制会把三个颜色压成一张图 |
| 店家 / 系列归属 | 批次归属 | ❌ | 由「应用到整批」负责，同步不越权 |
| 状态 / 驳回原因 / 发布结果 | 流程字段 | ❌ | 不能被同步覆盖 |

> 后四类**在接口上就没有开关**——`ShopCatalogDraftStyleSync.Field` 只列款式公共字段，
> 从类型系统上排除了「复制错东西」的可能，而不是靠调用方自觉。

---

## 三、同步语义

1. **整快照覆盖**：勾选即整块复制；模板为空即**清除**目标该项（不是「跳过不修改」）。
   这样「再同步一次」能把改错的值纠正回去 —— 与项目里价格修正的既有口径一致。
2. **价格整组**：六个字段一起搬，绝不出现「预约价 498、定金还是 0」这种对账失败状态。
3. **尺码表逐条重编 id**：目标草稿拿到的是 `sizechart-draft-<目标草稿 id 前 6 位>`，
   `productID` 清空。共用 id 会在发布时按 id 覆盖，导致最后一个颜色赢家通吃。
4. **模板草稿原样不动**，只写目标。
5. **已发布 / 已归档的目标自动跳过**：它们的产物已经在覆盖层里，改草稿不影响线上。
6. **整批一次落盘**：要么全成功，要么磁盘上一条都没变（沿用 `applyBatchAttribution` 的写法）。

## 四、改动清单

### 4.1 新增：草稿侧款式口径（纯逻辑，可单测）

`ItemManager/Services/ShopCatalog/ShopCatalogDraftStyleSync.swift`

- `styleKey(of:inheritedSeriesLabel:resolveSeriesName:)` —— 款式键 = **系列标签 + 品类 + 款式名**，
  系列口径与批次页展示分组**同源**（复用 `CatalogBatchGrouping.groupKey`）。
  这一层必须有，否则「未自报系列、靠整批继承」的草稿认不出彼此，
  同款三色会被拆成三组、同步按钮点不到对方。
- `groups(_:inheritedSeriesLabel:resolveSeriesName:)` —— 按款式分组，保持录入顺序。
- `siblings(of:in:...)` —— 同款其他颜色。
- `syncPlan(from:to:fields:)` —— 同步产物（目标 id → 更新后的草稿）。
- `Field` 枚举 —— 可同步字段白名单；`hasStyleContent` / `describe` 辅助。

### 4.2 草稿模型补两个字段

`CatalogProductDraft` + `fabric` / `styleDescription`（Optional + 默认 nil，旧 JSON 合成解码自动兜底），
并纳入 `publishOperationKey` —— 否则「改了面料再发布」会被幂等入口判成「同一内容」而吞掉。

### 4.3 仓库新增写入接口

```swift
// ShopCatalogDraftStore
@discardableResult
func syncStyleInfo(sourceDraftID: String,
                   targetDraftIDs: [String],
                   fields: Set<ShopCatalogDraftStyleSync.Field>) throws -> Int
```

服务层自己再判一遍「同款 + 未发布/未归档」，**预检与执行同源**，不靠 UI 自觉传对 id。
同款判定的系列令牌只在**双方都明确**时才参与比较 —— 批次里草稿的系列常常是继承来的，
拿空令牌去比会误判成不同款，把本该能同步的颜色拦掉。

### 4.4 发布时落地款式档案

`publish()` 中新增：草稿携带面料 / 描述时，按 `ShopCatalogStyleProfileSharing.writePlan`
**整款一份**写入 `styleProfiles`；`recoverPendingPublish` 同样补齐这一步。

⚠️ 关键防线：**纯补价草稿（两项都空）不写档案**。
`writePlan` 的语义是「空 = 清除」，若补价草稿也走一遍，会把同款已有的面料 / 描述整块抹掉 ——
「补个价格把面料弄丢」是这条链路最容易出的静默事故。发布后要改款式资料，走
`updateStylePublicInfo`（已存在的「款式公共资料」入口）。

### 4.5 界面：两个入口

| 位置 | 变化 |
| --- | --- |
| 补录草稿页 `ShopCatalogDraftDetailEditor` | 表单按 SPU/SKU **分区**：新增「款式公共资料（同款共用，只需填一次）」= 面料 + 款式描述 + 尺码表；原图片 / 配色尺码改为「颜色差异资料（仅本条颜色）」。底部新增「同款其他颜色」= 字段勾选 + `复制到同款其他 N 个颜色`，模板 = 本条草稿（点按钮时先把页面上未保存的输入落进草稿，不用先点一次「完成」） |
| 批次详情页 `ShopCatalogBatchDetailView` | 单品列表升级为 **系列 → 款式组 → 颜色** 三级；款式组下多一行「以『生成色一字领 OP』同步到其余 2 个颜色」，模板写进按钮文案，避免「复制了谁的资料」含糊 |

## 五、测试覆盖

`ItemManagerTests/ShopCatalogDraftStyleSyncTests.swift`，三个类：

- `ShopCatalogDraftStyleSyncTests`（纯逻辑）：款式分组 / 拆分边界（跨系列、跨品类、复合色剥离）/
  继承系列标签 / 同款其他颜色；同步产物（价格整组、尺码表重编 id、颜色私有字段零改动、
  空值清除、字段选择、跳模板自身）。
- `ShopCatalogDraftStyleSyncStoreTests`（仓库层）：写目标不动模板、落盘可重载、
  已发布目标被跳过、**传错别款 id 被服务层拦下**、模板不存在抛 `sourceDraftNotFound`。
- `ShopCatalogDraftStyleSyncEndToEndTests`（端到端）：录生成色 → 同步另两色 → 三条各自发布 →
  三个颜色都读到同一份尺码表 / 面料 / 描述且各自带预约价，款式档案整款只有一条；
  以及**纯补价草稿发布后不清除既有款式档案**。

## 六、明确没做的事

- **没有**把「一系列草稿」重构成「一个款式草稿挂 N 个颜色草稿」的新实体。
  同款不同色在发布后本来就是 N 个独立商品（用户侧要能单独加购、单独进心愿），
  再引入一层「款式草稿」等于给同一份事实造第二个真相来源。
  本次用「分组 + 一键同步」拿到同样的录入体验，改动面小得多。
- 发布之后要改款式面料 / 描述，入口仍是「款式公共资料」（不是重发草稿）——
  草稿是录入期的载体，发布后它的内容不再决定线上产物。
