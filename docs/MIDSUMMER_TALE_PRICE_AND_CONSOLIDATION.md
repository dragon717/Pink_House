# 仲夏物语 · 商品归集与价格口径修复

> 对应两个问题：
> 1. **商品归集**：同一系列下的商品被拆成多条独立链接，要统一归集到同一个链接下展示
> 2. **价格**：要按真实来源把价格填对，并且**从根上**解决「价格缺失或错误」，
>    让后续同类价格不用反复修

---

## 一、商品归集：一个电商链接 = 一个商品

### 问题到底是什么

「樱花小羊」在淘宝上**是一个链接**（item `1032370386538`），点进去在「颜色分类」里
选 印花SK / 印花JSK / 段段JSK / 无腰OP / 内搭 / 开衫 / 围裙 / 罩裙 / 小物 —— 共 9 款，
价格随所选款式变化。

而在我们库里它被写成了 **5 个独立单品**（sk / jsk / blouse / apron / cardigan），
于是品牌页出现 5 张卡片、5 个详情页、5 条原文出处，各自还只有 1–2 个颜色选项。
上一轮做的规格面板因此发挥不出作用——每个「商品」里根本没有款式可挑。

### 修改后的模型

一个商品 = 一个电商链接，用**三组规格**把多款装进去：

| 规格组 | `role` | 作用 |
|---|---|---|
| 款式 | `variant` | 印花SK / 段段JSK / 无腰OP / 内搭 / 开衫 / 围裙 / 罩裙 / 小物 |
| 颜色分类 | `color` | 粉色 / 浅青色 / 奶白色 / 米色 |
| 尺码 | `size` | S / M / L / XL / 均码 |

- `variant` 是**新增**的角色（`MidsummerSpecRole.variant`）。
  它不映射到衣橱的配色或尺码字段，只做两件事：决定**入库名称**、决定**价格**。
- 三组之间靠 **SKU 表**联动：选了「内搭」就只有「奶白色」可选、尺码里也只有 S/M/L/XL；
  选了「小物」则尺码自动收敛为「均码」。灰化**只**来自组合不存在，
  不来自「卖完了」（我们不校验也不扣库存）。
- SKU 表里每一项带**该款的参考价**，所以价格是逐款的，不是商品一个价。

代码上的增量很小，因为上一轮的规格面板 + 解析器已经能处理任意组数与联动：

| 文件 | 改动 |
|---|---|
| `Models/Midsummer/MidsummerModels.swift` | 新增 `MidsummerSpecRole.variant`；`resolvedRole` 关键词加「款式 / 版型 / 款型」；单品加 `variantCount` |
| `Services/Midsummer/MidsummerSpecResolver.swift` | `wardrobeMapping` 处理 `.variant`（只进备注）；新增 `displayName(_:selection:)` 与 `selectedVariantName(_:of:)` |
| `Services/Midsummer/MidsummerWardrobeInsertion.swift` | 入库名称改成 `樱花小羊 段段JSK`，备注加「款式：…」 |
| `Views/Midsummer/MidsummerSeriesListView.swift` | 「全部单品」→「全部商品」；行内显示「含 9 个款式」；详情页头加「包含款式」与商品链接 |
| `Views/Midsummer/MidsummerBrandView.swift` | 卡片副标题显示款式数；详情页新增「查看商品链接」 |

### 注意事项（踩得到的坑）

- **不要把不同链接的款硬并成一个商品**。这里的依据是「同一系列 = 同一链接」，
  而我们**只有樱花小羊一条真实链接**（其余系列 `itemURL` 均为空）。
  所以归集是按系列做的近似，真实链接拿到后可能需要拆开——
  **野草莓初代与 2.0 是两代、很可能是两个链接**，这一点已写进该商品的
  `priceNote`，拿到真实链接后要回来复核。`MidsummerPriceIntegrityTests`
  里的 `testSeriesWithMultipleProductsMustHaveDistinctLinks` 会在
  「同系列多个商品却没有各自链接」时报错，防止悄悄退回拆分状态。
- **`variantCount` 只在有款式组且选项数 > 1 时才 > 1**，所以未归集的系列展示文案不会变。
- 归集后 `item.id` 就是**商品** id（`midsummer-2026-sakura-lamb`），
  原来的 5 个单品 id 全部消失。旧数据里没有别处引用它们，但**如果你在别处
  （书签、分享、埋点）用过那些 id，需要一并改**。
- 商品的价格可能**一个字段都没有**（价格全在 SKU 表里）。任何
  「`price == nil` 就当缺价」的判断都是错的——必须走 `hasPrice` / `priceRange`。

## 二、价格：先看清根因，再谈填数

### 根因有三条，都不是「少填了一个数字」

1. **一个字段装了三种钱**。`price` 同时被用来装现货价、第三方参考价、尾款，
   于是没人说得清「同一个 ¥320 到底是定金还是全款」。
2. **区间是手写的第二份数据**。系列有 `priceMin` / `priceMax`，单品也有价格，
   两边靠人肉对齐——改一处忘一处，就出现「系列显示 ¥388–499、点进去单品写 ¥499」。
3. **缺价没有强制说明**。查不到价格就留空，界面显示「价格待补充」，
   但没人记得为什么缺，下一个人还得从头查一遍。

### 修复后的规则

**规则 1：口径与采集日必填。** 落在 `price` / `deposit` / `balance` 上的数字，
必须同时有 `priceKind`（`shop` 商品页价 / `reference` 参考价）和
`priceCapturedOn`（`yyyy-MM-dd`）。出处复用已有的 `sourceURL`。
没有采集日的价格无法判断是否过期，所以采集日由 App 自动打戳，不依赖填表人记得写。

**规则 2：区间一律派生，不再存储。** `MidsummerSeriesDTO` 的
`priceMin` / `priceMax` **已删除**，`priceRange` 是计算属性：

```
系列区间 = min/max( 每个单品的「参考价/现货价」+ 每个 SKU 的逐款价 )
```

改一个单品价，商品与系列的区间一起变——不存在第二处需要同步。

**规则 3：定金与全款分列。** 定金是另一个维度，来源常常只给一个价格带
（「定金 7–139 元」），无法归到某一款上，所以系列层保留一对**显式**的
`depositMin` / `depositMax`，但必须同时写 `priceSource` 说明出处。
界面把两者分两行显示：`¥199–699` + `定金 ¥7–139`。
以前把 388 的预约定金和 499 的现货价合成「¥388–499」正是口径错误。

**规则 4：缺价必须说明。** 没有任何价格的单品，必须写 `priceNote` 或 `note`
说明原因（「公开渠道未查到」「仅有报道未给价」），否则构建红。

**规则 5：同一数字不许写两遍。** `price` 与 `balance` 相等时视为冗余，
清掉一份（来源说的是尾款就写 `balance`，是参考价就写 `price`）。

### 落地的守卫

`ItemManagerTests/MidsummerPriceIntegrityTests.swift` 把上面 5 条全部变成断言，
直接对种子 JSON 跑。这一层才是「以后同类价格不用反复修」的保障：
数字可以填错，但**口径不明、来源不明、缺项不说明**这三类错误会在构建阶段就被拦下。

### 界面上的呈现

- 卡片：有定金先显示定金（当下真正要付的钱），否则显示派生区间
- 系列页：价格区间一行，定金另起一行；新增「价格口径」一行写明这些数字的来源
- 详情页：`参考价 ¥329` 带口径前缀，下面一行小字写「参考价 · 采集于 2026-09-15」
  与口径备注（多来源冲突时的取舍理由）

## 三、樱花小羊的真实价格（本轮新填）

→ 派生区间 **¥199–699**。

### 为什么没有用淘宝链接里的 ¥119

淘宝分享链接（`https://e.tb.cn/h.8JmuwHMKIB4LK8H`）解开后，目标地址里带着
`id=1032370386538&price=119&sourceType=item`。这个 `119` 是**分享者所选规格的挂出价**
（定金口径的展示价），与上面 9 款的参考价不是同一口径，也对不上任何一款的全款价。

所以处理方式是**记录而不强行统一**：
- 逐款价格用图鉴参考价（可核验、逐款、口径一致）
- 淘宝那个数字记在 `priceNote` 里，说明它与逐款价不同源，没有被当成某一款的全款
- 定金价带 `¥7–139` 来自「三坑新语 2026-06 淘宝 lolita 单品榜」，
  以「定金」口径单独登记在 `depositMin` / `depositMax`

> 想把 119 换成正价，需要拿到登录态下的商品页读 SKU 价——
> 未登录会话会被 302 到 `login.taobao.com`（实测见
> `MIDSUMMER_TALE_SPEC_SELECTION.md` §5）。届时只需改 SKU 表里的 `price`
> 与 `priceCapturedOn`，其余（商品区间、系列区间、卡片文案）自动跟着变。
