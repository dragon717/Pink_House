# 上新咨询双方案设计（仲夏物语 → 衣橱转化）

> 2026-09-15 · 目标：借助上新咨询场景，把顾客的衣物沉淀进自有账本体系（衣橱）。
> 两套方案表达方式与切入角度不同，但共用同一套数据（`MidsummerSeriesDTO`/`MidsummerItemDTO`），可配套使用。

---

## 一、方案 A：「上新速报」——资讯快讯流（客观 · 效率向）

### 定位与差异点
- **切入角度**：时间线快讯。按 图透 → 预约 → 尾款 → 出货 → 再贩 的阶段推进，复用现有 `MidsummerStage` 六档。
- **表达方式**：客观、克制、数据优先。像"新品上市公告板"，每条快讯 = 一个系列的状态变化。
- **侧重**：不错过、可溯源、数据完整（价格表/尺码表是页面一等公民）。

### 页面结构
1. 快讯流卡片：系列封面 + 阶段徽章 + 派生价格区间（`priceRange`，分列定金区间）+ 剩余预约天数。
2. 系列详情页：
   - **整体价格表**（必含）：从全系列单品自动派生的表格，按「现货价 / 全款预约 / 定金尾款预约」三列分组（对应 2026-09-15 定的价格归类）；
   - **单品尺码表**（必含）：每个单品（OP/JSK/SK/小物/套装）卡片内折叠面板，展开即尺码表；无数据时显示"待运营者补充"入口；
   - 每个单品右侧保留 `bag.badge.plus` 快速入库（已有能力，`MidsummerWardrobeInserter.quickInsert`）。

### 入橱关键环节与话术
| 环节 | 触点 | 话术要点 |
|---|---|---|
| 预约期 | 快讯卡「预约提醒」 | "预约后不用记日子——尾款日在衣橱里自动提醒你。" |
| 出货期 | 出货快讯推送 | "已预约？点入库管理收货，拆箱即入账。" |
| 全款预约 | 价格表全款列 | "全款预约的账也记得清：衣橱单独统计，不和定金尾款混。" |

---

## 二、方案 B：「种草手帐」——搭配内容流（主观 · 场景向）

### 定位与差异点
- **切入角度**：穿搭企划。以"这套怎么穿"为单位组织内容（如「秋季开学 JSK 三套搭法」），单品是搭配方案里的零件。
- **表达方式**：主观、有温度、场景化。手帐排版（复用 `MidsummerTheme` 主题色），带简短点评（版型/柄图/体感）。
- **侧重**：激发心动、辅助决策（尺码推荐、预算规划）。

### 页面结构
1. 手帐卡片：搭配主图 + 点评文字 + 所含单品胶囊（点开跳方案 A 的系列详情看尺码/价格表）。
2. 搭配详情：单品清单 + 合计预算（现货价合计，预约款标注"定金+尾款"拆分）。
3. 「收藏这套搭配」→ 生成心愿清单条目。

### 入橱关键环节与话术
| 环节 | 触点 | 话术要点 |
|---|---|---|
| 心动收藏 | 搭配卡「放进心愿单」 | "心愿单就是衣橱的前厅——先放进来，买不买都不亏。" |
| 尺码决策 | 尺码推荐条 | "把你的身高体重存进衣橱档案，下次上新直接告诉你穿什么码。" |
| 预算规划 | 合计预算条 | "点『加入心愿尾款』，月底它自动帮你算清要留多少钱。" |

## 三、两套方案的衔接逻辑

**A 是货架，B 是橱窗；B 产生心愿，A 完成交易，衣橱承接一切。**

1. **数据同源**：B 的搭配卡只引用 A 的系列/单品 DTO，不另存一份数据；价格表/尺码表只在 A 维护，B 展示时实时引用。
2. **双向跳转**：B 搭配卡上的单品胶囊 → 跳 A 的系列详情（看尺码表/价格表）；A 快讯的"搭配灵感"角标 → 跳 B 对应手帐。
3. **转化漏斗**：B 种草（收藏/心愿，轻动作）→ 心愿条目本身即衣橱预记录（`isDepositPlan` 前置态）→ 顾客回到 A 查价格表决定购买 → 定金/全款预约一键入库（`MidsummerWardrobeInsertion` 形态 A/B）→ 尾款记账、收货管理全在衣橱闭环。

## 四、必备资料：尺码表 + 整体价格表

### 1. 数据模型（小扩展）
- `MidsummerItemDTO` 增加 `sizeChart: MidsummerSizeChart?`（结构化表：`customName/身高/胸长/袖长/裙长…` 行列，或图片 URL，两者兼容）。
- 落库映射：一键入库时写入 `Clothing.sizeChartImagePath`（**字段已存在**，衣橱侧零改动）。
- 系列级价格表**不需要新字段**：`MidsummerSeriesDTO.priceRange` + 各单品 `price/deposit/balance/priceKind` 已够派生，渲染成表即可。

### 2. 获取渠道（优先级从高到低）
1. **淘宝商家详情页自动采集**：走本项目 `scrapers/` 管线（`run_collect.py -p taobao -k <款名>`）——`items.json` 已含 `title/price/detail_url/images`，尺码表是详情页里的 alicdn 图片，补一个"详情页尺码表图片识别→存入 sizeChart"的映射步骤即可。图片 CDN 无需登录，采集稳定。
2. **运营者人工补充**：采集不到（新品页未挂尺码表 / 图片是拼接长图无法结构化）时走人工入口（见下节）。
3. **兜底标注**：两者都没有时，单品页显示"尺码表待补充"，**不虚构数据**（与现有 `verified` 字段的诚实原则一致）。

## 五、运营者补充上传入口（白名单门控）

### 入口位置（三处，越靠近缺数据处越好）
1. **单品规格抽屉底部**（`MidsummerSpecPanel`）：无尺码表的单品显示"尺码表待补充 · 运营者补录"按钮；
2. **系列详情页"…"菜单**：新增「补录尺码/价格表」项，进入补录模式（复用 `MidsummerContributeView(existingSeries:)`，已在）；
3. **生成的分享/深链**：条目分享链接携带 `pinkhouse://midsummer/series/<id>/contribute` 路径，白名单用户点开直达补录表单，普通用户落在系列页。

### 门控与使用方式
- **门控**：复用现有 `store.isAdminUser` + CloudKit 创作者角色白名单（`MIDSUMMER_TALE_CLOUDKIT_SETUP.md`），非白名单用户三处入口均不渲染。
- **使用方式**：点补录 → 选单品 → 两个动作：①「拍照/选图传尺码表」（复用封面图的 PhotosPicker + 1200px 压缩管线，直接落 `sizeChart` 图片）；②「补价格」（复用现有单品价格三字段 + 价格口径分段控件，含全款预约口径）→ 提交写 CloudKit，`verified` 置 true 并记录 `priceCapturedOn`。
- **防呆**：补录表单沿用现有校验（系列名沿用、出处必填、单品款名必填——即 2026-09-15 排查过的那处校验，文案已按"款名"修正）。

---

## 六、落地优先级建议

1. P0：报错文案修正 + 补录入口（第 1、2 处）——纯复用，改动小；
2. P1：系列价格表渲染（数据已齐）+ scrapers 尺码表图片映射；
3. P2：方案 B 手帐流 + 心愿单入橱 + 全款预约口径（涉及 CloudKit 字段与 `MidsummerWardrobeInsertion` 的 `isFullPaymentReservation` 映射）。
