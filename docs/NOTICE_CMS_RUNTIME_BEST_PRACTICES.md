# 公告系统运行链路与排查最佳实践

> 更新时间：2026-04-07  
> 用途：沉淀当前公告系统在 Pink_House 中已经验证过的运行思路、排查顺序和实现约束，避免以后重复踩同一类 CloudKit / 本地缓存 / 弹窗状态问题。

## 1. 先记住这张全貌图

当前公告链路不是“云端一来就直接弹”，而是 4 段串起来：

1. `CloudKit Public Database`
   - 公告主数据来源
   - 管理员发布、更新、停用都落这里
2. `SwiftData 本地缓存`
   - App 实际读列表、筛选候选、展示 UI 都先读本地
   - 所以“管理页能看到公告”不等于“本次云同步成功”
3. `CloudKit Private Database + UserDefaults`
   - 存普通用户的已读、确认、dismiss、展示次数
4. `NoticePopupManager`
   - 只负责根据“当前本地公告 + 当前用户状态”决定要不要弹

结论：

1. “看不到公告”先别直接怀疑弹窗
2. 必须先分清是拉取问题、合并问题、候选问题，还是触发问题

## 2. 当前已经稳定下来的行为基线

### 2.1 云端拉取

当前公告查询采用“分层降级 + 本地排序”：

1. 先尝试带业务排序字段的查询
2. 若 CloudKit 报排序字段不可用，则降级为无排序查询
3. 若业务字段查询仍报 `参数无效`，再降级为更保守的标题查询
4. 最终统一在本地排序

这样做的原因：

1. CloudKit Dashboard 的索引状态经常滞后
2. 某些字段可能已存在，但还没被标记为 `Sortable / Queryable`
3. 不能因为一个排序字段没配好，就让整条公告链路彻底失效

### 2.2 本地列表来源

管理页“现有公告”现在明确区分来源：

1. `本次已从云同步`
2. `本地缓存`
3. `仅本地未同步`

这三个标签的意义是：

1. 先确认这条公告是不是本次真的从云端回来了
2. 避免把旧缓存误判成“云同步成功”
3. 方便定位删除失败、回流、脏缓存残留

### 2.3 删除语义

当前删除不是物理删，而是“停用并隐藏”：

1. 云端公告删除时，改成 `archived`
2. 管理页“现有公告”默认不显示 `archived`
3. 仅本地未同步公告，直接本地删除
4. 若云端记录已不存在，则清理对应本地缓存，避免假数据回流

### 2.4 管理员弹窗验证

管理员现在不再走“完全跳过弹窗”，而是走“验证模式弹窗”：

1. 管理员能在发布后重启 App 立刻验证弹窗是否生效
2. 同一条公告版本，管理员只验证一次
3. 验证模式不会写入 `read / acknowledged / dismissed / presentationCount`

这样管理员既能确认“公告确实发出去了”，又不会污染用户状态模型。

## 3. 排查时必须坚持的固定顺序

任何“杀端重进没公告”“公告拉到了但没弹”“删除了又回来”问题，都固定按下面顺序查：

1. 先查云端拉取是否成功
2. 再查本地是否已正确合并
3. 再查公告是否满足 modal 候选规则
4. 再查同步结束后有没有重新评估弹窗
5. 最后才查用户状态是否把它挡掉

不要跳步。

原因很简单：

1. 云端没拉到，后面全查都没意义
2. 拉到了但没合并，UI 仍然看不到
3. 合并了但字段不合法，根本不会进入 modal 候选
4. 候选合法但触发时机错了，仍然不会弹
5. 全都对了，才轮到已读/展示状态

## 4. 这次问题沉淀出的关键最佳实践

### 4.1 查询失败时，不要只看最终报错

`参数无效` 往往不是“代码完全错了”，而是 CloudKit 侧某个字段没有正确配置查询能力。

优先看这几类日志：

1. `公告排序查询失败，降级为...`
2. `成功拉取 X 条云端公告`
3. `本次云端公告拉取失败，跳过本地合并`

只要后面已经出现“成功拉取”，就说明当前主问题已经不是拉取失败，而是后续链路。

### 4.2 不要把 `recordName` 当成查询排序字段依赖

`recordName` 很容易在 CloudKit 上触发“不可查询 / 不可排序”。

更稳的做法是：

1. 用业务字段做查询兜底，例如 `createdAt`、`title`
2. 不把 `recordName` 放进筛选或排序主链路
3. `recordName` 只作为本地和云端记录关联键

### 4.3 云端同步成功，不等于弹窗会弹

弹窗是否出现，还取决于：

1. 本地公告列表是否已经刷新
2. `isSyncing` 是否已经结束
3. 当前用户身份是否已解析完成
4. 公告是否进入 `latestEligibleModalNotice()`
5. 普通用户是否受 30 秒节流限制

这也是为什么当前实现改成了：

1. 先同步并合并本地数据
2. 再刷新本地公告列表
3. 最后才结束 `isSyncing`
4. 结束后重新评估弹窗

### 4.4 管理员验证逻辑必须和用户状态逻辑解耦

管理员的目标是“验证公告已成功发布”，不是“模拟真实用户已经消费过公告”。

因此最佳实践是：

1. 管理员可立即验证
2. 管理员验证不写已读状态
3. 管理员验证不写展示次数
4. 但管理员同一版本只自动验证一次，避免每次重启都反复弹

### 4.5 软删除必须防回流

如果本地已删、云端旧版本还在，或者本地删了但云端停用失败，就可能出现“删了又回来”。

当前稳妥做法是：

1. 本地已是 `archived`，且本地更新时间不早于云端时，优先保留本地删除状态
2. 只有云端拉取成功后，才清理“云端已不存在”的本地缓存
3. 对于本地未上云记录，直接本地删除，不走云端停用

## 5. 最值得看的日志锚点

排查时优先搜索这些日志：

1. `开始同步公告`
2. `成功拉取`
3. `公告同步完成`
4. `service.notices changed`
5. `管理员命中可验证弹窗`
6. `以管理员验证模式显示公告弹窗`
7. `公告弹窗已显示`
8. `管理员验证模式关闭公告，不记录已读/展示状态`

如果日志停在“成功拉取”之前，先查 CloudKit。  
如果停在“成功拉取”之后但没有“命中可验证弹窗”或“显示公告弹窗”，再查候选筛选和触发时机。

---

## 6. 以后继续扩展时的落地约束

后续如果继续做公告中心、banner、正式入口，保持这几个约束不要回退：

1. 来源标签继续保留，不要再把本地缓存和本次云同步混成一类
2. 管理员验证模式继续保留，不要重新并回普通用户已读逻辑
3. 删除继续走“停用并隐藏”，不要在没有审计的情况下直接物理删线上记录
4. 云端查询继续保留降级链路，不要重新把某个单一排序查询当成唯一入口
5. 日志继续区分“拉取成功”“本地刷新成功”“候选命中”“弹窗显示”“状态写入”

---

## 7. 最简心智模型

一句话记住当前系统：

“公告先从云端拉下来，合并成本地缓存，再按规则挑出能弹的候选，最后根据用户或管理员身份决定怎么弹、记不记状态。”

只要这 4 段里任一段断掉，用户看到的现象都可能是“没有公告”。
