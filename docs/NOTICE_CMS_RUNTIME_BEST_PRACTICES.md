# 公告系统运行链路与排查最佳实践

> 更新时间：2026-04-23  
> 用途：沉淀当前公告系统在 Pink_House 中已经验证过的运行思路、排查顺序和实现约束，避免以后重复踩同一类 CloudKit / 本地缓存 / 弹窗状态问题。

## 1. 先记住这张全貌图

当前公告链路不是“云端一来就直接弹”，而是 4 段串起来：

1. `CloudKit Public Database`
   - 公告主数据来源
   - 管理员发布、更新、停用都落这里
2. `NoticeService` 内存集合
   - App 运行时读列表、筛选候选、展示 UI 都以本次 CloudKit 拉取后的内存集合为准
   - 旧版 `SwiftData Notice` 本地缓存不再参与启动读取，避免 TestFlight 覆盖安装后旧 schema 在 CoreData materialization 阶段直接 abort
3. `CloudKit Private Database + UserDefaults`
   - 存普通用户的已读、确认、dismiss、展示次数
4. `NoticePopupManager`
   - 只负责根据“当前内存公告 + 当前用户状态”决定要不要弹

结论：

1. “看不到公告”先别直接怀疑弹窗
2. 必须先分清是拉取问题、内存集合刷新问题、候选问题，还是触发问题

## 2. 当前已经稳定下来的行为基线

### 2.1 云端拉取

当前公告查询采用“分层降级 + 本地排序”：

1. 先尝试带业务排序字段的查询
2. 若 CloudKit 报排序字段不可用，则降级为无排序查询
3. 若业务字段查询仍报 `参数无效`，再降级为更保守的标题查询
4. 最终统一在本地排序

这样做的原因：

1. CloudKit Dashboard 的索引状态经常滞后
2. 某些字段可能已存在，但还没被标记为 `Sortable / Queryable`
3. 不能因为一个排序字段没配好，就让整条公告链路彻底失效

### 2.2 运行时列表来源

运行时公告列表现在以 `NoticeService.managedNotices / notices` 内存集合为准：

1. `NoticeService.setup()` 触发 `syncIfNeeded()`
2. `NoticeCloudKitService.fetchCloudNotices()` 从 Public Database 拉取公告
3. 拉取成功后，`NoticeService.refreshCollections(from:)` 刷新内存集合
4. 拉取失败时，保留现有内存集合，不读取旧 SwiftData `Notice` 缓存兜底

这样做的意义是：

1. 避免旧 TestFlight 安装留下的 `Notice` 本地 schema 在 iOS 17 真机上导致启动崩溃
2. 公告属于运营内容，云端是权威来源，短时间离线不应优先于启动稳定性
3. 排查“静默不弹”时，先看云端拉取和内存集合刷新，而不是先查本地 SwiftData 表

### 2.3 删除语义

当前删除不是物理删，而是“停用并隐藏”：

1. 云端公告删除时，改成 `archived`
2. 管理页“现有公告”默认不显示 `archived`
3. 仅内存未同步公告，直接从内存集合移除
4. 若云端记录已不存在，则清理对应内存公告，避免假数据回流

### 2.4 管理员弹窗验证

管理员现在不再走“完全跳过弹窗”，而是走“验证模式弹窗”：

1. 管理员能在发布后重启 App 立刻验证弹窗是否生效
2. 同一条公告版本，管理员只验证一次
3. 验证模式不会写入 `read / acknowledged / dismissed / presentationCount`

这样管理员既能确认“公告确实发出去了”，又不会污染用户状态模型。

### 2.5 普通用户新同步公告

普通用户仍然保留“冷启动尽量不要立刻打断”的原则，但新增了一条例外：

1. 若本次启动刚刚从云端同步到了新的 `modal` 公告
2. 且这条公告此前没有展示过
3. 则允许跳过冷启动 30 秒延迟，直接尝试弹出
4. 若本次弹出就是为了承接这条“新同步且未展示过”的公告，也可跳过“今日全局 modal 次数上限”

这样做的原因：

1. 正式公告发出去后，普通用户不应因为固定延迟而长期误以为“公告没有生效”
2. 但仍要保留“同一条公告不要重复弹”的去重逻辑
3. “新公告优先送达”与“日常减少打断”要分开治理，不能用同一条全局限制把真正的新公告吞掉

### 2.6 已读状态同步

公告已读状态在 `CloudKit Private Database` 中同步时，不再依赖 `recordName` 字段可查询。

当前更稳的做法是：

1. 使用 `CKQueryOperation` 分页拉取
2. 只请求真正需要的 `desiredKeys`
3. 用 `recordID.recordName` 反推出稳定状态 key
4. 不把 `recordName` 当成查询条件或可排序字段前提

这样可以避免：

1. `Field 'recordName' is not marked queryable`
2. 普通用户已读状态同步失败后，进一步干扰弹窗排查

## 3. 排查时必须坚持的固定顺序

任何“杀端重进没公告”“公告拉到了但没弹”“删除了又回来”问题，都固定按下面顺序查：

1. 先查云端拉取是否成功
2. 再查本地是否已正确合并
3. 再查公告是否满足 modal 候选规则
4. 再查同步结束后有没有重新评估弹窗
5. 最后才查用户状态是否把它挡掉

不要跳步。

原因很简单：

1. 云端没拉到，后面全查都没意义
2. 拉到了但没合并，UI 仍然看不到
3. 合并了但字段不合法，根本不会进入 modal 候选
4. 候选合法但触发时机错了，仍然不会弹
5. 全都对了，才轮到已读/展示状态

## 4. 这次问题沉淀出的关键最佳实践

### 4.1 查询失败时，不要只看最终报错

`参数无效` 往往不是“代码完全错了”，而是 CloudKit 侧某个字段没有正确配置查询能力。

优先看这几类日志：

1. `公告排序查询失败，降级为...`
2. `成功拉取 X 条云端公告`
3. `本次云端公告拉取失败，保留现有内存公告`

只要后面已经出现“成功拉取”，就说明当前主问题已经不是拉取失败，而是后续链路。

### 4.2 不要把 `recordName` 当成查询排序字段依赖

`recordName` 很容易在 CloudKit 上触发“不可查询 / 不可排序”。

更稳的做法是：

1. 用业务字段做查询兜底，例如 `createdAt`、`title`
2. 不把 `recordName` 放进筛选或排序主链路
3. `recordName` 只作为本地和云端记录关联键

### 4.3 云端同步成功，不等于弹窗会弹

弹窗是否出现，还取决于：

1. 内存公告列表是否已经刷新
2. `isSyncing` 是否已经结束
3. 当前用户身份是否已解析完成
4. 公告是否进入 `latestEligibleModalNotice()`
5. 普通用户是否受 30 秒节流限制
6. 这条公告是不是“本次云端新同步到”的新公告

这也是为什么当前实现改成了：

1. 先同步云端公告
2. 拉取成功后刷新内存公告列表
3. 最后才结束 `isSyncing`
4. 结束后重新评估弹窗

对普通用户再补一条：

1. 若命中“本次新同步到的新公告，且此前未展示”，可跳过 30 秒延迟
2. 若不是这类公告，仍按原来的冷启动节流规则执行

### 4.4 管理员验证逻辑必须和用户状态逻辑解耦

管理员的目标是“验证公告已成功发布”，不是“模拟真实用户已经消费过公告”。

因此最佳实践是：

1. 管理员可立即验证
2. 管理员验证不写已读状态
3. 管理员验证不写展示次数
4. 但管理员同一版本只自动验证一次，避免每次重启都反复弹

### 4.5 旧版本状态不要误伤新版本

这次排查里最容易忽略的一类问题是：

1. 老公告版本曾被 `dismissed`
2. 或老版本已经记录过 `presentationCount`
3. 新版本重新发布后，却被旧状态直接拦掉

当前更稳的做法是：

1. 所有 `read / acknowledged / dismissed / presentationCount` 判断，都优先看当前版本对应的 `readTrackingKey`
2. 只有当前快照确实属于“这条公告当前版本”时，才允许拿它拦截弹窗
3. 旧版本状态可以做兼容迁移，但不能默认直接阻断新版本

一句话：

“同一条公告换了版本后，旧版本的消费状态不能天然继承为新版本的阻断条件。”

### 4.6 软删除必须防回流

如果内存中已移除、云端旧版本还在，或者云端停用失败，就可能出现“删了又回来”。

当前稳妥做法是：

1. 云端停用成功后重新从 CloudKit 拉取权威列表
2. 云端记录已不存在时，从内存集合移除
3. 对于未上云记录，直接从内存集合移除，不走云端停用

## 5. 最值得看的日志锚点

排查时优先搜索这些日志：

1. `开始同步公告`
2. `成功拉取`
3. `公告云端拉取完成，本地 SwiftData 缓存已跳过`
4. `service.notices changed`
5. `普通用户命中新同步公告，跳过冷启动延迟`
6. `管理员命中可验证弹窗`
7. `以管理员验证模式显示公告弹窗`
8. `公告不满足 modal 基础规则`
9. `公告因用户状态被拦截`
10. `公告因当前版本已展示过被拦截`
11. `公告因今日全局弹窗次数上限被拦截`
12. `公告弹窗已显示`
13. `管理员验证模式关闭公告，不记录已读/展示状态`

如果日志停在“成功拉取”之前，先查 CloudKit。  
如果停在“成功拉取”之后但没有“命中可验证弹窗”或“显示公告弹窗”，再查候选筛选和触发时机。  
如果已经看到 `tryShowNotice called for ...`，下一步就直接看上面 8-11 这几条精细化拦截日志，不要再只靠旧的“公告不满足弹窗条件，跳过”做粗判断。

## 6. 以后继续扩展时的落地约束

后续如果继续做公告中心、banner、正式入口，保持这几个约束不要回退：

1. 运行时不要恢复为启动读取 SwiftData `Notice` 缓存，旧 schema 风险高于公告离线缓存收益
2. 管理员验证模式继续保留，不要重新并回普通用户已读逻辑
3. 删除继续走“停用并隐藏”，不要在没有审计的情况下直接物理删线上记录
4. 云端查询继续保留降级链路，不要重新把某个单一排序查询当成唯一入口
5. 日志继续区分“拉取成功”“内存刷新成功”“候选命中”“弹窗显示”“状态写入”

---

## 7. 最简心智模型

一句话记住当前系统：

“公告先从云端拉下来，刷新为运行时内存集合，再按规则挑出能弹的候选，最后根据用户或管理员身份决定怎么弹、记不记状态。”

只要这 4 段里任一段断掉，用户看到的现象都可能是“没有公告”。
