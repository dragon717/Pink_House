# 商品改名未生效 · 根因与整款同步修复（需求实现说明）

> 需求原文：「修改名称后，相关信息未发生任何变化。请排查并修复名称修改功能：说明名称更新未
> 生效的原因，确保修改后与名称关联的所有相关数据和显示内容都能正确同步更新，并补全必要的
> 验证方式。」
>
> 配图三张（同一款商品的改名前后）：
> ① 商品管理页长按「背心裙 [黄色]」→ 菜单「编辑基础（名称/分类）」；
> ② 「编辑商品」弹窗把名称改成「黄色蜜糖邦尼背心裙」→ 保存；
> ③ **点菜式选购页的标题依然是「背心裙」**，商品管理里的款式行标题也没变。

---

## 一、结论先说

**改名功能根本没坏 —— 坏的是「名称」这个字段没人读。**

- 界面上的**每一处标题都只显示「款式名」**（`designName`），这是 2026-09-23 就定下的硬规则：
  > 「标题文字永远等于款式名，颜色不参与标题文字；同款颜色数 > 1 时追加「· N 色」标注」
  > —— `ShopCatalogTitlePresentation.swift`

- 而「编辑基础（名称/分类）」弹窗里的「名称」写的是 `name` 字段（完整 SKU 名，含颜色词），
  **一个字节都没碰 `designName`**。

- 更关键的是：发布商品时 `designName` 被**无条件写成非空的显式值**
  （`ShopCatalogOps.swift` 发布路径 → `resolveDesignName(explicit:name:)`，而这个函数
  **永不返回 nil**，识别不出颜色词时兜底回退整名）。于是发布之后：
  `designName` 恒为非空 → `designName(of:)` 永远走「显式优先」分支 → **`name` 被永久遮蔽**。

**两处叠加 = 改名写进一个没有任何界面读的字段，所以「什么都不会变」。**

修复后用户截图里的那一步会变成：名称填「黄色蜜糖邦尼背心裙」→ 保存 → 点菜页标题变成
**「蜜糖邦尼背心裙」**（同款 2 色时显示「蜜糖邦尼背心裙 · 2 色」），颜色仍单独显示为
「黄色 / 粉色」标签。

## 二、根因（两处叠加，缺一不可）

| # | 位置 | 事实 |
|---|---|---|
| 1 | 展示侧 | 所有标题走 `ShopCatalogTitleResolver` → `ShopCatalogSameDesignGrouper.designName(of:)` = 「显式 `designName` 优先，否则按 `name` 剥离颜色词派生」 |
| 2 | 写入侧 | 发布路径写 `designName = resolveDesignName(explicit:name:)`，**永不返回 nil**（`baseName(for:)` 兜底回退整名）→ `designName` 恒为非空显式值 |
| 3 | 写入侧 | 两条改名入口（`upsertEntity`「基础编辑」/ `updatePublishedProduct`「深度编辑」）都**只写 `name` + `category`**，没有任何一处写 `designName` |

推论（第 1 + 2 条）：`baseName(for: name)` 这条派生分支**永远不会被执行**，
`name` 对显示完全没有影响力。

**为什么不能「顺手让弹窗也改一下 `designName` 就完事」**（这是最容易走错的一步）：

`designName` 是**款式（SPU）身份**，不是某个颜色的私有属性 ——

- `designKey` = `category | designName`（`ShopCatalogSameDesignGrouper`），
  列表款式组、点菜页合并卡、详情页「同款兄弟」轮播全靠它；
- `styleKey` = `seriesID | category | designName`（`ShopCatalogStyleProfileSharing`），
  款式档案（面料 / 款式描述）的 **`id` 就是它**；
- 尺码表的共享范围（`ShopCatalogSizeChartSharing.designScope`）也按 `designKey` 现算。

**只改被点中的那一个颜色**会同时造成两类事故：

1. 标题依旧不变（因为 `name` 才是它改的那个字段）——就是用户看到的；
2. 一旦真的改到 `designName`，就会把「2 色一款」**当场拆成两个单色款**，
   并让款式档案（面料 / 款式描述）与尺码表的共享范围**同时断链**
   —— 界面上表现为「改个名字，面料和尺码表都不见了」。

所以正确做法只有一条：**改名 = 款式级操作，一次落盘、整款生效。**

## 三、唯一口径（本次建立的机制）

新增 `ItemManager/Services/ShopCatalog/ShopCatalogProductRename.swift`（`nonisolated` 纯逻辑，
可单测），把改名收口成一份**计划**；界面弹窗的预览文案与落盘**共用同一份计划**
（沿用项目既有惯例：「删除」的预检与执行共用 `plan*Deletion`）。

### 3.1 名称 → 款式名

「名称」字段继续是**完整 SKU 名**（可含颜色词），款式名由它派生：

```
名称「黄色蜜糖邦尼背心裙」── baseName(for:) 剥离颜色词 ──▶ 款式名「蜜糖邦尼背心裙」
```

这与录入端 `ShopCatalogStyleEntryView` 的
`draft.name = "\(entry.color)\(designName)"` + `draft.designName = designName`
**是同一套口径**，不是新引入的规则。

### 3.2 七条收口

| # | 规则 | 为什么 |
|---|---|---|
| 1 | 款式名 = 名称剥离颜色词 | 与录入端一致；标题不含颜色是既有硬规则 |
| 2 | **扇出整款**（同系列 + 同品类 + 同款式名，**含已归档**） | 归档颜色留在旧款名上，等它被复活时就会把一款拆成两款 |
| 3 | 兄弟颜色的名字**定向替换**（旧款名 → 新款名），颜色词及其位置原样保留 | 「背心裙粉色」→「蜜糖邦尼背心裙粉色」，不改写颜色词的写法 |
| 4 | **品类一起改** | `designKey` 含品类，品类同样是款式级属性 |
| 5 | 名称**没被改动**时沿用现有款式名 | 存量里存在「款式名 ≠ 名称剥离颜色词」的人工命名（如名称「粉色款」+ 款式名「花花款」），重新派生会把它们**无声改掉**；深度编辑只改图片时走的正是这条分支 |
| 6 | 款式档案**按新键迁移**（删旧 id + 写新 id）；目标键已有档案时**无损合并**（目标值优先、补空缺字段） | 款式档案的 `id` 就是款式键，改名等于换主键；不迁移就是孤儿 |
| 7 | 衣橱 / 心愿记录**不跟着改**，但**如实告知条数** | 那是加入时的名字快照（`ShopCatalogTitlePresentation.swift` 口径 3 的刻意例外），且 `Clothing` 按 `catalogProductID` 引用商品、改名不断链 |

尺码表**不需要数据迁移**：它的行按 `productID` 存，共享范围由款式键现算；整款一起改，
款式键仍是同一个等价类。

### 3.3 两个必须摆对顺序的地方（`updatePublishedProduct`）

```swift
applyRenamePlan(renamePlan, overlay: &overlay)                 // ① 整款先落进覆盖层
let renamedProduct = renamePlan.products.first ?? updated
applySizeChart(sizeChart, for: renamedProduct, overlay: &overlay)  // ② 再算尺码表范围
```

- **① 必须在 ② 之前**：`writeTargetCatalog` 是按覆盖层现算的，改名还没写进覆盖层时，
  款式范围里只有自己一个颜色 → 尺码表只会扇出到一行。
- **② 必须传改名后的那一份**：局部变量 `updated` 的 `designName` 还是旧值，
  拿它去比款式键会和刚写进去的新键对不上 → 范围同样塌成自己一个人。

### 3.4 弹窗预览（让用户看见结果，不许静默）

改名弹窗的 `message` 用同一份计划现算，例如：

```
款式名：背心裙 → 蜜糖邦尼背心裙
同款其余 1 个颜色一并更新（整款共 2 色）
款式公共资料（面料 / 款式描述）随款式名一起迁移
颜色标签：黄色（标题文字不含颜色）
```

新名称里没有颜色词时改成明确警告：`⚠️ 新名称里没有颜色词，该商品将不再显示颜色标签`。

保存后的 toast 如实回报，例如：

```
已把款式名改为「蜜糖邦尼背心裙」（原「背心裙」）；同款 2 个颜色（含其余 1 色）一并更新
；已加入衣橱 / 心愿的 N 条记录保留加入时的名字（可在衣橱内单独改）
```

### 顺带修掉的一个隐患（已整组收口）

改名弹窗原来是 `.alert(isPresented:)` **挂在 `ProductManageRow` 上**的。
行视图是惰性 + 可复用的：列表一重排（滚动 / 切后台 / 跳系统相册返回），行视图重建，
挂在行上的弹窗连同它的 `@State`（`draftName`）一起归零 —— 名称输入到一半就会丢。

本次把**这一行上的全部模态**都上移到页面级（`.workbuddy/memory/RULES.md`
「表单编辑中快照与 sheet 呈现位置」那条红线的完整收口）：

| 原位置（`ProductManageRow` 行内） | 现位置（`ShopCatalogSeriesProductsView` 页面级） |
|---|---|
| `.alert("编辑商品")` + `draftName` / `draftCategory` | `.alert(isPresented: $showsRenameProduct)` + 页面级草稿 |
| `.sheet` 深度编辑（`showsDeepEdit`） | `.sheet(item: $productSheet)` → `ProductRowSheet.deepEdit` |
| `.sheet` 价格修正（`showsPriceCorrection`） | `ProductRowSheet.priceCorrection` |
| `.sheet` 追加销售记录（`showsSaleRecordAppend`） | `ProductRowSheet.saleRecordAppend` |
| `.confirmationDialog` 归档（`showsArchiveConfirm`） | `.confirmationDialog(presenting: $productConfirm)` → `ProductRowConfirm.archive` |
| `.confirmationDialog` 删除（`showsDeleteConfirm`） | `ProductRowConfirm.delete` |

两个 `Identifiable` 枚举（`ProductRowSheet` / `ProductRowConfirm`）**带上商品本身**，
因此不需要再维护一个「是不是这个商品」的平行 `@State` —— 那种双状态一旦不同步，
就会弹出**别的商品**的表单，而这类 bug 极难复现。确认框标题随目标变，所以用
`presenting:` 拿目标现算，不写死。

`ProductManageRow` 因此退化成**只渲染 + 发意图**的纯视图
（`onEditBasics` / `onSheet` / `onConfirm` 三个回调，不再持有任何模态 `@State`）。

也没有跑 XCUITest 的 UI 用例。原因与 09-24 遮挡排查时相同 —— 本机 `vm.swapusage`
总 8G 常年已用 6.5G+，`xcodebuild test` 会触发 `PruneExplicitPrecompiledModules` →
模块全量重编 → 静默卡死；本轮全程只用 `test-without-building` 绕开该阶段。

**已有的证据边界**：§7.3 覆盖的是「逻辑 + 接线」层 —— 端到端用例用的是**真实
`ShopCatalogStore` + 真实发布链路 + 真实覆盖层落盘**，断言读的也是 Store 的合并视图
（即界面真正消费的那份数据），所以「改名后点菜页标题会变」这件事在数据层已被证明。
**没被证明的**是「SwiftUI 视图确实重新渲染了」。改名走
`ShopCatalogDraftStore.renameProduct` → `saveOverlay` → `ShopCatalogStore.shared.reloadWithOverlay()`，
与既有的「归档 / 删除 / 价格修正」同一条刷新链路（那些功能在真机上都是即时刷新的）。

**复跑配方**（内存宽裕时）：

```bash
# 1) 注入验收种子到**构建产物**（Bundle 种子是空壳，不改仓库资源）
#    种子内容 = ShopCatalogSeedFixture.jsonString + 补足数量让列表溢出屏幕
# 2) 先编，后注入，再跑（顺序不能反 —— 重新构建会把注入的种子覆盖回去）
xcodebuild -scheme ItemManager -destination 'platform=iOS Simulator,id=FA7332BE-B29E-4879-A139-C68A24314DB1' \
  -derivedDataPath build/DerivedData ... build-for-testing
# 3) 关掉模拟器再编、编完再启（模拟器自身吃 2–4G，与编译器同场最易崩）
xcrun simctl shutdown all
# 4) 手点：系列详情 → 展开款式 → 长按颜色行 → 编辑基础（名称/分类）
#    → 名称填「黄色蜜糖邦尼背心裙」→ 保存
#    预期：① toast 报「已把款式名改为「蜜糖邦尼背心裙」（原「背心裙」）；同款 2 个颜色…」
#          ② 款式组标题变「蜜糖邦尼背心裙 · 2 色」
#          ③ 点菜式选购页卡片标题同步变「蜜糖邦尼背心裙」（← 用户截图里那一处）
```

2. **衣橱 / 心愿里已存在的记录名不会跟着改名**（刻意口径，见 §3.2 第 7 条）。
   界面 toast 会如实报告条数，用户可在衣橱内单独改。
3. **标题显示款式名、不显示完整 SKU 名** 是本次**没有改**的既有硬规则。
   如果产品期望的是「标题照抄名称字段（含颜色词）」，那是另一条需求
   —— 会牵动「· N 色」标注、颜色 chips、详情页配色行的一致性，需要单独评估。
4. **改成与同系列同品类下另一个款式同名** 时，两者在数据上合并为同一款：
   款式档案按「目标档案优先、补空缺字段」无损合并（`§3.2` 第 6 条），
   但**两个款式的商品不会合并**（它们仍是各自 id 的 product，只是共享款式名与档案）。
   这个边界目前没有界面提示。
